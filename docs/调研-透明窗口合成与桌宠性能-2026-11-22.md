# 调研：Windows 桌面 agent 的性能与合成优化（透明 Electron + Live2D）

> 对象：`<project-root>` 的 Electron 透明皮套窗、Live2D 715 drawable、拖动冻结渲染
> （实测 ±40px 从 53fps 到 166fps）。
> 日期：2026-11-22。方法：Electron/Chromium 官方文档与源码、Microsoft Win32/DWM 文档、
> 本项目实测文档与 `_probe/` 代码。只写实际核到的内容；核不到的单列在文末。

## 结论先行

1. Windows 上 Electron 的透明窗**默认不是 `WS_EX_LAYERED`**，而是 Chromium 用 `DwmExtendFrameIntoClientArea(-1)` + Direct3D 做的「emulated layered window」；因此透明像素**不会自动点击穿透**，且 `WS_THICKFRAME` 被禁用（用户拖边改尺寸不可用），这是硬约束，不是配置问题。
2. 拖动卡顿的根因是「窗口位移 + 每帧整窗重绘」叠加；拖动时冻结渲染的方向正确，但验收脚本测到的 166 是 **rAF 回调频率**，不是呈现帧率——冻结期间它只能证明调度器没被堵死，不能证明画面真的在 166fps 更新。
3. 最值得做的不是继续抠 715 个 drawable，而是先把「合成面积 + 合成路径」固定下来：保持 420×760 小窗（废弃/限制显示器并集兜底）、不在宠物窗叠 `backdrop-filter` / `backgroundMaterial`、不用 `setOpacity`、transparent resize 只在 drag-end 做一次；动画只动 transform/opacity。这样收益最大、风险最低。

## 证据

### 1. Electron 透明窗在 Windows 上到底是什么

- Chromium 的 `HWNDMessageHandler` 在 `is_translucent_` 时执行：
  - `MARGINS margins = {-1, -1, -1, -1}; DwmExtendFrameIntoClientArea(hwnd(), &margins);`
  - `::SetProp(hwnd(), ui::kWindowTranslucent, ...)`
  - 源码：`chromium/src/ui/views/win/hwnd_message_handler.cc` 第 2117–2125 行（`OnCreate`）。
- 同一文件第 1963–1970 行的注释说明：`WS_EX_LAYERED` 会让透明像素的点击自动落下，但「用 Direct3D 绘制透明窗口时并非如此」，所以 Chromium 把 translucent 窗口路由到 delegate 的自定义 hit mask。→ **透明区域不会自动穿透**，需要自己做命中测试/`setIgnoreMouseEvents`。
- 同一文件第 1227–1237 行：`WS_THICKFRAME` 用于 resizing，「Cannot be used with translucent windows」；`can_resize = !is_translucent_ && delegate_->CanResize()`。→ 透明窗的用户拖边 resize 被禁用。
- 同一文件第 3425–3437 行：translucent 窗口 resize 时给 `SetWindowPos` 加 `SWP_NOCOPYBITS`，注释指向 crbug.com/739724「Copying the old bits can sometimes cause a flash of black when resizing」。→ 即使程序化 resize，也有黑闪/重绘风险。
- Electron 侧同样有明确约束：
  - `shell/browser/native_window_views.cc` 第 222–225 行：`// Transparent window must not have thick frame.`，`if (transparent()) thick_frame_ = false;`
  - 第 294–309 行：`if (transparent() || has_client_frame()) params.opacity = kTranslucent;`；`if (IsTranslucent() && !has_frame()) params.shadow_type = kNone;`
  - 第 740–758 行：Windows 上 transparent 窗口的 `Maximize()` 不是原生最大化，而是 `SetBounds(display.work_area(), false)` 手工铺满工作区。
- Electron 官方性能指南（`docs/tutorial/performance.md` 第 253–254 行）的原话：「If your window is rendering a buttery-smooth animation, it'll need to talk to the GPU process about that – once again going through the main process.」→ 主进程里的同步工作（`getBounds`、`setSize`、同步 IPC）会直接拖慢动画；拖动 IPC 里的窗口查询必须节流（项目已在 2026-11-21 把尺寸校正节流到 250ms）。
- 结论：`transparent: true` 在 Windows 上等价于「无边框 + DWM frame extension + Direct3D 合成」，不是「一个可以随便 resize/穿透的普通窗口」。

### 2. 官方文档写死的限制

Electron `docs/tutorial/custom-window-styles.md`（`Transparent windows → Limitations`）原文：

- You cannot click through the transparent area（#1335）。
- Transparent windows are not resizable；设 `resizable: true` 可能让透明窗在某些平台直接失效。
- CSS `blur()` 只作用于窗口的 web contents，**不能模糊窗口下方其他应用**。
- DevTools 打开时窗口不再透明。
- Windows：不能用系统菜单/双击标题栏最大化（PR #28207）。

Electron `docs/api/structures/base-window-options.md`：

- `transparent`：Windows 上必须 frameless 才生效；`backgroundColor` 的 alpha 只在 `transparent: true` 时支持。
- `backgroundMaterial`：Windows，`auto/none/mica/acrylic/tabbed`，设置系统绘制的背景材质（含非客户区）。
- `roundedCorners`：无边框窗是否圆角，默认 true；Win11 Build 22000 以下无效。
- `thickFrame`：Windows 无边框窗是否用 `WS_THICKFRAME`；设 false 会移除阴影/窗口动画并禁用拖边 resize。
- `hasShadow`：默认 true；transparent + frameless 时 Electron 源码会强制 `shadow_type = kNone`（见上）。

Electron `docs/api/browser-window.md`：

- `win.setBackgroundMaterial(material)`：仅 Windows 11 22H2 及以上。
- `win.setIgnoreMouseEvents(ignore[, options])`：`forward: true` 在 Windows 上把 mouse move 转发给 Chromium；Windows 上 `forward: true` 在更高完整性级别窗口（如管理员权限）前会暂时失效。
- `backgroundThrottling`：关闭后，窗口最小化/被遮挡/隐藏时 `visibilityState` 仍保持 visible；官方建议在 hidden 时暂停昂贵操作。

### 3. Chromium/Electron 源码级证据（比文档更硬）

| 事实 | 源码位置 | 对我们的含义 |
|---|---|---|
| 透明窗走 DWM frame extension，不是 `WS_EX_LAYERED` | `ui/views/win/hwnd_message_handler.cc:2117-2125` | 不要假设透明像素会自动穿透 |
| `WS_EX_LAYERED` 与 Direct3D 透明窗的 hit-test 语义不同 | 同文件 `:1963-1970` | 需要自己维护命中区域/穿透状态 |
| translucent 不能加 `WS_THICKFRAME` | 同文件 `:1227-1237` | 用户拖边 resize 不可用；不要把它当普通可缩放窗口 |
| translucent resize 要 `SWP_NOCOPYBITS` 防黑闪 | 同文件 `:3425-3437` | 运行时改尺寸有视觉风险；能重建就重建 |
| `transparent` 强制 `thick_frame_ = false` | `shell/browser/native_window_views.cc:222-225` | 透明 = 无 thick frame，resize/阴影/动画都被连带影响 |
| `transparent` 把窗口设为 translucent，无边框时无阴影 | 同文件 `:294-309` | `hasShadow: false` 是冗余但无害；不要指望有系统阴影 |
| 透明窗的 `Maximize()` 是手工 `SetBounds(work_area)` | 同文件 `:740-758` | 最大化会把透明窗铺满屏幕，合成面积暴涨；宠物窗应 `maximizable: false` |
| `setOpacity` 在 Windows 上调用 `SetLayered()` + `SetLayeredWindowAttributes(LWA_ALPHA)` | 同文件 `:1383-1393` | 会把窗口变成真正的 `WS_EX_LAYERED`，和默认 translucent 路径不是同一条 |
| `SetLayered()` 只是给窗口加 `WS_EX_LAYERED`，不会移除 | 同文件 `:1892-1900` | 一旦调用 `setOpacity`，这个 style 会常驻 |
| `setIgnoreMouseEvents` 会加/删 `WS_EX_TRANSPARENT | WS_EX_LAYERED` | 同文件 `:1399-1408` | 高频 toggle 会反复改窗口 style，和透明路径叠加 |
| `backgroundMaterial` 在无边框窗上会 `is_translucent = true`，并 `DwmExtendFrameIntoClientArea(-1)` | 同文件 `:1661-1704` | 宠物窗不要设 acrylic/mica；它会把窗口推入 translucent 路径并带系统 backdrop 成本 |

补充：`setOpacity` 的实现只设置 `LWA_ALPHA`，并不移除 `WS_EX_LAYERED`。所以「淡出到 0 再淡入」之后，窗口仍然是 layered window；这和 Chromium 的 translucent/Direct3D 路径混用，至少会改变命中测试与合成语义。建议把「透明宠物窗上的 `setOpacity`」列为禁用项，用 CSS `opacity` 做淡入淡出。

### 4. DWM / 分层窗口的已知行为

- Microsoft `Layered Windows` 文档：
  - 用 `WS_EX_LAYERED` 的窗口，系统会自动合成并重绘分层窗口及其下方窗口；适合复杂形状、动画、alpha blending。
  - 创建后必须调用 `SetLayeredWindowAttributes` 或 `UpdateLayeredWindow` 才可见。
- Microsoft `UpdateLayeredWindow` 文档：
  - 该函数更新分层窗口的位置、大小、形状、内容和半透明；
  - 被它覆盖/露出的下方窗口**不需要重绘**，系统会自动重绘；
  - 原文：「This permits seamless animation of the layered window.」
  - → 分层窗口的「移动/动画」本身有系统级优化；但 Chromium 的透明窗默认不走这条路，所以不能直接套用「分层窗口动画很便宜」的结论。
- Microsoft `DWM_SYSTEMBACKDROP_TYPE` 文档：
  - `DWMSBT_MAINWINDOW`（Mica，长生命周期窗口）、`DWMSBT_TRANSIENTWINDOW`（Acrylic，瞬态窗口）、`DWMSBT_TABBEDWINDOW`（Tabbed）；
  - Electron 的 `backgroundMaterial` 就是把 `mica/acrylic/tabbed` 映射到这些枚举（`native_window_views.cc:104-115`）。
  - → 系统 backdrop 是 DWM 绘制的，不是 CSS；它和 `transparent: true` 是两条不同的「透明」实现，组合前必须实测，不要把它当 CSS 毛玻璃用。

### 5. 毛玻璃/模糊的成本

- Electron 文档已经写明：CSS `blur()` 只作用于 web contents，不能模糊桌面下方内容。所以「透明窗 + `backdrop-filter` 让桌面变毛玻璃」这个预期本身不成立。
- 页面内的 `backdrop-filter` 仍然有成本：
  - Motion 的《Web Animation Performance Tier List》（2025-11-05）指出：`filter: blur()` 虽然硬件加速，但「cost can escalate sharply with every increased pixel of blur radius, and with larger layers」；blur 还会让 layer 更大、增加显存；`backdrop-filter` 也会促使元素成为独立 layer。
  - 该文把「只改 transform/opacity 的合成动画」列为 A-tier；把触发布局/绘制的属性列为更低 tier。
  - 来源：`https://motion.dev/magazine/web-animation-performance-tier-list`。
- Chromium `docs/how_cc_works.md`：
  - cc 负责把 painted input rasterize/decode 成 GPU texture，再作为 compositor frame 交给 display compositor（第 17 行）。
  - property trees 把 transform / clip / effect 分开；transform/opacity/filter 的动画直接改 TransformNode / EffectNode（第 106–117、286–290 行）。
  - → transform/opacity 是合成器友好的属性，通常不触发布局/绘制；是否真正跑在合成线程，取决于元素是否被提升为 composited layer。动 width/height/top/left/backdrop-filter 会回到 layout/paint，成本通常显著更高。

### 6. 本项目实测与代码

- 实测数字（`docs/审计-为什么性能问题没暴露-2026-11-21.md:4-6`）：
  - 静止 76fps；窗口每帧位移 ±1px 79fps、±20px 62fps、±40px **53fps**、±80px 38fps；
  - 同时 `setInterval` 精度一起崩（1.5s 只跑 43 次移动）——合成器被窗口移动占满的正反馈；
  - 修完后 ±40px 是 **166fps**。
- 冻结渲染的实现（`pet-runtime/desktop/petbody-entry.mjs:1255-1285`）：
  - 主循环仍然 `requestAnimationFrame(frame)`；
  - 如果 `window.__pbDragging` 且 `Date.now() - __pbDraggingAt < 1500`，`state.dragFrozenFrames += 1` 并直接 `return`，不画这一帧；
  - 注释明确：「拖动时画面内容不需要变（她只是被搬走）：冻结后 Chromium 只更新窗口位置，GPU/合成压力骤降」。
- 验收脚本（`_probe/drag-perf-accept.cjs:69-88`）：
  - 在拖动（±40px、每 16ms）期间，用 `requestAnimationFrame` 自己数 1.2 秒的 `frames`，算 `fps = frames / 1.2`，断言 `fps >= 100`；
  - 同时断言 `dragFreezeState().frozenFrames` 增长、松手后停止增长。
  - → 这个 `fps` 是 **rAF 回调频率**；冻结期间渲染循环在 `return` 前已经 `requestAnimationFrame`，所以它能测到调度器频率，但不等于「实际呈现帧率」。
- 毛玻璃成本（`docs/审计-为什么性能问题没暴露-2026-11-21.md:34-37`）：
  - 皮肤层多处 `backdrop-filter`（8px / 9px / 20px）；
  - 项目此前没有「这层毛玻璃值多少 GPU」的单价；拖动时关掉毛玻璃是第一次量化「透明窗口 + 拖动时每帧重采样桌面」的成本。
- 窗口创建（`_incoming/my-neuro/live-2d/main.js:746-789`）：
  - `transparent: true`、`frame: false`、`alwaysOnTop: true`、`backgroundColor: '#00000000'`、`hasShadow: false`、`type: 'desktop'`、`backgroundThrottling: false`、`resizable: true`、`maximizable: false`；
  - `win.setAlwaysOnTop(true, 'screen-saver')`；`win.setIgnoreMouseEvents(startIgnoring, { forward: true })`。
  - 注意：`resizable: true` 对 translucent 窗口不会恢复用户拖边 resize（Chromium 源码 `can_resize = !is_translucent_`），属于无效配置，且 Electron 文档提示在部分平台可能让透明窗失效；`hasShadow: false` 也是冗余（transparent + frameless 已强制无阴影）。
- 窗口尺寸（`_incoming/my-neuro/live-2d/config.json:164-169`）：`pet_window` 为 **420×760**，小窗模式生效。
- `setOpacity` 在宠物窗上是「潜伏路径」：`main.js:655-682` 的 `hidePetForMove` / `revealPetAfterMove` 用 `setOpacity(0)` / 恢复，但源码里未找到调用方；`main.js:2423-2426` 的 `set-window-opacity` IPC 也没有渲染层调用方。它当前不生效，但一旦被用来做切屏淡出/淡入，就会触发上面的 `WS_EX_LAYERED` 路径。控制窗（`control-main.js:1045`）的 `setOpacity` 是另一条路径，不在本文讨论范围。
- 巨窗兜底（`main.js:537-596`）：
  - 如果 config 没有 `ui.pet_window`，`computePetWindowBounds` 会走「所有显示器并集」，返回 `totalWidth × totalHeight`；
  - 源码注释还保留「6.55 巨窗并集」的日志。
  - → 这是最坏情况：一个覆盖所有显示器的透明窗口，DWM 要合成整块 alpha surface；建议加硬上限或直接废弃该分支。
- 拖动 IPC（`main.js:2258-2290`）：
  - 每个 `pet-drag-to` 调 `win.setPosition(..., false)`；
  - 每 250ms 做一次 `getBounds()` + 必要时 `setSize()`，用来压住跨 DPI 拖动时的窗口放大（420→501→715 实测）；
  - 渲染层 `js/avatar/petbody/ui.js:253-270` 已经用 `requestAnimationFrame` 合并 mousemove，一帧只发一次。
  - → 拖动期间仍在做「程序化 resize」，而 translucent 窗口 resize 会走 `SWP_NOCOPYBITS` 防黑闪；这是剩余抖动的可疑来源之一。
- 点击穿透（`js/avatar/petbody/ui.js:40-46`）：
  - `sendIgnore` 有 `lastIgnore` 边沿去重，不会每次 mousemove 都发；
  - 但 `setIgnoreMouseEvents` 本身会加/删 `WS_EX_TRANSPARENT | WS_EX_LAYERED`（Electron 源码 `:1399-1408`）；如果同时用过 `setOpacity`，`layered_` 为 true，切换语义会变。
- 715 drawable：`docs/复盘-项目演进-2026-11-15.md:10`「Electron 透明窗 + Cubism5 渲染（715 drawable / 23 表情）」。这是渲染成本，但不是当前拖动瓶颈的主因（冻结后 rAF 恢复）。
- GPU 状态：Electron `app.getGPUFeatureStatus()` 返回 `chrome://gpu/` 的 Graphics Feature Status，需在 `gpu-info-update` 之后读（`docs/api/app.md:1615-1621`）。透明窗如果落到软件合成，成本会完全不同；应把这个状态纳入 doctor。

### 7. 桌面宠物同类项目

- **Shimeji-ee**：Java/JVM 桌面宠物，原项目在 Google Code 归档，GitHub 上是社区 fork（如 `DalekCraft2/Shimeji-Desktop`，把 JRE 6 升到 JDK 25）。它是 JVM 路径，和 Electron/Chromium 的 DWM 路径不同，透明窗口的具体实现不能直接搬。
- **DesktopMate**：Steam 上的商业桌面宠物；未找到官方源码。社区有 Mod 加载器（如 `YusufOzmen01/desktopmate-custom-avatar-loader`），但那不是窗口合成实现，不能作为性能依据。
- **Mate-Engine**：开源 Unity 桌面宠物（`shinyflvre/Mate-Engine`），README 可核；但本次未核到其透明窗口脚本的具体文件/行号，因此不引用其实现细节。
- 结论：同类项目能提供「小窗 + 逐像素 alpha + 点击穿透」的形态证据，但**没有可核的、比 Chromium 源码更权威的 Windows 合成性能资料**；本文以 Chromium/Electron/Win32 文档为主。

## 我们能落地的

| 改动 | 收益 | 代价 / 风险 | 优先级 |
|---|---|---|---|
| 指标改名/拆分：`rafHz`（rAF 回调频率）与 `presentedFps` / `longFrames`（实际呈现）分开；冻结期间只报 `rafHz`，不再把 166 叫「渲染帧率」 | 避免用「调度器没堵」误判「画面流畅」；回归能被真正看见 | 需要接 CDP/GPU trace 或至少用 `requestAnimationFrame` 的时间戳算 p50/p95；多一个采集点 | P0 |
| 透明宠物窗禁用 `win.setOpacity`；淡入淡出改 CSS `opacity`（根元素/容器） | 避免 `setOpacity` 把窗口切成 `WS_EX_LAYERED`，与 Chromium 的 translucent/Direct3D 路径混用 | CSS opacity 由页面合成，不改变 OS 窗口 style；但宠物窗内容就是全部，够用 | P0 |
| 透明宠物窗禁止用户 resize / 禁止运行时改尺寸；固定 420×760，换尺寸走「重建窗口」 | 规避 `WS_THICKFRAME` 禁用与 `SWP_NOCOPYBITS` 黑闪；减少拖动中的 resize 抖动 | 重建窗口有状态迁移成本；需要保存/恢复窗口位置与渲染状态 | P0 |
| 拖动期间保持冻结渲染 + 关闭 `backdrop-filter`（已做）；把主循环从「rAF 里 early-return」改成「drag-start `cancelAnimationFrame`、drag-end 重启」 | 少一层空转 rAF；冻结期间不再每帧进 JS | 需要可靠的 drag-end/超时兜底（现有 1.5s/3s 新鲜度可复用） | P1 |
| 宠物窗不要设 `backgroundMaterial`/acrylic/mica；需要毛玻璃的设置面板另开一个小窗 | 避免把宠物窗推入 translucent + 系统 backdrop 路径；减少 DWM 重采样 | 多一个窗口；小窗的透明/圆角要单独调 | P1 |
| 动画只动 `transform` / `opacity`；不要动 `width/height/top/left/backdrop-filter` | 避免 layout/paint；transform/opacity 是合成器友好属性（是否上合成线程取决于 layer 提升） | 现有皮肤若用 top/left 做位移，需要改写；Live2D canvas 本身不受影响 | P1 |
| 保留小窗模式，给「显示器并集」分支加硬上限（如最大 1.5 屏）或直接废弃 | 防止 config 缺失时创建一个屏幕大小的透明 surface；合成面积可控 | 跨屏移动需要另一套坐标方案；可能影响「拖到副屏」体验 | P1 |
| 拖动中不要做程序化 `setSize`；跨 DPI 撑大只在 drag-end 校正一次 | 去掉 translucent resize 的黑闪/重排；拖动更稳 | 拖动过程中可能短暂变大 1–2 帧；用 CSS 缩放遮一下 | P1 |
| 点击穿透只在「进入/离开可交互区域」时 toggle，保持现有 `lastIgnore` 边沿去重；不要在 mousemove 里反复 `setIgnoreMouseEvents` | 减少 `WS_EX_LAYERED` style churn；避免和 translucent 路径打架 | 需要命中测试的边界判定；现有 `elementFromPoint`/alpha 判定可复用 | P1 |
| doctor 加 GPU 状态：`app.getGPUFeatureStatus()`，软件合成时降级（Live2D 分辨率/帧率/特效） | 透明窗在软件合成下会灾难性变慢；提前发现驱动/GPU 进程问题 | 需要定义降级策略；`gpu-info-update` 之后才可读 | P1 |
| 性能预算进 doctor：拖动 `rafHz` p50/p95、`longFrames`、面板打开 ms、字幕出现 ms | 把「顺不顺」变成可回归的指标；对应审计文档的「缺性能预算」 | 需要统一采集口径；历史数据要重算 | P2 |
| 评估「固定大窗 + 内部 transform」vs「移动小窗」：前者省 `SetWindowPos`，但增大透明面积 | 如果窗口移动仍是瓶颈，这是一条替代路径 | 大窗的 DWM 合成成本可能更高；必须 A/B 实测，不能拍脑袋 | P2 |
| 降低 Live2D drawable / idle 降帧（715 → 更低） | 减少 GPU/CPU 绘制成本；对静止/低功耗场景有效 | 影响画质/表情丰富度；优先级低于合成路径 | P2 |
| 用 CDP/GPU trace 采「实际 present 帧」与长帧 | 补上 `rafHz` 看不到的呈现层问题 | 采集成本/权限；只在性能验收时开 | P2 |

### 场景化建议（什么时候移动窗口 vs 什么时候 setOpacity）

| 场景 | 建议 | 理由 |
|---|---|---|
| 宠物整体被拖走 | 移动**小窗口**，每 rAF 一次 `setPosition`；拖动期间冻结渲染 | 窗口位移是必要的；冻结避免「移动 + 重绘」叠加 |
| 宠物在窗口内走动/转身/做动作 | **不要移动窗口**；在 canvas 内用 transform 移动精灵 | 窗口不动，DWM 不需要重合成整个 surface；transform 通常比移动窗口便宜 |
| 淡入/淡出/隐藏 | **CSS opacity**，不要 `win.setOpacity` | 避免 `WS_EX_LAYERED` 与 translucent 路径混用 |
| 跨屏/跨 DPI | drag-end 后校正一次尺寸/位置；不要拖动中反复 `setSize` | translucent resize 有 `SWP_NOCOPYBITS` 黑闪风险 |
| 需要桌面毛玻璃 | 单独小窗 + `backgroundMaterial: 'acrylic'`（Win11 22H2+），或干脆不做 | CSS blur 不能模糊桌面；系统 backdrop 有自己的合成成本 |
| 需要点击穿透 | `setIgnoreMouseEvents(true, {forward:true})` + 命中测试，边沿触发 | 透明像素不会自动穿透（Chromium 源码注释） |

## 明确不适用（以及为什么）

- **用 `backdrop-filter` 让透明窗模糊桌面。** Electron 文档明确：CSS `blur()` 只作用于窗口 web contents，无法模糊窗口下方其他应用；桌面毛玻璃的官方可用路径是 DWM `backgroundMaterial`，而它有 Win11 22H2+ 与 translucent 路径约束。
- **用 `win.setOpacity` 做宠物淡入淡出。** Windows 实现是 `SetLayered()` + `SetLayeredWindowAttributes(LWA_ALPHA)`，会把窗口变成真正的 `WS_EX_LAYERED`；Chromium 的透明窗默认走 DWM frame extension + Direct3D，两者混用会改变命中测试/合成语义。
- **运行时拖边 resize 透明窗。** Chromium 对 translucent 窗口不设 `WS_THICKFRAME`；程序化 resize 也会用 `SWP_NOCOPYBITS` 防黑闪。需要改尺寸就重建窗口。
- **把透明窗最大化。** Electron 在 Windows 上是 `SetBounds(work_area)` 手工铺满，不是原生最大化；透明 surface 会变成整屏，合成成本暴涨。宠物窗保持 `maximizable: false`。
- **直接照搬 WPF `AllowsTransparency` / 分层窗口方案。** WPF 的 layered window 是另一条路径（保留 bitmap、GDI/DirectX airspace 问题），和 Electron/Chromium 的 DWM frame extension 不同；WPF 的「分层窗口动画很便宜」不能直接套到 Electron。
- **直接把 DesktopMate 当实现参考。** 未找到官方源码；社区只有 Mod 加载器，没有窗口合成源码。Shimeji-ee 是 JVM 路径，也不能直接搬。
- **把 166 当成「渲染 166fps」。** 验收脚本数的是 rAF 回调；冻结期间渲染循环在 `return` 前已经请求下一帧，所以 166 只证明调度器频率，不证明画面呈现。
