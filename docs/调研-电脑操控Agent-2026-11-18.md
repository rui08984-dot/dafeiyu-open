## 0. 三个判断（先说结论）

1. **我们不是「没有 agent」，是「没有目标态」。** 宿主早已有 30 轮工具循环
   （`js/ai/llm-handler.js:377 maxIterations = 30`，含打断、连续空响应恢复），
   也有**单动作级**验证契约（`verify-contract.js` 的 `verified/effect/action_sent/nextIfFailed`，L1 像素/L2 UI 树/L3）。
   缺的是**任务级成功判据**——所以「做完没有」只能由模型的沉默决定。OSWorld 把这件事做成了纯函数，这是我们最该抄的一条。
2. **长任务的能力上限由「验证」决定，不由「规划」决定。** planner 只能猜下一步该干什么，
   谁来告诉它猜错了？没有 oracle 的重规划会变成「换个方式瞎试」。故补强顺序必须是 **验证 → 熔断/恢复 → 计划 → 记忆**。
3. **动作空间该收不该放。** UI-TARS-desktop 用 **10 个动作**打 OSWorld；Agent-S 用 **12 个**；
   OSWorld 基线 **16 个**（含 FAIL/DONE）。我们 `act` 对外 12 个、底层 `game-control.js` **38 个 case**。
   38 个 case 里约 10 个是采集原语/元工具/单游戏特化，它们占提示词、稀释选择，却不增加能力。

## 2. 我们缺什么（四个短板逐条对上做法）

现状校准（避免重复造）：宿主**已有** 30 轮工具循环、单动作验证契约、技能库、SoM 编号、UIA 服务降级链。
所以下面四条都是「在既有件上加一层」，不是新建子系统。

### 2.1 planner：缺「计划对象」，不缺「思考循环」

- **现状**：模型在 30 轮循环里边想边做，计划只存在于对话上下文里（`llm-handler.js` 直接把 `voiceChat.messages` 发给模型）。
  后果可观测：轮数上限是唯一的「停止」机制；一旦跨过 5–6 步，模型会忘记第 2 步做过什么（上下文里全是工具返回的噪声）。
- **做法**（Agent-S 的数据流 + 我们 ADR-004 的注入纪律）：
  1. 计划是一个**小对象**：`[{id, text, status: todo|doing|done|failed, verify?}]`，存宿主插件，不进 system；
  2. 每轮只把**变化**（≤80 tokens）注入最后一条 user 的易变尾巴——与 `world-sense` 完全同一条纪律（前缀 hash 不许变）；
  3. 重规划输入是结构化的：`failed_subtask + completed[] + remaining[]`（`manager.py:173` 的 `generator_message` 就是这个形状）；
  4. **不做 DAG**。Agent-S 需要 DAG 是因为 OSWorld 任务里有并行依赖（下文件→装→开）；我们的任务是线性的，
     拓扑排序换来的是两次额外 LLM 调用和一套解析器。等真出现并行子任务再说。
- **判据**：3 个 ≥8 步任务端到端成功率从 0/N 到 ≥2/3，且前缀缓存命中不掉（≥90%）。

### 2.2 验证：单动作已有，任务级为零

- **现状**：`verify-contract.js` 把「这个动作生效了吗」做到了极致（L1 像素 dHash / L2 UIA 回读 / L3 不验证，
  外加 `action_sent` 这个「能不能安全重试」的判据——这一条比大多数开源项目都强）。
  缺的是「**整个任务成功了吗**」：`skill-library.js` 只能用 `exitHash`（dHash 相似度 ≥0.75）近似，等于用像素猜语义。
  但**读取器其实已经有了**：`edit_text`（WM_GETTEXT 回读输入框）、`get_value`、`clipboard read`、
  `read_text`（UIA TextPattern）、`see windows` —— oracle 的 getter 应当直接复用它们，而不是新写一套。
- **做法**（OSWorld 三元组）：每个任务/技能声明一个 **oracle**：
  ```
  oracle = { result: <getter>, expected: <getter 或常量>, metric: <纯函数>, conj? }
  ```
  getter **必须读外部真实状态**（文件内容、窗口标题、UIA 文本、计算器显示区），**禁止读工具返回值**——
  这是「真假成功」治理的根（`docs/复盘-真假成功与系统性治理-2026-11-09.md` 同一结论）。
  三条纪律来自 Terminal-Bench：① oracle 必须被 gold 动作序列验证过；② 任务带隐藏测试（agent 不可见）；
  ③ 失败要能区分「没做到」与「做到了但方式不同」（用多判据 `or`，如 OSWorld 的 `conj:"or"` + 两个 gold 文件）。
- **判据**：抽 5 个现有任务，把工具返回值改成「谎报成功」，oracle 仍判 5/5 失败。
  这一条过了，才允许谈长任务。

### 2.3 恢复：有建议字段，没有消费者

- **现状**：`nextIfFailed` 已经写进了每个动作的结果里，但**没有任何代码读它**——它只是给模型看的一句话。
  实测过的恢复手段只有「再试一次同样的动作」或「换一个工具」，没有熔断。
- **做法**（反射与决策分层 + 熔断）：
  1. **循环检测**：连续 N 次（N=2）动作后 `effect='suspected_noop'` → 强制换 grounding 档（ADR-008 的阶梯），
     而不是原地重试。browser-use 的 `no change` 一行结论就是为此设计的；我们的 dHash 已经在算，只是没有"连续计数"。
  2. **反射**用**独立一次调用**、且**禁止给建议**（`REFLECTION_ON_TRAJECTORY` 的硬约束）——
     反射层给建议会与决策层打架，实测表现是模型开始执行"反射里提到但没验证过"的动作。
  3. **恢复阶梯**（代价递增）：幂等重试 → 换 grounding 档 → 重规划剩余子任务 → `ask_user` → `fail`。
     每上一档必须记一条 evidence，否则无法事后归因。
  4. **不可重试的动作**由 `action_sent=true && verified=null` 直接封死重试（已有契约，缺的是执行者遵守它）。
- **判据**：注入 4 类故障（窗口最小化 / 模态弹窗遮挡 / 目标按钮 disabled / UIA 树空壳），
  恢复成功率 ≥3/4，且**误伤计数 = 0**（不允许为了通过而点到别的按钮）。

### 2.4 长任务记忆：有技能，没有「教训」

- **现状**：`skill-library.js` 已经是 Voyager 那一套的正确形态（entryHash 进入场景校验、exitHash 退出校验、
  Beta(1,1) 后验、只认 verified 成功、REPLAYABLE 白名单排除靠运行时编号的动作）。
  缺两块：① 记忆只有「成功的动作序列」，没有「这类任务该怎么想、上次为什么失败」；
  ② 检索粒度是"整条技能"，没有 Agent-S 那种 narrative（任务级）/ episodic（子任务级）两级。
- **做法**：
  1. **任务级 narrative**：任务结束后写一条 `{task_signature, plan_that_worked | why_failed, steps_used}`，
     嵌入走已有的 8090 服务；
  2. **子任务级 episodic**：只对「失败过的子任务」写，内容是「换哪条路成功的」；
  3. **只在 t=0 检索**（`manager.py:122` 的 `if self.turn_count == 0`）——一次任务只付一次召回成本，
     与 ADR-004 的 token 红线一致；
  4. 检索命中要在日志里留 evidence，否则无法评估记忆是否真的有用（否则就是"感觉有记忆"）。
- **判据**：同一类任务第二次执行的步数下降 ≥30%，且日志里能看到被引用的 lesson id。

### 3.2 该加（3 个，全部是「控制流」而非「能力」）

1. **`finish` / `fail`**（或合并成 `done(ok, reason)`）。为什么必须有：现在"做完了"表现为模型不再调工具，
   "卡住了"表现为模型一直调工具直到 30 轮——两者在日志里几乎不可区分，技能库与评测都无法归因。
   OSWorld 的 `infeasible` 任务（26/368）正是靠这个信号计分的。
2. **`ask_user(question)`**。UAC/密码框/歧义选择（"存到哪个目录"）当前会让模型去猜。
   伴侣型产品里「她问一句」的体验成本远低于「她点错了」。
3. **`wait(ms)`**。安装、加载、弹窗动画。现在靠 scroll/drag 制造延时或盲重，污染动作历史。

### 3.3 该删/该下沉（让 12 个可见动作真的只有 12 个）

| case | 问题 | 处置 |
|---|---|---|
| `mc` / `pvz` / `pvz_state` / `list_game_profiles` | 单游戏特化（违反「代码不能特异化」判据） | 下沉到 `game` profile 实现，不作为 `act` 分支 |
| `wgc_hash` / `wgc_shot` | 采集原语，不是语义动作 | 归 Rust 内部能力 |
| `recent_actions` / `project_status` / `knowledge` / `skill` | 元工具（记忆/查询），不属于"操控" | 移出 `game-control` 命名空间，独立工具 |
| `semantic` | 历史兼容层 | 若无调用方即删 |
| `edit_text` | 是**读**（WM_GETTEXT 回读输入框），却排在动作表里，与 `get_value` 职责重叠 | 归入 `see`/读类，动作表只留写操作 |

> 判据（沿用项目铁律）：换一个应用要不要改这段代码？——上表每一项都是"不用改"，所以它们本就不该在动作表里。

### 3.4 grounding：我们已有一条阶梯，缺的是「升档判据」

现有链（实测）：**UIA 直调 Invoke/SetValue → UIA 编号点击 → SoM 标注图编号 → 物理坐标点击**，
其中 `snapshot` 已经能诊断 `shellOnly`（UIA 树是空壳）、`scanned`（扫了多少节点）、`chromiumWoke`，并在 0 元素时建议 `som_snapshot`。

该补的三件事：
1. **归一化坐标契约**（UI-TARS 的 factor + `scaleFactor`）：SoM 图被压缩时已有 `scale` 与刻度尺，
   但物理坐标点击仍是裸像素。跨 DPI/多显示器时这是隐患（我们已为游戏踩过 DPI 坑）。统一成「交付坐标 = 归一化 + 显示器标识」。
2. **元素去重与标签合并**（OmniParser `remove_overlap_new`）：OCR 文本落在图标框内时**并入图标**而不是单独编号。
   我们的 `click_element` 全屏 dHash 误报、以及"同一按钮在树上出现两次"都属于这类问题。
   注意 OmniParser 的 IoU 是 `max(iou, 覆盖率)`——**不是标准 IoU**，否则嵌套框永远去不掉。
3. **索引生命周期**：已有 `SOM_STATE.seq` 世代号（每次快照递增、旧编号作废），这是正确的。
   补 browser-use 的 `*` 标记思路：新快照里标出「新增元素」，让模型知道"界面变了，别用旧计划"。

## 4. 评测升级：从 10 个工具级任务到 30+ 任务级任务

### 4.1 把 OSWorld 的任务定义落到我们的 `tasks.mjs`

现有 schema：`{id, title, setup, run, verify, cleanup}` + `hostVerify`（Node 侧独立验证）——
**形状已经对了**，`hostVerify` 就是 OSWorld 的 getter+metric 的雏形。缺的是纪律：

| OSWorld 字段 | 我们对应 | 要补的纪律 |
|---|---|---|
| `instruction` | `title` + 任务描述 | 任务必须**只用用户语言**描述目标，不提示操作路径（否则测的是执行力不是理解力） |
| `config`（setup 步骤） | `setup` | 故障注入也放这里，`cleanup` 必须能撤 |
| `evaluator.result`（getter） | `verify` + `hostVerify` | **只读外部状态**；禁止 `return {ok:true}` 这种自证 |
| `evaluator.expected` + `func`（metric） | `hostVerify` 的断言 | 多判据相乘/相或，别写成"包含关键字就算过" |
| `trajectory` | `last-run.json` | 保留每步动作+证据，用于事后归因（现在已有） |
| `possibility_of_env_change` | 无 | 加一个 `stability: high / low`，低稳定任务不进 CI 门禁 |

### 4.2 任务矩阵（10 → 34）

| 类别 | 现有 | 目标 | 例子 | 验收用哪层 |
|---|---|---|---|---|
| 单应用 UIA | 4 | 6 | 记事本读文/UIA 点计算器/窗口 move+size | L2 UIA 回读 |
| 文件·剪贴板·键盘 | 3 | 5 | 剪贴板回环/键盘输入回读/file 工具只读 | 外部状态（文件/剪贴板） |
| **多步复合** | 0 | **6** | "新建记事本→写三行→另存到桌面→读回校验" | 外部文件 + 窗口标题 |
| **不可完成（infeasible）** | 0 | **3** | 目标按钮 disabled / 需要密码 / 目标文件不存在 | 期望 `fail` + **副作用为零**（文件未变、窗口未关） |
| **失败恢复** | 0 | **6** | 窗口最小化、模态弹窗遮挡、UIA 空壳、动作 no-op 后换路 | 恢复成功 + 误伤计数 0 |
| **长任务（≥8 步）** | 0 | **3** | 跨应用：查资料→写入→计算→改回 | oracle（§2.2）+ 步数 ≤ gold×1.5 |
| **grounding 探针** | 0 | **10** | 给截图+元素树，只断言"指的是不是 #k" | point-in-bbox（OpenCUA 思路），不真点 |

配套预算：单任务步数上限按 gold 步数 ×2（对齐 OSWorld `--max_steps 15` 的精神），
保留 p50/p95，**新增**四个指标：成功率、平均步数、恢复成功率、误伤计数。

### 4.3 LLM 级任务怎么跑（不改产品代码）

我们现在的评测是 `8004 /eval → pluginManager.executeTool`，**绕过 LLM**，所以测不到 planner。
两条路：
- **外部同构（立即可做，不改产品）**：eval runner 自己读 `llm_providers.json`，
  用同一条 prompt + 同一套工具描述调模型，工具执行仍走 `executeTool`。
  代价：测的不是宿主 `LLMHandler` 的真实链路（缺易变尾巴注入、缺插件 hooks），结论要标注"同构复现"。
- **宿主入口（需产品侧一个只读端点）**：`POST /agent-run {task, budget}`，返回轨迹。
  属于产品改动，本轮**不做**，记入 ADR-006 的 Action Items。
