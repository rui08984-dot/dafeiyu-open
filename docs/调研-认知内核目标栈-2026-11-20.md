## 2. 六问结论（每条带真实 path:line）

### Q1 目标栈存储 schema

**先纠正一个选型**：Letta 的 memory block 不是目标栈的好模板，**CronTask 才是**。memory block 是自由文本，没有 typed 状态、没有计数器、没有 CAS；CronTask 有完整生命周期字段，见 `letta-code/src/cron/cron-file.ts:66-112`：

- 身份：`id`、`agent_id`、`conversation_id`（`:67-76`）
- 调度：`cron`、`timezone`、`recurring`（`:83-85`）
- 生命周期：`status`（active/paused/fired/missed/cancelled，`:31-36`）、`created_at`、`expires_at`、`last_fired_at`、`fire_count`、`cancel_reason`、`jitter_offset_ms`（`:91-97`）
- 上次结果：`last_run_at`、`last_run_outcome`、`last_run_reason`、`last_run_error`、`missed_count`、`failed_count`（`:99-106`）

**Letta memory block 能借鉴的**：
1. 字段白名单与「保护字段」：block 有 `label / value / limit / read_only / description / metadata`（`letta/schemas/block.py:19-40`），且 MemFS frontmatter 里 agent 只能改 `description`，`read_only` 是受保护字段，不能新增/删除/改值（`letta-code/src/memory-frontmatter.ts:58-104`，`letta-code/src/agent/memory-git-hooks.ts:27-36`）。这正好对应「goal 的 status/budget/attempts 只能由宿主写，LLM 只能写 text」。
2. 预算内联显示：渲染时把 `chars_current` / `chars_limit` 写进 prompt（`letta/schemas/memory.py:154-165`）。对应我们每轮在易变尾巴里写 `steps 3/20 · llm 1/4`，让模型看见真值，而不是让它自己数。

**不能借鉴的**：
1. block 是自由文本，没有 `status` 枚举、没有 `attempts`、没有 `cursor`，无法做状态机与 CAS。
2. V1 的 `limit` **只显示不拒绝**：`update_block_value()` 只检查类型，不检查长度（`letta/schemas/memory.py:771-780`）。这不是预算，只是提示。
3. block 是 agent 全局的，不是 per-goal；多个目标会互相污染。
4. 自编辑**本轮不生效**：`letta-code/src/agent/prompts/letta_root_memfs.md:58` 明说「Editing memory does NOT change your behavior in the current turn」，要等下次 recompile。

**建议的 v1 schema**（在 ADR-011:41-49 基础上补字段；“写者”是硬约束）：

| 字段 | 类型 | 写者 | 说明 |
|---|---|---|---|
| `schema_version` | int | 宿主 | 迁移用 |
| `id` | string | 宿主 | `g-<base36 time>-<rand4>` |
| `rev` | int | 宿主 | 每次变更 +1，CAS/乐观锁 |
| `text` | string ≤200 | 用户 / LLM | 目标描述 |
| `intent_key` | string | 宿主 | 归一化去重键（见 §5 的 40 字符算法，建议加长到 64 + hash） |
| `source` | enum | 宿主 | `user / open_loop / curiosity` |
| `status` | enum | **仅宿主** | `queued / active / paused / done / failed / abandoned` |
| `priority` | int 0–100 | 宿主（LLM 可建议） | 避免 float 比较抖动 |
| `done_when` | OracleRef | 用户 / 宿主校验 | 必填；没有就只能是 note（ADR-011:45） |
| `risk` | enum | 宿主 | `low / medium / high`（ADR-011:47） |
| `budget` | object | 宿主 | `max_steps=20 / max_wall_ms=600000 / max_llm_calls=4`（ADR-011:62） |
| `used` | object | **仅宿主** | `steps / wall_ms / llm_calls`，只增不减 |
| `attempts` / `replans` | int | 宿主 | `replans ≤ 2`（cetana 的默认值，`cetana/cetana/agent.py:52`） |
| `cursor` | int | 宿主 | 最后一个已验证的子任务下标；只增 |
| `plan_id` | string\|null | 宿主 | 指向 ADR-006 的 plan 对象 |
| `blocked_by` | string[] | 宿主 | 依赖的 goal id；v1 可为空 |

| `evidence` | array | 验证器 | `{at, kind, ref, ok, confidence}`，来源+周期+置信度（借 cetana，`cetana/cetana/beliefs.py:22-35`） |

| `created_at / activated_at / last_decision_at / last_attempt_at / last_tick_minute` | epoch ms | 宿主 | `last_decision_at` / `last_tick_minute` 用于重启后的幂等判断 |

### Q2 调度：定时 vs 事件 vs 混合

**Letta 没有墙钟 heartbeat**，它有两层完全不同的循环：

| 层 | 节拍 | 谁决定继续 | 出处 |
|---|---|---|---|
| 单次 `step()` 内的工具循环 | 无时间概念，最多 `max_steps=50` 步 | 模型每次工具调用带 `request_heartbeat`，但 `is_final_step` 硬覆盖为停 | `letta/constants.py:75`；`letta/agents/letta_agent.py:247`（`for i in range(max_steps)`）、`:1884`（`continue_stepping = request_heartbeat`）、`:1907-1910`（hard stop overrides） |
| 用户排程（cron） | **60s tick** | 到点入队，不执行 | `letta-code/src/cron/scheduler.ts:131`（`TICK_INTERVAL_MS = 60_000`）、`:802`（`setInterval`） |
| 后台反思（sleeptime） | **按步数，不按时间**：默认每 25 步 | 步数触发 | `letta-code/src/settings-manager.ts:187-188`（`reflectionTrigger: "step-count"`、`reflectionStepCount: 25`）；`letta-code/src/cli/args.ts:305-317` |
| 最小可排程粒度 | **1 分钟**；小于 60s 向上取整到 `*/1 * * * *` | 解析器 | `letta-code/src/cron/parse-interval.ts:41-47` |

**结论**：Letta 的设计是「请求内有界步进（模型可要求继续，但 50 步硬停）+ 分钟级排程（只入队）」。它没有 30s 心跳，也没有让 tick 直接执行动作。

**我们的 30s 是否合理**：合理，但**应改成「事件优先，30s 兜底」**。

依据：
1. 宿主已有两个节拍：世界采样 1s（`_incoming/my-neuro/live-2d/plugins/community/world-sense/index.js:29`）、发言预算 15s（`_incoming/my-neuro/live-2d/js/core/speech-budget.js:50`）。30s = 2× 发言节拍、30× 世界节拍，不会和采样抢节拍，也不会让日志不可读（ADR-011:89 的原始理由成立）。
2. 默认 `maxWallMs=10min`，30s 给 20 次检查，预算超支最多晚 5% 被发现；60s 会翻倍到 10%，10s 则变成 60 次检查但用户感知不到差别。
3. **活动门不该等 30s**：`world-store` 已经维护 `history` 与 `recentChanges(withinMs)`（`_incoming/my-neuro/live-2d/js/core/world-store.js:408-412`），活动态 `gaming / watching / away` 在 `:111-116` 判定。用户一开游戏，应该由变化事件触发「下一个安全点暂停」，30s tick 只做兜底。ADR-011:83 只写了 30s 检查，这是可以改进的点。
4. tick 绝不能执行动作，只能改状态/入队。Letta cron 就是这么做的：`letta-code/src/cron/scheduler.ts:8`（enqueues matching tasks）、`:414`（`queueRuntime.enqueue`）、`:650`（`fireCronTask`）。
5. tick 必须**可重启幂等**。Letta 的参考实现有洞：`shouldFireTask()` 只按 cron 表达式匹配当前分钟（`letta-code/src/cron/scheduler.ts:282-292`），同一分钟内的去重靠内存 `firedThisMinute`（`:783-784`、`:591-594`），而启动时会立即 tick 一次（`:794`）——**静态推断**：重启落在同一分钟会重复入队。我们应在 goal 里持久化 `last_decision_at` / `last_tick_minute`，不靠内存 Set。

固定 cron 全时轮询仍然否（ADR-011 Option C）；Letta 的 cron 是给「用户显式排程」的，不是给自主性的。

### Q3 安全点与副作用幂等

**安全点的定义**（与 ADR-011:99 一致，但给出源码依据）：

- 一个 cycle 只执行一个 step，执行完就停在边界：`cetana/cetana/agent.py:129-152`（取 `current_step` → `_execute` → `advance`）。
- 计划只允许从 cursor 往后改，已执行前缀不可变：`cetana/cetana/intentions.py:66-71`（`advance()`、`replace_remaining()` 保留 `plan[:cursor]`）。
- 重规划前先 `advance()` 越过失败步，再替换剩余：`cetana/cetana/agent.py:212-213`。这保证「已经做过的步骤」不会被新计划重写或重放。
- 因此安全点 = **cursor 边界 + T1/T2 已完成 + 没有未决写操作**。用户说话、活动态变化、更高优先级 goal 抢占，都只能在这个点发生。

**Letta 的两个可抄做法**：
1. 需要审批的工具在执行前就停：`letta/agents/letta_agent.py:1780-1793`，`continue_stepping = False`，`stop_reason = requires_approval`，不会先做再问。
2. 到达步数上限时，挂起的审批**不执行**，转为 denial 入队：`letta-code/src/websocket/listener/turn-max-turns.ts:36-46`。这是 fail-safe 的正确方向：宁可少做，不可多做。

**副作用幂等怎么做**：
1. **重试闸门用 `action_sent`，不用 `ok`**：`_incoming/my-neuro/live-2d/plugins/community/dispatch/verify-contract.js:23-24` 明确「`ok=false + action_sent=true` 表示发出去了但不确定成没成，这种情况绝不能重试，会做两遍」；`:57` 再次强调它是唯一能决定能否安全重试的字段。我们的 dispatch 已经有这个契约，arbiter 直接消费即可。
2. **写前日志（write-ahead）**：动作发出前先追加一条 ledger：`{goal_id, rev, cursor, step_id, action_hash, action_sent: null, ts}`；动作返回后补 `action_sent / effect / evidence`。重启时任何「有 intent 无 result」的记录都视为**未知**，必须重新读世界（oracle getter），不能自动重试。
3. **checkpoint 只在子任务完成时写**：ADR-011:54 说「每完成一个子任务 checkpoint 一次」，对应 `goals.json` 原子写 + ledger 一行。Letta Code 的 memory 写是每次操作 git commit 并返回 sha（`letta-code/src/agent/memory-git.ts:1230-1267`），思路可借（sha = checkpoint id），但**频率不可借**：30s tick 若每次 commit，一小时 120 个 commit。
4. **单写者**：Letta Code 用文件锁串行化 **harness 侧**的 memory 写入（`letta-code/src/agent/memory-operation.ts:26-58`）；primary agent 自身的编辑不走这把锁，靠 memory-git 的冲突兜底（审计 S-13 已修正措辞）。我们是单 Electron 实例，但仍要防「arbiter 与 LLM 循环同时改同一个 goal」：用 `rev` + CAS，`update(patch, expectedRev)` 不匹配就拒绝并重读。
5. **前置条件**：执行前用 `done_when` 的 getter 读一次「目标前提是否还成立」；前提消失直接 `failed`（ADR-011:111），不要继续。后置条件：T1/T2 失败进 ADR-007 阶梯；不可逆动作必须 T3 才能标 done。
6. **ask_user 是状态不是异常**：问题、选项、超时（默认 5 分钟）写进 evidence（ADR-011:100）。Letta 的 `CONVERSATION_BUSY_WAIT_TIMEOUT_MS = 5 * 60 * 1000`（`letta-code/src/agent/approval-recovery.ts:33`）是同一量级，可作参照。

### Q4 预算 / 活动门 / 熔断

**预算的真实实现**：

| 系统 | 预算 | 值 | 是否强制执行 | 出处 |
|---|---|---|---|---|
| Letta V1 单次 step | `max_steps` | 50 | **是**，硬覆盖模型的 heartbeat | `letta/constants.py:75`；`letta/agents/letta_agent.py:1907-1910` |
| Letta V1 core memory | 字符上限 | block 默认 100,000（`CORE_MEMORY_BLOCK_CHAR_LIMIT`）；另有 persona/human 常量各 20,000，但 archive 分支内未见调用 | **否**，只渲染 `chars_current/chars_limit`，`update_block_value` 不校验 | `letta/constants.py:433-435`；`letta/schemas/block.py:20`；`letta/schemas/memory.py:154-165`、`:771-780` |
| Letta Code memfs | 字符上限 | 单文件 20,000；核心记忆 65,536；深度 2 | **是**，git pre-commit 硬失败 | `letta-code/src/memory-constraints.ts:325-330`；`letta-code/src/memory-frontmatter.ts:58-104` |
| Letta Code 反思 | 触发间隔（step-count） | 每 25 步 | 是（配置项） | `letta-code/src/settings-manager.ts:188` |
| AutoGPT classic | cycle 预算 | `math.inf` | **没有上限** | `autogpt/classic/original_autogpt/autogpt/app/main.py:594-600` |
| AutoGPT Platform | 连续相同失败 | 3 次 | 是（但是提示级） | `autogpt/autogpt_platform/backend/backend/copilot/sdk/tool_adapter.py:139-146`、`:393-416` |
| 我们 | `maxSteps=20 / maxWallMs=10min / maxLlmCalls=4` | — | **必须由 arbiter 代码拒绝** | `docs/adr/ADR-011-目标栈与决策节拍.md:62` |

**关键教训**：Letta V1 的字符预算只是「显示」，不是「拒绝」；Letta Code 则改成 commit 时硬失败。我们的预算也必须走后者：`used.steps >= budget.max_steps` 时 arbiter 直接 `failed`，不能只在 prompt 里写「你还有 3 步」。

**活动门**：Letta 没有可抄对象（它没有桌面上下文）。我们已有 `world-store` 五态机：`away`（idle ≥ 300s，`_incoming/my-neuro/live-2d/js/core/world-store.js:50`、`:111`）、`gaming`（`:112`）、`watching`（`:114`）。规则照 ADR-011:83/98：自主 goal 在安全点 `paused`；用户显式发起的 goal 继续但表达层静音。

**熔断**：AutoGPT Platform 的做法是 key = `(tool_name, args_fingerprint)`（`autogpt/autogpt_platform/backend/backend/copilot/sdk/tool_adapter.py:403-404`），连续 3 次相同失败后返回一段 `STOP: ... Do NOT retry` 文本（`:405-416`），成功时清掉该 tool 的所有 args 计数（`:431-443`）。**可抄阈值与 key，不可抄「只发文本」**：它只是劝模型，模型可以不理。我们的第 3 次相同 `(action, target, pre_state_hash)` 必须由 dispatch 层直接拒绝派发，再升级到 `ask_user`。另外 `_incoming/my-neuro/live-2d/plugins/community/dispatch/verify-contract.js:18` 的 `suspected_noop` 已经是「前后状态一致」的信号，熔断应消费它，而不是只看 `ok:false`。

### Q5 自编辑 vs 外置计划

| 维度 | Letta memory block 自编辑 | 我们的计划差分注入 |
|---|---|---|
| 载体 | system prompt 里的 block | 最后一条 user 的易变尾巴 |
| 生效时机 | **下一次 recompile**（`letta-code/src/agent/prompts/letta_root_memfs.md:58`） | 当轮立即 |
| 每次编辑的 token | 工具**返回整块新值**（`letta/functions/function_sets/base.py:388`、`:450`），不是只返回 diff | ≤80 tokens，只拼变化的行（ADR-006:44、:111） |
| 额外开销 | 至少 1 次工具调用 + 工具结果回灌（还要模型生成 old/new 字符串） | 0 次（宿主直接注入） |
| 前缀缓存 | 改的是 system prompt → 前缀变 | 前缀一字不动（ADR-006:111） |
| 可审计 | 依赖 git/snapshot 纪律；Letta Code 用 commit 记录（`letta-code/src/agent/memory-git.ts:1230`） | 宿主同时写 goals.json + ledger，天然可回放 |
| 结构 | 自由文本，无 typed status | 每行有 id/status/verify，可 CAS |
| 适用时间尺度 | 人格、偏好、教训（周/月） | 当前计划（秒/分钟） |

**结论**：自编辑不是「更省 token 的 diff」——它的工具调用返回整块，且改 system prompt；它适合**长期自我**，不适合**当前计划**。两者不是二选一：

- 计划状态走外置差分（ADR-006），因为要当轮生效、要 typed、要可审计。
- 任务结束后的教训/技能沉淀走自编辑式写入（ADR-012），因为那是给未来的自己。

**一个值得抄的细节**：`memory_replace` 要求 `old_string` 在 block 中**唯一匹配**，0 次或多次都报错（`letta/functions/function_sets/base.py:359-373`）。把这套「前置条件不满足就拒绝」搬到计划 diff：每条 diff 带 `line_id + expected_status + expected_rev`，不匹配就丢弃并重读，防止 LLM 基于过期计划改状态。反面教材是 `memory_rethink` 整块重写（`letta/functions/function_sets/base.py:488-509`），计划绝不能用这种模式。

### Q6 为什么明确否掉 AutoGPT / BabyAGI

**AutoGPT Classic（不是凭印象，是源码）**：

1. 官方退役：`autogpt/classic/README.md:7`「This project is unsupported, and dependencies will not be updated.」
2. 预算是无限的：`_get_cycle_budget()` 在没有 `continuous_limit` 时返回 `math.inf`（`autogpt/classic/original_autogpt/autogpt/app/main.py:594-600`），主循环 `while cycles_remaining > 0`（`:683`）。
3. 终止由模型决定：唯一的正常结束是模型调用 finish（`AgentFinished`）；交互模式下还会问用户「继续吗」，并把 cycle 预算**重置**（`main.py:775-778`）。
4. 有一步不消耗预算：模型返回 `use_tool=false` 时直接 `continue`（`main.py:732-733`），不递减 `cycles_remaining`——可以在不推进任务的情况下空转。
5. 失败计数只统计「thoughts 解析失败」，不统计动作失败：`consecutive_failures >= 3` 才终止（`main.py:696-710`），且每次成功提出 action 就清零（`:711`）。
6. 具体故障有 issue 佐证：`Significant-Gravitas/AutoGPT#1994`「Gets stuck in a loop」（2023-04-16 创建，closed），复现步骤是「持续接受下一步」，现象是「虽然 Google 已返回结果，仍重复同样的查询」。经 `gh api` 读取原文核对。

**BabyAGI（原版，babyagi_archive）**：

1. 当前仓已不是原版：`babyagi/README.md:4` 明说「This project has been archived and moved to the babyagi_archive repo (September 2024 snapshot)」。
2. README 自己承认无限循环：`babyagi_archive/README.md:44`「running an infinite loop」；`:100-102` 警告「Running this script continuously can result in high API usage」。
3. 循环只有一个出口：`babyagi_archive/babyagi.py:548-605`，`while loop:`（`:550`）在任务队列为空时 `print('Done.'); loop = False`（`:603-605`）。
4. 但每轮都会追加新任务：`task_creation_agent` 生成 `new_tasks`（`:583-588`），然后逐条 `tasks_storage.append`（`:594`）；`prioritization_agent` 的 prompt 要求「Do not remove any tasks」（`:460-470`）。任务生成只追加，列表能否排空取决于模型某次生成空列表（每轮只 `popleft()` 一个）。
5. 没有预算、没有 oracle、没有去重、没有安全点；每轮 `time.sleep(5)`（`:602`），每次 sleep 后都是一次 LLM 执行 + 一次任务生成 + 一次重排。
6. 目标漂移是结构性的：新任务由「上一个任务的结果 + objective 字符串」生成（`:420-430`），没有外部 `done_when` 锚点，误差会逐轮复合。

**否掉的不是「它们旧」，而是三个具体机制**：终止条件由模型给、预算没有代码真值、任务生成没有外部判据。这三条正好是 ADR-011 的五条准入闸要解决的。

## 6. 未解问题 / 需实测的假设

1. **30s 与事件触发的真实收益**：假设活动态变化事件能把「开游戏 → 暂停」的延迟从 ≤30s 降到「下一个安全点」（通常 <1s）。需在真机跑 2 小时「有 goal + 中途开游戏」的场景，记录暂停延迟与误暂停次数。
2. **30s tick 的前缀缓存影响**：假设 tick 不改 plan 时不注入任何文本，前缀命中率仍 ≥90%。需用 100 轮「计划不变」的会话实测 cache hit；若 arbiter 每 tick 都写 `last_decision_at` 进 prompt，就会破坏缓存——这一点必须在实现时禁止。
3. **预算口径**：`maxLlmCalls=4` 到底数哪些调用？建议只数「规划 + 重规划 + 结果汇报」，不数每步 ReAct 的工具循环（那由 `maxSteps=20` 约束）。需在 3 个长任务上核对计数是否与实际账单一致。
4. **重启后的「前提消失」检测**：`active → paused` 后重新观测，能否用 T3 getter 识别「文件被删/窗口已关/应用已更新」？需 20 个故障注入用例，统计漏判与误判。
5. **intent_key 的合并质量**：40 字符去标点归一化可能把「打开 PCL」和「打开 PCL 启动器」合并，也可能把「打开 B 站」和「打开 B 站下载页」拆开。需 50 条真实用户语句标注，测 false merge / false split。
6. **ledger 体积**：30s × 数小时 = 120 行/小时；若每行 200B，一天约 0.6MB。需定保留策略（建议 7 天滚动 + 状态迁移永久）。
7. **commitment 与用户对话的公平性**：用户连续聊天时，active goal 会一直 paused；是否需要「空闲 10 分钟且无新用户消息 → 在安全点恢复」的规则？这是产品决策，需用户拍板。
8. **依赖关系**：`blocked_by` 在 1 active + 3 queued 下是否需要？若需要，A 完成后 B 自动激活的判定应放在 arbiter 还是 goal-store？建议放 arbiter，goal-store 只存字段。
9. **时钟**：`maxWallMs` 必须用单调时钟（`performance.now()` / `process.hrtime.bigint()`），不能用 `Date.now()`（系统时间调整会让预算瞬间超支或永不到期）；`created_at` 等展示字段才用墙钟。
10. **cetana 的可信度**：它是 0 star、单作者的参考实现，设计干净但未经过生产验证。我们只抄结构（cursor/reconsider/trace），不抄它的错误处理细节；所有假设要用自己的单测覆盖。
