# 调研：DSH CLI 能力面 vs 大肥鱼现有接入（2026-11-20）

> 目的：回答「现在接了 DSH 的 CLI，但能不能像人一样使用 —— 目标、计划模式、审批、创建工作区、
> 发起新对话、装插件开关等等」。
>
> **方法与边界**：只读。只跑了 `--version` / `--help` / `--dump-config` 这类不执行任务的命令；
> 从安装包 `app.asar` 解出源码与各包 README 作为一手证据；不装依赖、不改配置、不派真任务。
> 每条结论都标了真实文件行号或命令输出。凡属「读源码推断、尚未实跑」的，单独标 **【待实测】**。

## 3. 用户点名六项的逐项结论

### 3.1 目标（goals / 长期任务）

**有，但只能模型自己发起；CLI 没有「设目标」参数。**

- 领域：`dsh-goal`（状态机，持久化在 session log，默认轮上限 256：`dsh-goal/README.md:12,46`）。
- 驱动：`dsh-goal-round-driver` —— agent 空闲且 goal 处于 armed 时**自动续轮**（`dsh-goal-round-driver/README.md:12`）。
- 工具：`get_goal()` / `create_goal(objective, max_goal_rounds?)` / `update_goal(...)`（`dsh-tool-goal/README.md:34-38`）。
- 人的入口：`/goal` 命令（`dsh-command-goal/README.md:12`）——**仅交互命令面**；headless 没有命令面。
- 权限约束：`create/edit/pause/resume` 必须在「runtime-root agent 的当前轮里有 direct human message」（`dsh-tool-goal/README.md:52`）。headless 的任务正是 `source:{kind:"user"}`（`headless-index.js:361-367`），所以**具备资格**，但没有任何东西促使它去建。

**结论**：能力在，入口缺。要「像人一样定目标」，只能在提示词里约定 + 回执里透出 goal 状态；
真正的程序化 `/goal` 只有 SDK profile 有（`dsh-sdk-jsonrpc-server/README.md:40`）。

**风险**：一旦模型建了 goal，`goal-round-driver` 会在同一次进程里续到完成或 256 轮
（`dsh-goal-round-driver/README.md:12`），而我们的超时只杀 wrapper（`vts-server.mjs:172`）——见 §5。

### 3.2 计划模式（plan mode）

**有；但 headless 不可达。**

- 包：`dsh-plan-mode`，headless 组合里**已挂载**（`headless-default.yml:218-219`，提示词在 `:220-265`）。
- 进入：`/plan` / `/plan <message>`（`dsh-plan-mode/README.md:55`）。
- 退出：模型调 `exit_plan_mode` → 人工审阅 Approve / Keep planning（`README.md:61-63`）。
- 关键限制：`/plan` 属于**命令面**，需要 `dsh-commands` 适配器；headless 明确「无命令面」
  （`dsh-commands/README.md:28`），任务文本直接进 agent（`headless-index.js:361`）。
- 无交互审阅时 `exit_plan_mode` fail-closed（`plan-mode/README.md:93`）；headless 也没有 `ask_user`
  通道（C12），所以就算进了也退不出来。

**结论**：不要把 plan mode 硬塞进 headless（只能改源码/patch，收益低）。
程序化 `/plan` 只有 SDK（`dsh-sdk-jsonrpc-server/README.md:40`）；人肉用就在桌面端/Web。

### 3.3 审批（approval / permission / yolo）

**有，四层：**

1. **策略**：`ask`（默认）| `never`（`dsh-user-approval/README.md:12,45-47`）。
   headless 没有 answerer，`ask` 会 `unavailable` → fail-closed。
2. **预置**：出厂 `read-only` / `workspace-write` / `danger-full-access` 三档，一键同时设 sandbox+approval
   （`headless-default.yml:165-176`；`dsh-permission-presets/README.md:31-45`）。
   但补丁语义是**整块替换**（`dsh-app-boot/README.md:208`），我们的 `permission` 行只剩
   `defaultPreset`（`headless-composed.yml:331-334`），预置表回落到 schema 默认的两档
   （`permission-presets/lib/index.js:140-157`）—— **`read-only` 大概率已不可选**【待实测】。
3. **入口**：`--permission-mode`、`--approval-policy`（`dsh-headless/lib/startup.js:37`）、
   环境变量 `DSH_PERMISSION_MODE`（`headless-composed.yml:307-312,324-329`）、
   `/permission <preset>`（命令面）、SDK `approval/request`、ACP `session/request_permission`。
4. **实际生效值**：用户补丁把 `defaultPreset` 设成 `danger-full-access`
   （`~/.dsh/profiles/headless/cordis.patch.yml:172-175`），源码在 `agent/created` 时把
   sandbox+approval 一起写入该预置（`permission-presets/lib/index.js:192-195,376-394`）。

**结论**：**我们当前其实是「无沙箱 + 不审批」（yolo）**，只是没人显式声明。
【待实测】需跑一次任务读 `session` 里 `permission/preset` 事件确认。
建议：每次派活显式传 `--permission-mode` + `--approval-policy never`，别靠 profile 兜底。

### 3.4 创建工作区

**CLI 的「工作区」= 进程 cwd；GUI 才有 workspace 实体。**

- GUI/桌面：`dsh-workspace` 注册表 + `dsh-api-workspace-controller`（create/rename/remove/reorder/
  archive/follow），`web-patch.yml:87,151`；`dsh-workspace/README.md:12,51-58`；`dsh-api-workspace-controller/README.md:12,25`。
- CLI：调用目录即 workspace 根（`dsh/README.md`「Entry modes」段末）；`--add-dir` 追加可写根
  （`startup.js:37`、`dsh-headless/README.md:88`）；模型可 `working_directory({cd:"src"})`
  （`dsh-tool-working-directory/README.md:22`）。
- ACP：`session/new` 带**绝对 cwd** 建会话（`dsh-acp/README.md:66`）。
- SDK：`session/working-directory/set`（`dsh-sdk-protocol/README.md:52`）。

**我们**：HTTP → CLI 全链路其实支持 cwd（`index.js:970`、`vts-server.mjs:162,170`、
`dsh-dispatch.mjs:12,58`），但 `dispatch_to_dsh` 的 schema 只有 `task`/`wait`
（`index.js:275-286`），所以模型永远传不进来 —— **半接，差一个字段**。

### 3.5 发起新对话

**有，而且我们已经在用；缺的是「续聊」。**

- 新会话：每次 headless 运行默认 `session-<uuid>`（`dsh-headless/README.md:47`）。
- 续聊：`--session-id <id>`，要求同 cwd、同 preset、非子代理会话
  （`dsh-headless/README.md:75,189`）。
- 协议面：ACP `session/new|list|resume|close`；SDK `session/prompt|resume|query|wait`。
- 存储：`~/.dsh/sessions/<cwd 编码>/<sessionId>/session.v4.jsonl.zstd`
  （实测：`<project-root>` 下 19 个会话，共 40 MB；单个 167,923 字节）。

**我们**：每次派活=新会话（已接）；`sessionId` 在 `vts-server.mjs:184` 的返回体里有，
但 `dispatch/index.js:1072-1078` 只取 `text/error/tookMs`，**把它丢了** → 无法续聊、无法审计。

### 3.6 装插件 / 开关

**装：有 CLI。开关：CLI 没有，只能改 YAML 或用工具/UI。**

- 装/删/查：`dsh plugin --profile <p> add|remove|why <pkg>`（转发 pnpm；`bin.js:115-126`）。
- 版本豁免：`dsh plugin ... version-exemptions|allow-version|revoke-version`
  （`dsh-plugin-manager/README.md:83`）。
- 开关：`plugin_manager` 服务/工具（toggle `disabled`、bundle 选择、install/remove）；
  **base 里 `tool-plugin-manager` 默认 `disabled: true`**（`base-patch.yml:16-18`），
  SDK profile 才 `disabled: false`（`sdk-patch.yml:26`）；headless 没开 → **headless 里的 agent 不能管插件**。
- 技能：不是「装」，是放文件。`<project>/.dsh/skills`、`~/.dsh/skills` 等
  （`dsh-skill-filesystem/README.md:45-52`）。

**我们**：完全没接。真要做，路径是「用户在设置里点一下 → 我们跑 `dsh plugin --profile headless add ...`
→ 跑 `--dump-config` 验证 → 重启进程」。**不要**让模型自主装（见 §5）。

### 3.7 其他在 CLI 里发现、用户没点名但值得知道的

- **子代理 + 工作流**：headless 里有 `subagent` / `subagent_fork` / `workflow`（可后台跑），
  这是「一个人干不完就分头干」的能力，已间接可用。
- **后台作业**：`job_output/list/kill`，长命令不阻塞。
- **技能热发现**：技能目录被 watch，新增文件下一轮就能用，不用重启。
- **`--json` 是投影不是日志**：`status`（turn/step + usage）、`text`、`thinking`、`tool_call`、
  `tool_result`、`session`、`final`；除 `final` 外每串截到 8 KiB，单行 32 KiB
  （`dsh-headless/README.md:102`；事件构造在 `json-stream-Dc3g2Bl1.js:180-281`）。
  **我们现在只用了 `session`/`final`/部分 `status`/工具名**，其余全丢。
- **执行器有 native 与 PTC 两种**（`tool-executor-native` / `tool-executor-ptc`，后者 headless 默认关，
  `headless-default.yml:360-364`）。
- **上下文压缩是自动的**（compaction-basic + pruner + spill），不需要我们管。

## 4. 「像人一样使用」的判据

「像人」不是功能清单堆满，而是**四件事**：知道在哪干活、能问能答、干到一半能改主意、干完能复盘。

### 4.1 最小集（不接就不算「像人」，5 条）

| # | 能力 | 判据（可观测） | 改动量 |
|---|---|---|---|
| **M1** | **任务台账带 cwd + sessionId** | `dispatch_to_dsh({task, cwd})` 的返回 JSON 里有 `sessionId`；`check_dispatch(id)` 能查到同一 id 的 `sessionId`；下一轮传 `session` 能续上（模型能说出上一轮产物名） | schema +2 字段（`index.js:275-286`）；`row` 存 `sessionId`（`index.js:1029`、`:1072-1078`） |
| **M2** | **权限显式化** | 只读任务里模型尝试写文件 → `tool_result.status="error"` 且含 sandbox 拒绝；不出现任务卡死等审批 | `dsh-dispatch.mjs:53-55` 加 `--permission-mode`/`--approval-policy`（当前可选最窄的是 `workspace-write`） |
| **M3** | **可观测** | `check_dispatch` 返回 `tools:[...]`、`turns`、`usage.totalTokens`、`durationMs`；失败时 `reason.kind` 原样透出（不再被压成一句「没办成」） | 解析 `json-stream-Dc3g2Bl1.js` 的 `status.step_end.usage`、`tool_call.tool`、`final.reason`（`:215-257`） |
| **M4** | **超时真杀干净** | 900s 超时后 `state=failed`，且 `Get-Process` 里没有残留 `DeepSeek Harness`/`dsh` 子进程；不会出现「已超时但文件还在被写」 | `vts-server.mjs:170-172` 改 `taskkill /T` 或 `detached`+`process.kill(-pid)`；`dsh-dispatch.mjs` 里给 dsh 子进程加 kill 树 |
| **M5** | **任务文本不走 shell 拼接** | 任务里含 `&`、`\|`、`"`、`>` 时行为不变、不执行额外命令 | `dsh-dispatch.mjs:58` 的 `shell:true` 去掉，改用 `shell:false` + 完整路径 `dsh.cmd`；或改走 stdin（`-`，`README.md:36`） |

> M5 是**现存缺陷**，不只是「加分」：`spawn('dsh', args, {shell:true})` 在 Windows 上会把
> 整个命令行交给 cmd.exe 重新解析（Node 官方明确要求 shell 模式不得传未转义输入）。
> 任务文本来自模型、模型又读外部内容 —— 这是一条从「网页里一句话」到「本机任意命令」的路径。

### 4.2 加分集（像人之外还像「靠谱同事」，6 条）

| # | 能力 | 判据 | 代价 |
|---|---|---|---|
| S1 | 长期目标 | 长任务里 `tool_call` 出现 `create_goal`，收尾出现 `update_goal(complete)`；`check_dispatch` 显示 `goal.phase` | 低（提示词 + 解析）；注意轮上限 |
| S2 | 多轮续聊 | 同一 session 第二次派活能引用第一次的文件；台账里 `sessionId` 复用率 > 0 | 低（M1 之后几乎免费） |
| S3 | 子代理/并行 | `tool_call` 出现 `subagent`，`check_dispatch` 统计 `subagents:N` | 低（解析） |
| S4 | 技能库 | 模型 `skill` 调用命中 `<project>/.dsh/skills/<name>`；同一套路第二次不再重新探索 | 中（要写技能） |
| S5 | 可审批（真 ask） | 敏感操作弹出审批 → 用户点「允许一次」→ 继续；拒绝则 `outcome=rejected` | 高（要常驻 SDK/ACP 客户端，见 D3） |
| S6 | 插件开关 | `dsh plugin add` 后 `--dump-config` 出现新行；`plugin_manager` 不可用时给出明确提示 | 中（运维动作 + 人工确认） |

### 4.3 一句话结论

- **「派活」这一层已经很接近了**：headless 有 shell/文件/搜索/子代理/工作流/技能/联网，
  模型能独立干完一件事。
- **「像人」差的不是智力，是三个接口**：`cwd`（在哪干）、`sessionId`（跟谁聊）、
  `permission-mode`（能干到什么程度）。这三样 DSH 全都有，我们一个都没传。
- **「审批 + 计划模式 + 目标命令」这三样 headless 天生没有**，要就要换 SDK profile；
  不要就别在 headless 上硬做。

## 5. 明确否掉 / 不建议接的

| 不建议 | 理由（证据） |
|---|---|
| **让模型自主装/删插件** | 插件是 Host 进程内代码，装完立刻在沙箱外执行（`dsh-plugin-manager/README.md:31`）；且每次操作需 full-access 或审批（同段）。等于让模型改自己的运行时。 |
| **在 headless 里开 goal 自动轮** | `goal-round-driver` 会续到 256 轮（`dsh-goal/README.md:12`），而我们的超时只杀 node wrapper（`vts-server.mjs:172`）→ 孤儿进程 + 持续烧 token。 |
| **依赖 DSH 内部 Remote API（Typert/Web 控制器）** | README 明说它是 Host controller +「generated Client `ctx.remote.workspace` namespace」成对生成（`dsh-api-workspace-controller/README.md:12`），无稳定公开契约，随版本变。 |
| **每次任务都用 `danger-full-access`** | 现在事实上就是（§3.3）。模型读到的任何外部文本都可能变成写盘/执行指令；`apply_patch` 虽默认关，`write`/`pwsh` 是全开的。 |
| **让模型自己选 `permission-mode`** | 权限是「人给的授权」，不是「agent 的偏好」；模型选必然选最宽。由我们按任务类型定。 |
| **用 `shell:true` 传任务文本** | 见 M5。 |
| **在 headless 上实现 plan mode** | 没有命令面、没有审批通道（`plan-mode/README.md:93`、`dsh-commands/README.md:28`），只能改源码/patch，收益远低于直接用桌面端或 SDK。 |
| **自建第二套定时任务** | headless 里没有 `dsh-schedule`；项目已有「主动性四路」；再接一套只会打架。 |
| **把 desktop profile 拉到 CLI 跑** | 被硬拒（`bin.js:35-37`）；桌面端那棵树由 Electron 管。 |

## 6. 未解问题（需实测）

1. **派活链路现在到底通不通？** `vts-server.mjs:170` 用 `process.execPath`（Electron）
   直接 `spawn` `dsh-dispatch.mjs`，**没有** `ELECTRON_RUN_AS_NODE=1`；
   同项目其他 spawn 都显式设了（`main.js:1137,1200`）。
   旁证：`pet-runtime/data/dispatch-history.jsonl` 里 `"action":"dispatch"` 计数为 **0**。
   → 需实跑一次 `dispatch_to_dsh({task:"echo hi"})` 看是否真的产出 DSH 回复。
2. **当前生效权限到底是 full-access 还是 workspace-write？**
   组合配置写 `workspace-write`（`headless-composed.yml:307-312`），用户补丁写
   `defaultPreset: danger-full-access`（`cordis.patch.yml:172-175`），源码在 `agent/created`
   时按预置覆盖两者（`perm.js:192-195,376-394`）。→ 跑一次任务，在 session 日志里找
   `permission/preset` 事件。
3. **`--session-id` 续聊在跨进程/跨 cwd 下的实际拒收边界**（`README.md:75,189` 列了 5 种拒收）。
   → 同一 cwd 连跑两次，第二次带第一次的 sessionId。
4. **打包成安装器后 `dsh` 是否在 PATH 里**。开发机 PATH 里有
   `...\DeepSeek Harness\resources\runtime\cli\bin`（`which dsh` 实测），
   Explorer 启动的 Electron 继承的环境可能不同。→ 改用绝对路径更稳。
5. **单次派活的 token 成本**。`--json` 的 `status.step_end` 带 `usage`
   （`json-stream-Dc3g2Bl1.js:215-227`），我们没解析；→ 解析一次即可得到基线。
6. **`--add-dir` 在 Windows ACL 沙箱下的限制**（`dsh-headless/README.md:184`：额外根会拒子进程调用）。
   若保持 full-access 则无关；若要收窄到 workspace-write 就必须实测。
7. **headless 与桌面端会话是否真的隔离**：README 说 preset/cwd 不匹配即拒
   （`README.md:75`），但没实测过两边同名会话。→ 低优先。
8. **`--permission-mode read-only` 现在还能不能用**：补丁整块替换了 `presets`
   （`app-boot/README.md:208`、`headless-composed.yml:331-334`），schema 默认表只有两档
   （`perm.js:140-157`）。→ 跑一次 `--permission-mode read-only` 看是否报 unknown preset；
   若报错，需要把三档表写回 `cordis.patch.yml`。
