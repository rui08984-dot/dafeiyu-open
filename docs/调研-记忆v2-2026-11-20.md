## 2. 六个必答问题

### 2.1 重要性累加触发反思的精确机制

**公式（照源码，不照论文印象）：**

```
每感知到一个新 event:
    event_poignancy = LLM 打分 1..10（idle 事件直接 1）
    importance_trigger_curr -= event_poignancy
    importance_ele_n += 1

每一步模拟:
    if importance_trigger_curr <= 0 and (seq_event + seq_thought 非空):
        run_reflect()
        importance_trigger_curr = importance_trigger_max
        importance_ele_n = 0
```

- **打分尺度 1..10**：`generative_agents/reverie/backend_server/persona/prompt_template/v3_ChatGPT/poignancy_event_v1.txt:12`（1 = 刷牙铺床，10 = 分手/录取）；代码侧强制输出一个 1..10 整数：`.../persona/prompt_template/run_gpt_prompt.py:1889`。
- **idle 不花 LLM**：描述含 `"is idle"` 直接返回 1：`.../cognitive_modules/reflect.py:76-77`。
- **只有 event 累加，chat 不累加**：chat 的 poignancy 算了也存了（`.../cognitive_modules/perceive.py:165-171`），但累减用的是 `event_poignancy`（`perceive.py:178`），`importance_ele_n` 也只在新 event 上 +1（`perceive.py:179`）。这是读源码才能看到的细节。
- **阈值 150**：`.../memory_structures/scratch.py:61`（`importance_trigger_max = 150`）；初始 `curr = max`（`scratch.py:62`）。按 1..10 分，约 15–30 个事件触发一次。
- **检查频率**：每个模拟步都检查，不是定时器。`persona.py:219-223` 的主序列是 perceive → retrieve → plan → `self.reflect()`；触发判断在 `reflect.py:152-153`。
- **触发后产出**：
  1. `generate_focal_points(persona, 3)` 生成 3 个焦点（`reflect.py:110`），输入是「最近 `importance_ele_n` 个 event+thought」的 `embedding_key`（`reflect.py:24-33`）；
  2. 每个焦点 `new_retrieve` 默认取 30 个节点（`retrieve.py:199`）；
  3. 每个焦点生成 5 条 insight（`reflect.py:121`），所以单次反思最多 3×5=15 条 thought；
  4. 每条 thought 写入 `add_thought`，带 30 天 `expiration`、SPO、关键词、poignancy、embedding、证据节点 id（`reflect.py:122-132`）。
- **重置**：`curr = max`、`ele_n = 0`（`reflect.py:167-169`）。

**三个必须知道的坑：**

1. **`nodes[-1*importance_ele_n:]` 在 `ele_n=0` 时等于全量**（`reflect.py:32`）。Python 的 `[-0:]` 是 `[0:]`，不是空列表。正常触发时 `ele_n>0`，但配置成 0 或异常路径会退化成「对全部记忆做焦点」，不要照抄这个写法。
2. **`concept_forget=100`、`daily_reflection_time=60*3`、`daily_reflection_size=5`、`overlap_reflect_th`、`kw_strg_*_reflect_th` 全是死配置**：`scratch.py:49-54` 定义后，全 `persona/` 目录 grep 不到任何使用点。`thought_count=5`（`scratch.py:64`）也是死配置，真正的 5 硬编码在 `reflect.py:121`。
3. **GA 没有「每天最多几次」**。只要有事件把累加器打到 0 就反思；它没有时钟闸、日配额、间隔闸。我们 ADR-010 的「每天 ≤4 次、间隔 ≥1h」是产品校准，不是 GA 常量。

**对我们的用法：** ADR-010 的 `acc ≥ 60`（`docs/adr/ADR-010-记忆v2反思与巩固.md:27-29`）是合理的保守值，但必须标成「我们的校准值」，不能写成「GA 阈值」。按 1..10 分，60 约等于 6–15 条高信息量事件，比 GA 的 150 更容易触发；上线前用实测触发次数校准（见 §6）。

### 2.2 反思产出的存储形态

**GA 的节点结构**（`generative_agents/reverie/backend_server/persona/memory_structures/associative_memory.py:19-43`）：

```
ConceptNode:
  node_id, node_count, type_count, node_type(thought/event/chat), depth
  created, expiration, last_accessed
  subject, predicate, object
  description, embedding_key, poignancy, keywords, filling
```

**thought 与原始记忆的引用关系：**

- `type="thought"`，`depth=1`；如果 `filling`（证据节点 id 列表）非空，`depth += max(证据节点的 depth)`（`associative_memory.py:205-212`）。这就是「thoughts tree」：不是显式树对象，而是 `depth` + `filling` 两个字段表达的 DAG。
- 证据来自 LLM 输出的编号：`insight (because of 1, 5, 3)`（`prompt_template/v3_ChatGPT/insight_and_evidence_v1.txt:11`），cleanup 把编号解析成列表（`run_gpt_prompt.py:2147-2156`），`generate_insights_and_evidence` 再把编号映射成真实 `node_id`（`reflect.py:50-52`）。
- `filling` 是证据 id 列表，但没有反向 children 索引，也没有 parent 指针；要遍历「这条结论基于哪些结论」只能顺 `filling` 走。
- `expiration` 写 30 天（`reflect.py:124`），但**没有任何代码读它做过期判断**。全仓只在构造、保存、加载时出现（`associative_memory.py:32,125-127`），没有任何 `expiration < now` 的比较。不要把它当 TTL。

**映射成 `insights.jsonl` 一行（建议 schema）：**

```json
{
  "id": "ins_20261120_0001",
  "created_at": 1763000000000,
  "text": "他这周作息很乱，连续三天凌晨还在打游戏",
  "evidence_ids": ["f_abc123", "ep_0007", "msg_01142"],
  "depth": 1,
  "importance": 7,
  "keywords": ["作息", "打游戏", "凌晨"],
  "focal_point": "他最近的作息",
  "confidence": 0.62,
  "occurrences": 1,
  "status": "active",
  "superseded_by": null,
  "model": "local-xxx",
  "prompt_version": "reflect-v1"
}
```

字段对应：`description`→`text`，`filling`→`evidence_ids`，`poignancy`→`importance`，`depth` 保留，`keywords` 保留，`expiration` 不要抄（改用 `status`/`stale_at`）。

**我们当前的硬缺口：证据 id 不存在。** 对话历史只有 `role/content`，没有消息 id（`_incoming/my-neuro/live-2d/plugins/community/memory-recall/index.js:79` 的注释明确说「jsonl 现在没有时间戳，靠文件顺序当时间」）。`episodes.jsonl` 的卡片也没有 id（`js/core/episode-store.js:113-120` 的 `parseCard` 只产出 `at/title/summary/facts/turns/span`）。`user-facts.addFact` 的 schema 也没有 `evidence_ids`（`js/core/user-facts.js:159-167`）。所以「反思必须带 ≥2 个 evidence_ids」这条 ADR 决策，**今天没有可指向的稳定 id**，必须先把 evidence 坐标系定下来（建议：`对话历史.jsonl` 行号 + episode 序号 + fact id，三者都写进 insight）。

### 2.3 巩固判据：情景记忆 → 语义记忆，「可以忘」的条件

这一题要分四个来源看，因为它们的答案完全不同。

#### (a) Generative Agents：没有巩固，也没有遗忘

- `expiration` 只写不读（见 §2.2）。
- `concept_forget=100` 是死配置（`scratch.py:49`，全目录无引用）。
- 没有把 event 合并成 semantic 的步骤；thought 是追加，不是替换。
- 结论：**GA 只能抄「触发 + 证据链 + 层级」，不能抄「遗忘」**。

#### (b) mem0 HEAD：自动路径已改为「只增不改」

- `add()` 的 infer 路径是 V3 phased batch pipeline（`mem0/mem0/memory/main.py:918-944`）：
  1. 先用当前对话去向量库取 top 10 条已有记忆（`main.py:925-933`）；
  2. 一次 LLM 调用做 additive extraction（`main.py:942-944`，系统提示词 `ADDITIVE_EXTRACTION_PROMPT` 在 `mem0/mem0/configs/prompts.py:468` 起，开头明确「Your sole operation is ADD」）；
  3. 对提取出的文本做 **md5 精确哈希去重**（`main.py:1022-1026`），命中已有 hash 或本批已见 hash 就跳过；
  4. 批量写入，history 记为 `ADD`（`main.py:1079-1091`）。
- 也就是说，**自动 add 路径没有 LLM 判 UPDATE/DELETE/NONE**，只有 ADD + 精确去重。这是 2026-11 的 HEAD 行为，不是老版本。
- 经典的 ADD/UPDATE/DELETE/NONE 提示词仍在仓库里：`mem0/mem0/configs/prompts.py:176-330`（`NONE` 定义在 `:185`，JSON 事件枚举在 `:444-445`）；TS 侧也有同名函数 `mem0/mem0-ts/src/oss/src/prompts/index.ts:105-118`，但当前 `mem0/mem0-ts/src/oss/src/memory/index.ts` 只 import、未见调用，实际 add 用的是 `ADDITIVE_EXTRACTION_PROMPT`（`index.ts:912`）。Python 全仓 grep `DEFAULT_UPDATE_MEMORY_PROMPT` / `get_update_memory_messages`，除 `prompts.py` 自身和 tests 外没有调用点。
- 显式 `update(memory_id, text)` / `delete(memory_id)` API 仍在（`main.py:1829-1881`、`main.py:1883`），但那是调用方主动调用，不是自动巩固。
- **TTL**：`add(..., expiration_date=...)` 可带日期（`main.py:769`，文档 `main.py:788-789`），存储为 `metadata["expiration_date"]`（`main.py:820-829`）；`_payload_is_expired` 用 `date < today` 判断（`main.py:442-449`），搜索默认隐藏过期项（`show_expired=False`，`main.py:1403`）。
- **没有本地衰减**：OSS 的 `project.update(decay=True)` 直接抛错（`main.py:467-471`），decay 是付费/云功能。
- 搜索默认值：`top_k=20`、`threshold=0.1`（`main.py:1393-1399`）。

判据（`core/evolution.py`）：

最后一次运行（`data/evolution_state.json`，2026-11-19T21:38:54）：

解读：**衰减每天在跑（最近一次 170/184），但合并和归档在最近一次运行里是 0**（`evolution_state.json` 只存最近一次计数，是否历史上从未触发需查滚动日志——审计 S-25）。0.95 的合并阈值对短中文记忆很可能永远够不到；60 天 + importance<0.2 的归档条件也太苛刻。这两条是「有代码但没效果」的典型，不能当作已验证的巩固策略。

#### (d) 我们本地层的现有闸门

- 事实 supersede（不是 TTL）：纯规则只处理「几乎一字不差」——bigram Jaccard ≥0.75，或公共前缀 ≥6 且覆盖长串 70%，或短串 bigram 全包含（`js/core/user-facts.js:97-117`）；其余交给一次小 LLM 裁决 UPDATE/ADD（`memory-recall/index.js:696-717`）；被取代的写 `valid_to=now`、`superseded_by`，不删除（`user-facts.js:144-170`）。裁决失败/离线时保守不压（`user-facts.js:20`）。
- 只索引当前有效事实：`activeFacts()` 才进召回（`memory-recall/index.js:239-247`）。
- episode → fact 的保守升级：每卡最多 3 条、6–60 字、不像问句、`source:'episode'`、`confidence:0.6`（`memory-evolve/index.js:175-190`）。
- slow 层三重闸：跨天出现 ≥2 次才提议（`persona-layers.js:98-117`）；与 core 冲突拒、每周 ≤5 条、同类去重、每类最多 8 条旧的可挤掉（`persona-layers.js:126-145`）。
- 没有任何「删除用户事实」的路径；ADR-010 也明确只 supersede/mark stale（`docs/adr/ADR-010-记忆v2反思与巩固.md:118`）。

**「可以忘」的分层结论（建议）：**

| 层 | 可以忘吗 | 判据 | 动作 |
|---|---|---|---|
| 原始对话 / 用户事实 | 不删 | 只被新事实 supersede | `valid_to` + `superseded_by`，永不物理删除 |
| 情景卡片 episode | 不删，只降权 | 年龄、是否被后续 episode 覆盖 | 保留原文；召回按 30 天半衰期降权 |
| 反思结论 insight | 可 stale，不删 | 被新 insight supersede、N 天未被引用、证据全部失效 | `status: stale/superseded`，从注入候选中剔除 |
| slow 人格层 | 可挤掉 | 每类 >8 条 | 丢最旧（`persona-layers.js:142-145`） |
| 工作记忆 / open_loop | 可删 | TTL 7 天、已闭环、用户取消 | 物理删除（可从原文重建） |
| MemOS 原始记忆 | 归档不删 | 合并 ≥0.95、60 天无人访问且 importance<0.2 | `archive_memory`（不是 delete） |

**关键判断：不要把「时间到了」当巩固判据。** 现有三个真实系统给出的判据都是「访问次数 + 重要性 + 冲突 + 明确过期」，没有一个是「存放超过 N 天就转成语义记忆」。情景→语义的正确触发是「同一结论跨天/跨 episode 重复出现」，而不是「这条 episode 老了」。这正好复用 `persona-layers.js:114` 的 `days.size >= 2`。

### 2.4 关系时间线：Graphiti 的双时间轴怎么建模

**三层组织：**

| 层 | 类 | 关键字段 | 代码 |
|---|---|---|---|
| Episode（原始输入） | `EpisodicNode` | `content`、`source`、`valid_at`（原文所述时间）、`created_at`（入库时间，继承自 `Node`）、`entity_edges` | `graphiti/graphiti_core/nodes.py:245-259`；`created_at` 在 `nodes.py:103` |
| Entity（实体节点） | `EntityNode` | `name`、`labels`、`created_at`、`summary`、`attributes`、`name_embedding` | `nodes.py:426-431`；`Node` 基类 `nodes.py:99-107` |
| Edge（事实/关系边） | `EntityEdge` | `fact`、`fact_embedding`、`episodes[]`、`expired_at`、`valid_at`、`invalid_at`、`reference_time`、`created_at` | `edges.py:228-253`；基类 `edges.py:48-53` |

**双时间轴的含义：**

- `valid_at` / `invalid_at` = **世界时间**：这条事实在现实中何时成立/不再成立。
- `created_at` / `expired_at` = **系统时间**：这条记录何时入库/何时被系统判定失效。
- `reference_time` = 产生这条边的 episode 的时间戳，用来解析「上周」「昨天」这类相对时间（`edges.py:250-253`；抽取提示词 `prompts/extract_edges.py:182-186`）。

**矛盾消解（只失效，不删除）：**

- 新边的 `valid_at` 晚于旧边时，旧边被盖上 `invalid_at = 新边.valid_at`、`expired_at = now`（`utils/maintenance/edge_operations.py:774-791`）。
- 两条边时间重叠且互相矛盾时，`resolve_edge_contradictions` 用「谁先失效」的区间逻辑决定归档哪条（`edge_operations.py:795-830`，赋值在 `:826`）。
- 查询侧直接按 `valid_at` / `invalid_at` 区间过滤（`search/search_filters.py:62-63`）。
- 未来时态的计划/承诺：`valid_at` 用 episode 的 reference time，不用未来发生日期；软 deadline 不写进 `invalid_at`（`prompts/extract_edges.py:182-186`）。这条直接适用于我们的「他答应周末给我听新曲子」。

```
  "predicate": "猫名",                // 新增，受控词表：叫/住在/工作于/喜欢/讨厌/养/承诺/关系
  "object": "布丁",                   // 新增
  "valid_from": 1761000000000,        // 世界时间：开始成立
  "valid_to": null,                   // 世界时间：不再成立
  "recorded_at": 1761000000000,       // 新增，系统时间：入库时间（旧记录默认=valid_from）
  "expired_at": null,                 // 新增，系统时间：被判定失效的时间
  "supersedes": ["f_old"],
  "superseded_by": null,
  "invalid_reason": null,
  "source": "episode",
  "confidence": 0.6,
  "evidence_ids": ["ep_0007", "msg_01142"],   // 新增，必须可回溯
  "episode_ids": ["ep_0007"]                  // 新增
}
```

理由：

1. Graphiti 的 Episode/Node/Edge 三层，在我们这里分别对应 `episodes.jsonl` 卡片 / `(subject, predicate)` 隐式节点 / 这条 fact 记录；不需要真的建节点表，读取时按 `(subject, predicate)` 分组即可。
2. 现有 `user-facts.js` 已有 `valid_from/valid_to/supersedes/superseded_by`（`user-facts.js:159-170`），只缺 `subject/predicate/object` 和 `recorded_at`；加字段向后兼容，旧记录读出来是 `undefined`，视图层兜底为 `"用户"/null/null`。
3. 「某时刻 T 成立的事实」= `valid_from <= T && (valid_to == null || valid_to > T)`，这就是 Graphiti 的 `valid_at/invalid_at` 过滤，不需要图库。
4. 当前数据佐证：`用户事实.json` 25 条，24 条 `source:"episode"`、1 条 `explicit`，**0 条有 supersedes 历史**。也就是说：关系时间线一旦上线，面对的是「几乎全是 episode 抽出来的 0.6 置信度事实」，先要解决抽取质量和证据链，而不是先做多跳。

**当前数据的一个具体缺陷：** `_promoteEpisodeFacts` 调 `addFact` 时只传 `text/source/confidence`（`memory-evolve/index.js:184`），**没有传 episode id**；`addFact` 也没有 `evidence_ids` 字段（`user-facts.js:159-167`）。所以现在每条 episode 事实都断了来源，做不了「点回原话」。这是关系时间线上线前必须先补的。

### 2.5 双源注入消解：MemOS 原文库 + 事实表

**先纠正一个前提：当前召回路径并没有同时查 MemOS 和事实表。** 现在每轮自动注入只查本地索引，索引源是：

- `对话历史.jsonl`、`AI日记.txt`、`记忆库.txt`、`核心用户记忆.txt`、`用户记忆.json`、`用户事实.json`（只 active）、`episodes.jsonl`（`memory-recall/index.js:219-257`）。
- MemOS 只在两个地方出现：写入（`_postToMemos`，`index.js:483-500`）和「用户说忘掉」时的 `/search` 删除流程（`index.js:548`）。**召回不查 MemOS**。
- 所以「MemOS 原文库 + 事实表双源」是下一轮要新建的能力，不是现有消解逻辑。如果直接把 MemOS 加进召回，必须先设计下面这套，否则会重复注入、分数不可比。

**三套现成公式（真实常量）：**

1. **Generative Agents 三因子**（`retrieve.py:145-150, 170, 194, 232-249`）：
   - `recency = 0.99^i`，`i` 是按 `last_accessed` 升序排序后的序号（不是真实时间差）。**注意方向**：源码把最老的节点放在 `i=1`（权重 0.99），最新的节点拿到 `0.99^N`（更小），与「越新越该靠前」相反，疑似实现 bug。我们不要照抄这个方向，按真实时间差做衰减。
   - `importance = node.poignancy`；
   - `relevance = cos(node_embedding, focal_embedding)`；
   - 三者各自 min-max 归一化到 0..1（`:232-236`）；
   - `master = 1*recency*0.5 + 1*relevance*3 + 1*importance*2`（权重 `scratch.py:57-59` 全 1，硬编码 `gw=[0.5,3,2]` 在 `retrieve.py:244`，求和 `:247-249`）；
   - 取 top 30（`:262`），命中节点的 `last_accessed` 更新为当前时间（`:266-267`）。
   - 注意：`0.99^i` 是**名次衰减**，不是 30 天半衰期；我们的 `0.5^(age/30)` 更接近真实时间，不要混用。

2. **我们本地 recall**（`memory-recall/index.js`）：
   - 词法：`(1 + ln tf) * idf`，单字权重 0.45（`:391-396`）；向量：与词法做 RRF，等权（`:799-827`）。
   - 稳定来源免衰减：`核心/事实/用户记忆`（`:412-418`）；其余 `activity = 0.5^(ageDays/30)`（`:418`）。
   - 长度归一：`score *= 1/(1 + 0.25*ln(1 + len/120))`（`:422-423`）。
   - 来源重要度：`核心 1.0 / 用户记忆 0.9 / 记忆库 0.6 / 日记 0.5 / 对话 0.3`（`:424`）。
   - 强化：`min(1.8, 1 + 0.2*ln(1+hits))`（`:425-428`）。
   - 最终乘子：`(0.9 + 0.5*activity + 0.9*importance) * reinforce`（`:428`）。
   - 去重：按去空白后前 120 字（`:432-441`）。
   - 注入闸：每 token 均分 ≥3.0、≥顶部 50%、或余弦 ≥0.70（`:155-161`、`:874-877`）；最多 3 条（`:161`）。

3. **MemOS 部署版**（`memos_system/core/mos.py`）：
   - `similarity_threshold=0.5`、`top_k=5`（`mos.py:58-64`，配置 `config/memos_config.json:34`）；
   - `final_score = similarity * (1 + importance * 0.3)`（`mos.py:421-434`，importance_weight 0.3 在配置 `:40`）；
   - BM25 权重 0.3、layer_weights、recency_weight 0.1（配置 `:37-47`）。

**建议的消解顺序：**

1. **不要跨源相加原始分数。** BM25、余弦、MemOS 的 `similarity*(1+0.3*importance)` 口径不同，直接相加会让某个源的量纲压倒其他源。先用**每源内部排序**，再做 RRF（我们已有 `fuseRRF`，`memory-recall/index.js:822`）。
2. **给每个源打 stable/volatile 标签。** 事实、episode、核心记忆是 stable，不做时间衰减；MemOS 原文、对话是 volatile，做 30 天半衰期。
3. **冲突不融合，只标记。** 同 `(subject, predicate)` 下，active fact 与 MemOS 原文 object 不一致时：事实优先注入，MemOS 条目标 `conflict` 并从本轮候选剔除；日志留痕。需要裁决时复用 `_adjudicateFact`（`memory-recall/index.js:696-717`），但只在**写入/巩固**时调用，不要每轮查询都调。
4. **按证据去重，不只按文本。** 现有文本前 120 字去重（`:432-441`）挡不住「fact 是 episode 的摘要」：同一件事会以 fact + episode + MemOS 三条出现。建议：若 fact 的 `episode_ids` 包含该 episode，注入 fact 时跳过该 episode；同一 `evidence_ids` 交集 ≥1 的候选只留精度最高的那个。
5. **预算硬上限。** 当前注入 3 条、每条 90 字（`:969`）。建议分层预算：fact/insight ≤2 条、episode ≤1 条、raw chat ≤2 条，总 ≤5 条；关系时间线单独 ≤60 tokens（`docs/调研-世界感知Phase2-4-2026-11-18.md:157-163` 已定）。
6. **仲裁公式可借用，但别混用 TTL。** `fact-store.js` 的 `score = conf*freshness + rank/100*0.1`、`conflictTol=0.12`、`4×ttl` 剔除（`js/core/fact-store.js:20-29, 115-162`）是为**毫秒级运行时状态**设计的；它的「新鲜度惩罚、冲突标记、来源优先级」形状可以借，但 `ttlMs` 不能套到以天/月计的记忆上。

### 2.6 检索质量评测：LongMemEval 能不能裁成 20–50 题

**数据形状**（`LongMemEval/README.md:75-88`）：

- 三个文件：`longmemeval_s.json`（约 115k tokens / 40 sessions）、`longmemeval_m.json`（约 500 sessions）、`longmemeval_oracle.json`（只保留证据 session）。每个文件 500 条（`README.md:79`）。
- 单条字段：
  - `question_id`、`question_type`（`single-session-user` / `single-session-assistant` / `single-session-preference` / `temporal-reasoning` / `knowledge-update` / `multi-session`；`_abs` 后缀 = abstention）（`:80-81`）
  - `question`、`answer`、`question_date`
  - `haystack_session_ids`、`haystack_dates`、`haystack_sessions`（每 session 是 turn 列表，turn 为 `{role, content}`，证据 turn 带 `has_answer:true`）（`:85-87`）
  - `answer_session_ids`（证据 session id，用于 session 级召回）（`:88`）

**指标：**

- QA 正确率：LLM-as-judge，按题型给不同 prompt（`src/evaluation/evaluate_qa.py:25-42`）：
  - temporal-reasoning 允许天数 off-by-one；
  - knowledge-update 只要最终答案是新值就算对，哪怕同时提到旧值；
  - single-session-preference 用 rubric，不要求覆盖所有点；
  - abstention 检查是否识别「不可回答」。
- 检索指标（`src/retrieval/eval_utils.py:12-29`）：
  - `recall_any`、`recall_all`、`nDCG@k`；
  - session 级：`recall_all@5/10`、`ndcg_any@5/10`（`LongMemEval/src/evaluation/print_retrieval_metrics.py:30`）；
  - turn 级：`@5/10/50`（`LongMemEval/src/evaluation/print_retrieval_metrics.py:37`）；
  - 检索评测跳过 30 条 abstention（`LongMemEval/README.md:206`）。

**裁成 20–50 题（建议 36 题）：**

| 题型 | 题数 | 考什么 |
|---|---|---|
| single-session-user | 8 | 用户明说的事实/偏好 |
| single-session-preference | 5 | 个性化建议是否用到偏好 |
| temporal-reasoning | 8 | 「上周/三天前/去年」的时间定位 |
| knowledge-update | 6 | 换猫名/换工作/搬家后只答新值 |
| multi-session | 5 | 跨 episode 综合 |
| abstention | 4 | 没发生过的事要承认不知道 |
| 合计 | 36 | |

**单题 JSONL 形状：**

```json
{
  "id": "m001",
  "type": "knowledge-update",
  "question": "我家猫现在叫什么？",
  "gold_answer": "咪咪",
  "gold_evidence_ids": ["f_abc123", "msg_01142"],
  "question_date": "2026-11-20",
  "expected": "answer",
  "notes": "旧值布丁已 valid_to；答布丁算 stale-leak"
}
```

**指标与门禁：**

- 确定性指标（不花 LLM，可直接进 CI）：
  - `recall_any@5` ≥0.85；
  - `recall_all@5` ≥0.60（多证据题不要求全中，但要看趋势）；
  - `nDCG@5` 作为排序质量；
  - `stale_leak = 0`：注入/回答里出现 `valid_to` 非空的事实即失败；
  - `evidence_coverage = 100%`：每条 insight 至少 2 个 evidence_ids（与 ADR-010:31 一致）；
  - `abstention_accuracy`：无命中时是否说「不记得」，而不是编。
- 可选 LLM 判分：用本地模型跑 `evaluate_qa.py` 的题型 prompt，只做趋势，不做门禁。
- 现有 `_probe/memory-probe.cjs` 已有 `recall@1/@3/@5`、按来源分组、p50/p95 延迟（`:222-236`、`:253-255`），但题目是「从文档抽最具区分度的二字词」自动生成（`:1-19`），本质是自匹配，且正常路径退出码恒 0（`:19`；初始化失败分支在 `:288` 会 exit 1——审计 S-24）。它适合当**开发期温度计**，不能替代固定金集。

**建议的落地方式：** 新建 `_probe/out/memory-gold.jsonl`（36 题，人工写，冻结），配 `_probe/memory-gold-eval.cjs`；每次改召回/反思/事实层都跑，输出 JSON 对比基线；允许 ±3 个点回归，`stale_leak` 必须为 0。

## 4. 明确否掉的方案

| 方案名 | 理由（成本/隔离/可维护性） |
|---|---|
| 上 Graphiti/Neo4j/FalkorDB 图数据库 | 单机几十条事实用不上；图库进程 + schema + 备份 + 迁移四份成本；与现有 JSON 原子写形成两套真相。ADR-010 已否（`docs/adr/ADR-010-记忆v2反思与巩固.md:38` 及 Option E） |
| 每晚固定 3 点全量总结 | 用户作息不固定，3 点可能人在游戏/不在；输入随历史线性增长；无证据链。ADR-010 Option B（`:51-59`） |
| 每 N 轮固定反思 | 寒暄也触发；成本与对话量线性；轮次不等于信息量。ADR-010 Option C |
| 每个 episode 都反思 | 一天十几个 episode；相邻结论高度重复，污染 `insights.jsonl`。ADR-010 Option D |
| 把全部事实塞给模型总结 | 上下文早晚爆；幻觉无法定位；违反 ADR-004 成本约束。ADR-010 Option F |
| mem0 的 in-place UPDATE/DELETE 自动改写 | 丢历史、不可审计；与「只 supersede 不删除」冲突；mem0 HEAD 自己也已改成 additive-only（`mem0/mem0/memory/main.py:918-944`） |
| 纯向量阈值召回（只靠 cos≥0.5） | 中文短句余弦只有 0.40–0.55（`memory-recall/index.js:817-820` 实测注释）；会漏精确命中；必须词法+向量 RRF |
| 对稳定事实做时间衰减 | 身份类事实会被压死（`memory-recall/index.js:408-418` 已踩过）；核心/事实/用户记忆必须免衰减 |
| 自动删除低价值记忆（GA `concept_forget` / 定期 purge） | GA 的 `concept_forget=100` 是死配置（`scratch.py:49`，无引用）；删除不可逆；ADR-010 明确删除只由用户发起（`:118`） |
| 把 GA 的 `expiration` 字段当遗忘机制 | 写了从不读（`associative_memory.py:125-127` 只有保存/加载）；不是机制 |
| 抄 Letta archive / MemGPT V1 源码 | 上游 `letta/AGENTS.md:3-20` 明确禁止把 archive 用于生产、评测、对比、复制；该代码已退役，不代表当前实现 |
| 把 Graphiti 的逐边 LLM 抽取管线整套搬来 | 每次 ingest 多次 LLM + 图写入；我们日增几条事实，成本/收益不成立；只抄字段和失效规则 |
| 召回时把 MemOS 分数和本地 BM25 分数直接相加 | 量纲不同（cos vs BM25 vs `sim*(1+0.3*importance)`），不可比；必须先源内排序再 RRF |
| 让反思结论直接写人格 core 或技能库 | 一次概括会污染身份；ADR-012 明确 insight 是 semantic，不是 procedural，变技能必须走执行+验证链（`docs/adr/ADR-012-技能沉淀与程序性记忆.md:92`） |
| 用固定时钟/整点触发反思 | 与「重要性触发」重复且更差；ADR-010 已否 B/C/D |

### 5.2 缺什么（对照 ADR-010 Action Items）

ADR-010 仍是 Proposed（`docs/adr/ADR-010-记忆v2反思与巩固.md:3`），Action Items 全部未勾（`:122-128`）：

3. `insights.jsonl` 不存在：`grep -rn "insights" _incoming/my-neuro/live-2d --include=*.js` 无命中；`find _incoming/my-neuro -name "insights*"` 无结果。
4. 反思代码不存在：`grep -rn "reflection\|反思" _incoming/my-neuro/live-2d/plugins --include=*.js` 无命中。
5. 双闸沉淀未实现：没有「同一结论出现次数」统计；`addFact` 没有 `source:'reflection'` 的调用方。
6. 开放回路未实现：没有 open_loop 文件/插件。

8. 检索质量评测未接入：`grep world-eval` 无实现；`memory-probe` 是自动出题、非金集、exit 0（`:19`）。
9. 证据链断裂：`addFact` 无 `evidence_ids`（`user-facts.js:159-167`）；`_promoteEpisodeFacts` 不传 episode id（`memory-evolve/index.js:184`）；对话历史无消息 id（`memory-recall/index.js:79`）。
10. 跨层巩固不存在：MemOS 每天演化自己的 Qdrant（`evolution.py:152-246`），但本地 `user-facts/episodes/slow` 之间没有相互巩固；episode→fact 只是 3 条字符串的粗升级。

### 5.3 三个必须纠正的现状判断

**纠正 1：「事实表（TTL + 来源绑定 + 冲突不放行）」说的是 `fact-store.js`，不是用户事实层。**

- `js/core/fact-store.js` 是**运行时状态仲裁**：`ttlMs` 毫秒级、`sourceRank`（mod 100 / api 80 / memory 60 / vision 50 / replay 20）、`conflictTol=0.12`、`4×ttl` 剔除（`:20-29, 96-107, 115-162`）。它服务游戏 HUD/状态，不是长期记忆。
- `js/core/user-facts.js` 是**长期用户事实**：`valid_from/valid_to`、supersede、无 TTL（`:132-172`）。
- 交接文档 `docs/交接-大肥鱼桌宠-2026-11-08-0830.md:7624` 把两者混成一句「事实表（TTL+来源绑定+冲突不放行）」。做记忆 v2 时如果按 TTL 设计用户事实，会直接把「他以前养过布丁」过期掉。**用户事实层不要 TTL。**

**纠正 2：MemOS 原文库当前不在召回路径里。**

- 写入：`_postToMemos`（`memory-recall/index.js:483-500`）。
- 召回：只查本地索引（`:219-257`），没有 `/search` 调用。
- `/search` 只出现在「用户说忘掉」的删除流程（`:548`）。
- 所以「双源注入怎么消解」目前没有真实冲突可测；这是一个待建能力，必须先做离线对比（见 §6）。

**纠正 3：「巩固没有」不准确，MemOS 有每日演化；问题是它没有效果。**

- 配置每天跑（`memos_config.json:102-104`），最后一次 scanned 184、decayed 170。
- 但 `merged=0`、`archived=0`（最近一次运行）：0.95 合并阈值和 60 天/0.2 归档阈值在真实数据上没被触发过。
- 本地层没有跨层巩固；MemOS 的演化也不会回写 `用户事实.json`。
- 所以准确说法是：**「MemOS 层有衰减式演化，本地事实/episode 层没有巩固，且 MemOS 的合并/归档阈值未被验证。」**

### 5.4 与既有设计文档的衔接

- `docs/调研-世界感知Phase2-4-2026-11-18.md:157-163` 已经提出「关系时间线是纯函数视图，不建图」，与本调研一致；本调研补充了 Graphiti 的字段级依据和 `recorded_at/expired_at` 双时间轴。
- 同文档 `:142-144` 已提出「evidence_ids ≥2、去重余弦 ≥0.88、沉淀 confidence ≥0.75」。本调研发现 **0.88 阈值可能过高**：中文短句余弦常见 0.40–0.55（`memory-recall/index.js:817-819`），0.88 很可能永不合并，和 MemOS 的 0.95 一样变成死阈值。建议先用真实 insight 对做阈值扫描（见 §6）。
- ADR-012 的边界要保留：反思结论是 semantic，不是 procedural；不能直接变技能（`docs/adr/ADR-012-技能沉淀与程序性记忆.md:92`）。

## 6. 未解问题 / 需实测的假设

1. **importance 1..10 的映射未校准。** 现有 `memory-evolve._score` 输出 0..1（`memory-evolve/index.js:326-337`），不是 1..10。候选映射 `1 + 9*score` 或分桶（0/1–3/4–6/7–8/9–10）。假设：规则分与人工 1..10 标签的 Spearman ≥0.5。测法：抽 50 条真实用户话，人工打分，算相关性；<0.4 则改为「规则先筛候选，LLM 只给候选打分」。
2. **触发阈值 60 未实测。** GA 的 150 是按 1..10 分、约 15–30 事件；我们的 60 约 6–15 事件。假设：60 + 新增 ≥6 + idle ≥10min 的组合下，每天 1–3 次反思。测法：上线两周记录触发次数、insight 数、用户负反馈；>4 次/天调到 80–100，<0.5 次/天降到 40。
3. **「≥2 条证据」会误杀单事件洞察。** 「他今天很安静」可能只有 1 条证据。假设：拒收率 <30%；若 >40%，按 insight 类型分档——`observation` 允许 1 条，`trait/summary` 必须 ≥2 条。
4. **insight 去重阈值 0.88 可能永不触发。** 中文短句余弦 0.40–0.55（`memory-recall/index.js:817-819`），MemOS 0.95 在 184 条上 merged=0。假设：0.80–0.85 能合并真重复且不并掉不同结论。测法：100 对真实 insight 人工标「同义/不同」，扫 0.75–0.90 找 F1 最优点。
5. **MemOS 是否该进召回路径。** 假设：把 MemOS top 5 用 RRF 并入本地召回，在 30 条语义改写题上 `recall_any@5` 提升 ≥5 个点，且 `stale_leak=0`。若提升 <2 点或延迟 p95 增加 >100ms，不接。必须先离线跑，不要直接上线。
6. **关系时间线用「扩展 facts」还是「新建 relation 文件」。** 假设：给 `user-facts` 加 `subject/predicate/object/recorded_at/evidence_ids` 能覆盖 90% 的「什么时候改的/以前是什么」问题。测法：写 20 条时间线问题，人工判断现有字段是否够；若多跳问题 >20%，再考虑图。
7. **反思是否真的提升陪伴感。** 没有离线指标能替代。假设：反思驱动的主动提及（「你上周说…」）被用户接受率 ≥35%，负反馈 ≤8%。测法：A/B 两周，接 `speech-budget` 的 accepted/ignored/negative（`docs/调研-世界感知Phase2-4-2026-11-18.md` §4.2 已有账本）。
8. **open_loop TTL 7 天是否合理。** 没有承诺兑现时长的数据。假设：承诺从说出到完成的中位数 ≤7 天。测法：先记录 `promised_at/closed_at`，两周后看分布；中位数 >7 天则 TTL 改 14 天。
9. **episode 卡片摘要是否忠实。** 目前只有 8 张卡，未人工审计。假设：20 张卡的事实错误率 <10%。若 >20%，先改 episode 提示词，再谈把 episode 当证据。
10. **MemOS 每日 5% 衰减是否伤害召回。** `final_score = sim*(1+0.3*importance)`，importance 从 0.7 衰减到 0.1 只让总分下降约 15%（1.03/1.21）；理论上不致命，但 `decayed=170` 说明几乎所有记忆每天在降。假设：对 top-5 召回排名影响 <1 位。测法：固定 30 题，比较衰减前后的命中排名。
11. **`_gateHits` 的余弦索引可能错位。** 它用 `opts.cos[out.length]` 取当前候选的余弦，而 `out.length` 是已通过数量，不是候选在 `all` 里的下标（`memory-recall/index.js:871`）。当有候选被跳过时，余弦会张冠李戴。假设：修复后语义召回率变化 ≥2 个点。测法：先修再跑 `--paraphrase` 探针；在修之前，所有语义评测数字都不可信。
12. **LongMemEval 的迁移性未验证。** 它面向英文长对话（按 README/论文口径；本机只有 `data/custom_history` 的样例脚本，未下载 500 题数据文件），而我们是中文、短对话、1159 行。假设：只把它当「管线回归」，不宣称绝对能力；绝对值差异 >20 个点属正常。测法：同一套 36 题金集 + LongMemEval 抽 50 题，双轨跑，只看趋势。
