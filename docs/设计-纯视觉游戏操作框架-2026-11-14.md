# 设计：纯视觉游戏操作框架（2026-11-14）

> 用户目标：像人一样「只用画面 + 键鼠」打游戏 —— 快速、准确、判断合理。
> 先落地一款游戏验证，再推广到多款。
> 硬约束：**模型要自然知道怎么用**（不靠 skill 说明书）、**要快**（Rust/C）。

---

## 一、现状与实测瓶颈（这是设计的起点）

### 1.1 我们已有什么

| 能力 | 位置 | 状态 |
|---|---|---|
| WGC 抓窗口帧（CreateForWindow，被遮挡也能抓） | `pet-core/src/wgc.rs` | ✅ 实测 ZCode 1311×877 / 348ms、PotPlayer 2576×1456 / 393ms |
| 鼠标注入（含 UAC 探针/4px 急停/遮挡检测/贝塞尔拖拽） | `pet-core/src/native.rs` | ✅ 28ms（对比 pwsh 773ms） |
| 键盘注入（扫描码，游戏认） | `pet-core/src/native.rs` | ✅ 1-3ms |
| 屏幕哈希 / 局部灰度差 | `pet-core/src/native.rs` | ✅ 34ms 全屏 dHash |
| UIA 树 + 语义动作 | `pet-core/src/uia.rs` | ✅ 41.8ms |
| 常驻内核（serve 模式，稳态 1ms） | `pet-core/src/main.rs` | ✅ 本轮新加 |
| 视觉原语：血条(颜色) / 网格差分 / 按钮 / 数字(OCR) | `pet-runtime/tools/visual_enhance.py` | ✅ 但见 1.2 |
| 模板匹配找图 | `pet-runtime/tools/visual_locate.py` | ✅ |
| 动作后验证（区域灰度差） | `game-control.js` `actAndVerify` | ✅ |

### 1.2 实测瓶颈（关键）

```
visual_enhance.py bars --window ZCode  →  1.289 秒
  ├─ Python 启动 + import cv2   ~757ms
  ├─ WGC 抓帧（一次性 spawn + BMP 落盘 + 读回）  490ms
  └─ OpenCV 检测  42ms
```

**结论：现有路径 1.3 秒/帧，做不了任何「反应」。**
动作游戏要的是 **10-30ms/帧**（30-100fps）。差 40-100 倍。

三个瓶颈各自的原因：
1. **Python 每次新进程** → 解释器 + cv2 import 全付一遍
2. **WGC 一次性调用** → spawn pet-core + 建 session + 等首帧 + 写 BMP + Python 读回（四次拷贝）
3. **跨进程传图** → 像素走「GPU → CPU → 文件 → Python」

## 二、分层架构（LLM 不在实时回路）

```
┌──────────────────────────────────────────────────────────────┐
│ L3 规划层 · LLM（秒级，异步，不在回路）                        │
│   输入：低频关键帧（1-2 张/秒）+ 结构化状态摘要                 │
│   输出：**意图**（不是坐标）                                    │
│     { "goal":"kill_boss", "target":"nearest", "style":"burst" }│
└───────────────────────┬──────────────────────────────────────┘
                        │ 意图（改一次管几秒）
┌───────────────────────▼──────────────────────────────────────┐
│ L2 策略层 · Rust 行为树（10-50ms）                             │
│   目标选择（最近/最脆/威胁最大）→ 技能优先级 → 走位 → 闪避判定   │
│   输入：L1 的 GameState（每帧）；输出：原子动作                │
└───────────────────────┬──────────────────────────────────────┘
┌───────────────────────▼──────────────────────────────────────┐
│ L1 感知层 · Rust 常驻（8-30ms/帧）                             │
│   · 常驻 WGC frame pool（60fps，不重建 session）               │
│   · 确定性检测：血条/蓝条(HSV) 技能CD(环形灰度) 敌人(轮廓/模板) │
│   · 输出 GameState { hp, mp, skills[], enemies[], self }      │
└───────────────────────┬──────────────────────────────────────┘
┌───────────────────────▼──────────────────────────────────────┐
│ L0 反射层 · Rust（1-5ms）                                      │
│   SendInput 扫描码 + 鼠标快轨（已有）                          │
└──────────────────────────────────────────────────────────────┘
```

**为什么 LLM 必须不在回路里**：
- 云端 VLM 一次 1-3 秒；本地 7B 也要 300-800ms
- 动作游戏「看到技能特效 → 闪避」的窗口是 **100-200ms**
- 结论：**高层用 LLM（秒级决定打谁），低层用确定性代码（毫秒级决定怎么打）**
- 这也正是开源游戏 AI 的共同做法（待调研确认具体数字）

## 三、延迟预算（目标 vs 现状）

| 阶段 | 现状 | 目标（Rust 常驻） | 做法 |
|---|---|---|---|
| 抓帧 | 490ms | **3-8ms** | WGC frame pool 常驻；GPU texture 直接进检测（或单次 staging 回读） |
| 预处理 + 检测 | 42ms（Python OpenCV） | **5-15ms** | Rust：`image`/`opencv-rust`，ROI 限定 + 降采样 |
| 决策 | — | **1-5ms** | 行为树（纯算术，无分配） |
| 注入 | 28ms（Rust 快轨） | **1-3ms** | 已有 SendInput 扫描码 |
| **端到端** | **1290ms** | **10-30ms** | 30-100fps 反应 |

**关键工程原则**：
1. **一个常驻进程**（扩展 pet-core），WGC session / 检测器 / 行为树全在内存里
2. **零落盘**：绝不写 BMP 再读（那是 490ms 的一半）
3. **ROI 优先**：只算需要的区域（血条在左下、技能栏在底部、敌人在画面中部）
4. **降采样**：1440p → 960p 检测，坐标按比例换算（精度损失可接受）

## 五、决策层：行为树（不是 LLM）

```
Selector(
  Sequence( hp < 30%, UseHeal ),
  Sequence( incoming_damage, Dodge ),
  Sequence( skill_ready(ultimate) && enemy_in_range, UseUltimate ),
  Sequence( skill_ready(2), UseSkill2 ),
  Sequence( enemy_in_range, BasicAttack ),
  MoveTo(nearest_enemy)
)
```

- 节点是 Rust 结构体，每帧 walk 一次（微秒级）
- **可热改**：行为树用 JSON 描述，游戏切换换一份（这就是「多款游戏」的扩展点）
- **LLM 只改参数**：`target=nearest` / `style=burst` / `retreat_hp=40%`

### 多游戏扩展
每款游戏一份**profile**（已有 `SEMANTIC_PROFILES_BUILTIN` 的雏形）：
```json
{
  "game": "minecraft_pve",
  "capture": { "hwnd_title": "Minecraft", "fps": 30 },
  "roi": { "hp": [0.02,0.88,0.18,0.03], "hotbar": [0.30,0.92,0.40,0.06] },
  "detect": { "hp": {"type":"bar","color":"red","min_len":0.1} },
  "keys": { "attack":"mouse_left", "forward":"w", "dodge":"space" },
  "tree": "pve_basic.json"
}
```

## 六、「模型自然知道怎么用」（不靠 skill）

### 6.1 问题
现在 `game_control` 一个工具 36 个动作 + 一大段 arg 描述 → 模型要读很久，还容易选错。

### 6.2 解法：**工具面收窄 + 语义化**
新增 **3 个**工具（不是往 36 个里再加）：

| 工具 | 参数 | 作用 |
|---|---|---|
| `game_see` | `window`（可选）、`detail`（`state`/`frame`/`both`） | 看游戏状态：结构化 GameState + 可选一帧图 |
| `game_act` | `intent`（`attack`/`dodge`/`skill 2`/`move left`/`use item`）、`window` | 一次高层动作（内部自动选键鼠路径 + 验证） |
| `game_loop` | `mode`（`start`/`stop`/`status`）、`profile`（如 `minecraft_pve`） | 启停**反应循环**（L1+L2 自己跑，模型不用管） |

设计要点：
- **工具描述是 schema 的一部分，每次请求都带** → 会话压缩/新建都不会丢（这正是「不靠 skill」的关键）
- 描述 ≤ 500 字（现在那段 arg 描述有 2000+ 字）
- 错误信息带 `nextIfFailed`（已有）
- **模型只需要知道 3 件事**：怎么看、怎么动一下、怎么让它自己打

### 6.3 不给模型的东西
- 不要让它写行为树
- 不要让它报坐标（那是 L1/L2 的事）
- 不要让它每帧决策（那是 1-3 秒的延迟源）

## 七、语言选型

**结论：Rust**（不是 C）

| 维度 | Rust | C |
|---|---|---|
| 性能 | ≈ C（同 LLVM，零成本抽象） | 基准 |
| 内存安全 | 编译期保证 | 手动 → 常驻 60fps 循环里 UAF 直接崩整局 |
| 现有代码 | **已有 5000 行 pet-core**（WGC/UIA/SendInput 全套） | 要重写 |
| Windows API | `windows` crate（微软官方维护） | 手写 P/Invoke 头 |
| ONNX 推理 | `ort`（DirectML EP 支持） | onnxruntime C API（要自己管生命周期） |
| OpenCV | `opencv-rust` binding | 原生 |
| 编译期 | 慢（可接受，不是热路径） | 快 |

**什么时候才值得上 C/内联汇编**：需要榨最后 10%（手写 AVX2 做像素比对）时，可以用 Rust 的 `core::arch` 内联（不需要换语言）。

## 十一、三份调研的硬数据（2026-11-14，本机实测 + 公开实测）

### 11.1 抓帧

| 方案 | 数字 | 性质 |
|---|---|---|
| **我们的常驻 WGC** | **1.9ms/帧**（1311×877 全帧回读） | 本机实测 |
| 一次性 WGC（我们改前） | 348–490ms | 本机实测 |
| 回读拟合 | `0.85ms + 0.383ms/MB`（1440p 6.5ms / 4K 13.6ms） | 本机两点拟合 |
| 只拷 ROI（400×200 = 0.32MB） | **0.3ms** | 推算 |

**结论**：抓帧已经不是瓶颈。真要再榨，就在 GPU 端先缩到 640×640 再回读（→0.9ms）。

### 11.2 检测（我们的实测，ROI 尺寸决定一切）

| ROI | 检测耗时 |
|---|---|
| 全图 1311×877 | 46ms |
| 20%×20%（262×175） | 3ms |
| 血条典型 18%×3% | **2ms** |
| gray（技能 CD） | 2ms |
| colors（找目标） | 4ms |

公开实测对照：ROI 400×200 颜色+连通域 **0.78ms**；全屏 1440p 颜色+连通域 33ms。
→ **profile 必须写小 ROI，这是 10 倍级差异**。

### 11.3 推理（如果要上模型）

| 后端 | YOLOv8n 640 | 备注 |
|---|---|---|
| ORT CPU 8 线程 | 31ms | 本机实测 |
| **ORT DirectML（RTX 4060）** | **6.5ms** | 本机实测，**但要先装 onnxruntime-gpu** |
| TensorRT fp16 | 1–2ms | 要 CUDA |
| OpenVINO（Intel 核显） | 3.3ms | 本机核显未启用 |

**本机硬约束（实测）**：
- `onnxruntime` 当前是 **CPU 版**（providers = [Azure, CPU]）→ GPU 推理不可用
- 显存：空闲 2330 MiB / 剩 **5627 MiB**；开 1080p 游戏后剩 **0–2100 MiB**
- 所以模型预算 **0.5–1.5GB**；Qwen3-VL-8B（6.14GB）**必溢出**

### 11.4 开放词汇检测（零标注）

| 模型 | 参数 | 文件 | 本机估算 | 判断 |
|---|---|---|---|---|
| **YOLOE-11s** | 10–12M | **27.8MB** | 3–5ms | ✅ **首选**（T4 3.3ms，零样本 LVIS 27.5） |

| OWLv2 | 154M | 620MB | 600–800ms | ❌ prompt 换一个词 mAP 从 0 跳到 0.348 |
| Florence-2 | 0.23B | 463MB | 1–2s（自回归） | ❌ 官方 ONNX 导出至今报错 |

2. **第二版**「零样本当老师 + 小模型当学生」：YOLOE 自动标 300–800 帧 → 训 YOLO26n/s（2–3.5ms）
   - 工具：`autodistill`（2.8k★），全程零人工画框
   - 先例：Project AIRI（Neuro-sama 同类）用 <1000 张标注做到了

### 11.5 前后处理的坑（比推理还贵）

| 操作 | 耗时 | 教训 |
|---|---|---|
| `cv2.resize` INTER_AREA（大倍率缩小） | 10ms | **慢 6.5×**，用 LINEAR（1.54ms） |
| `cv2.dnn.blobFromImage` 1440p→640 | 4.96ms | 推荐写法 |
| 后处理 `.tolist()` + `NMSBoxes` | **31.5ms** | **是主因** |
| `argpartition(top200)` + 向量化 NMS | **1.81ms** | 快 17× |
| 手写 numpy 颜色阈值 | 19.7ms | 比 `cv2.inRange` 慢 5 倍 |

### 11.6 注入与传帧

| 项 | 数字 |
|---|---|
| SendInput → WM_INPUT | **p50 0.94ms**（我们用的就是它） |
| PostMessage → 窗口过程 | 0.02ms（但游戏收不到） |
| 共享内存传帧（14.75MB） | **0.55ms** |
| 命名管道传帧（同尺寸） | **6.31ms**（慢 10 倍）→ **绝不能用管道传整帧** |

**我们现在是「写文件」（~3.8ms）→ 应该改共享内存（0.55ms），预计再省 3ms。**

### 11.7 开源界的能力真话（第一份调研）

| 项目 | 感知 | 决策 | 频率 | 真话 |
|---|---|---|---|---|
| BetterGI 18k★ | 血条颜色连通域 + 22×12px 技能 ROI | JSON 优先级表 | **50ms** | 真能跑，但**不会闪避**（靠护盾/奶妈） |
| ok-wuthering-waves 8.6k★ | 模板 + 颜色比例 + OCR | 角色类 + 优先级仲裁 | 50ms | 闪避键在配置里但**代码从未读取** |
| Cradle（MIT） | GroundingDINO + 小地图 | GPT-4o 每步 5 次 | **秒级（2fps）** | 真能跑 RDR2 主线，但不是战斗反应 |

**「真正能跑纯视觉打 boss 的，全是高频 CV 反射环 + 阻塞式技能脚本，没有一个靠 VLM 实时决策。」**

三件可抄的：
1. **血条像素高度当距离**（2–7px 远 / 6–25px 近战）—— 不用测距
2. **低血只读一个像素** `(808,1010)` ——「80% 的判断只需要 1 个像素」
3. **JSON 优先级决策表**（`index` 越小越优先，条件函数只有十几个）—— 比行为树好维护，LLM 可写

**空白（我们的差异化机会）**：**闪避**。全开源界都没做（前摇识别是 3–8 帧时序问题）。可做 8–16 帧轻量时序模型（TCN/GRU，<1M 参数）+ 100ms 反射。
