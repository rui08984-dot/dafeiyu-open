## 2. 可直接抄的机制

### 2.0 先答五个机制问题（Q6 的三条恢复任务设计见 §4.1；每条带真实 repo/path:line）

#### Q1 最小结构：意图→计划→执行→验证→恢复，状态由谁持有？计划是什么数据结构？

**结论：这些仓库里没有一个把「意图→计划→执行→验证→恢复」完整做成一个对象；最接近最小结构的是
Agent-S 的「`requires_replan` + 失败子任务 + 已完成列表 + 剩余列表」状态机。计划在运行时都是线性列表，
DAG 只是生成顺序的中间产物。**

|---|---|---|---|---|---|

**对我们的最小结构（设计结论）**：

一句话：**goal 只认外部 `done_when`；plan 只存线性 ≤8 行；每行带一个 T2 verify；执行器只报 effect；
恢复由宿主按「错误类 + 副作用是否已发生 + oracle 是否判过」三轴选档。** 不是任务树，也不是图。

```
goal{ id, text, done_when: OracleRef, budget{maxSteps,maxWallMs,maxLlmCalls}, status }
  └ plan[] ≤8: { id, text, status: todo|doing|done|failed, verify: T2Ref,
                 attempts, evidence[], last_error_kind }
       └ execute: 现有 30 轮工具循环（只消费当前行，不持有计划真值）
       └ verify:  T1 每动作 / T2 每行 / T3 任务结束
       └ recover: 0 不重试 → 1 幂等重试 → 2 换 grounding → 3 重规划 → 4 ask_user → 5 fail
```

> T1/T2/T3 沿用 ADR-007：T1 = 动作效果（已有 `verify-contract`）、T2 = 子任务声明式断言（新增）、
> T3 = 任务级外部 oracle（新增）。

- **状态所有权**：`mind-kernel` 持 goal+plan，原子写 `data/goals.json`；`llm-handler` 只持对话；
  `pet-core` 不持任何计划状态（与 ADR-001/006 一致）。
- **持久化粒度**：只抄 LangGraph 的 `Checkpoint`（`id/ts/channel_values/channel_versions`）与
  `CheckpointTuple.pending_writes` 的思想，不引入其运行时；每个 plan 行状态变化写一次
  （等价 `durability: sync`），不要每个 token 写。
- **DAG 不需要**：Agent-S 生成 DAG 后立即拓扑排序成线性队列（`manager.py:313-317`），
  运行时并没有并行；为 3–8 步线性任务付两次 LLM 调用不划算（与 ADR-006 Option B 的结论一致，本轮源码再次证实）。

#### Q2 重规划输入：失败后传给重规划器的精确字段

**Agent-S s2（最干净的一处）**：

- 函数签名：`get_action_queue(instruction, observation, failed_subtask: Optional[Node] = None,
  completed_subtasks_list: List[Node] = [], remaining_subtasks_list: List[Node] = [])`
  （`Agent-S/gui_agents/s2/agents/manager.py:293-300`）。
- 调用点传参：`failed_subtask=self.failure_subtask, completed_subtasks_list=self.completed_tasks,
  remaining_subtasks_list=self.subtasks`（`agent_s.py:228-234`）。
- 失败分支的 prompt 实际只渲染两项：
  `"The subtask {failed_subtask} cannot be completed. Please generate a new plan for the remainder of the trajectory.
  Successfully Completed Subtasks: {completed_subtasks_list}"`
  （`manager.py:173-177`）。
  **注意：`remaining_subtasks_list` 虽然传进来了，但失败分支没有渲染它**——这是一个真实缺口：
  重规划器看不到「已经计划但还没做」的条目，可能把剩余条目重造或漏掉。我们抄字段，但要补渲染 remaining。

**Agent-S s1（另一处，带失败动作原文）**：

- `failure_feedback = f"Completed subtasks: {self.completed_tasks}. The subtask {self.current_subtask}
  cannot be completed. Please try another approach. {executor_info['plan_code']}. Please replan."`
  （`Agent-S/gui_agents/s1/core/AgentS.py:254`）。
- 这里比 s2 多一个关键字段：`plan_code`（失败前实际尝试的动作代码）。重规划器不仅知道「哪个子任务失败」，
  还知道「上一次具体怎么做的」，能显著降低重复同一条错路。**这是本轮最值得抄的一个细节。**

**Agent-S s3（子任务结果信封）**：

- `CodeAgent` 返回 `{task_instruction, completion_reason, summary, execution_history, steps_executed, budget}`
  （`Agent-S/gui_agents/s3/agents/code_agent.py:266-273`），外层 Worker 把这些字段拼进下一轮 prompt
  （`gui_agents/s3/agents/worker.py:210-224`）。
- `completion_reason` 的取值是一个三态枚举：`DONE` / `FAIL` / `BUDGET_EXHAUSTED_AFTER_{n}_STEPS`
  （`code_agent.py:176/184/260`；文档解释见 `gui_agents/s3/memory/procedural_memory.py:43-49`）。

**τ-bench（没有重规划器，只有反馈字段）**：

- 唯一的下一步输入是 `EnvResponse{observation, reward, done, info}`（`tau/tau_bench/types.py:52-56`），
  其中 `EnvInfo{task, source, user_cost, reward_info}`（`types.py:45-49`）。
- 工具异常被原地压成字符串：`observation = f"Error: {e}"`（`envs/base.py:105-106`），
  然后继续 `messages.extend(...)`（`agents/chat_react_agent.py:80-85`）。所以 τ-bench 的「重规划输入」
  就是**带错误文本的对话历史**，没有 `failed_subtask/remaining` 这些结构化字段。
- 它唯一的结构化失败标签在事后分析脚本里：`FaultAuthor{user,agent,environment}`
  （`auto_error_identification.py:31-34`）与
  `FaultType{called_wrong_tool, used_wrong_tool_argument, goal_partially_completed, other}`
  （`auto_error_identification.py:48-53`）。这些名字可以直接当我们 `error_kind` 的枚举。

**我们下一轮的重规划 payload（设计，不写代码）**：

```
{
  task_id, plan_id, attempt, replan_count,
  failed_subtask: {id, text, verify_hint},
  failed_action: {tool, args, result_summary, error_kind, error_text},
  completed: [{id, text, evidence}],
  remaining: [{id, text}],          // 必须渲染，修 Agent-S 的缺口
  world_digest: "前台窗口/文件是否存在/关键 UIA 摘要",
  budget_left: {steps, wall_ms, llm_calls}
}
```

#### Q3 失败分类：哪些原地重试、哪些必须改计划、哪些放弃

**判据顺序（综合四处源码）**：

1. **先问副作用是否可能已经发生**。`action_sent=true && verified=null` 的动作绝不能自动重跑
   （`live-2d/plugins/community/dispatch/verify-contract.js:23-24` 的契约注释；
   browser-use 的 prompt 也明写 `A failed call may have partially executed: inspect, never replay uncertain actions automatically`，
   `browser-use/browser_use/agent/prompt.py:36`）。
2. **再问错误是不是可重试类**。LangGraph 是唯一给出「按异常类判定」的实现：
   `ConnectionError` 与 HTTP 5xx → 重试；`ValueError/TypeError/ArithmeticError/ImportError/LookupError/
   NameError/SyntaxError/RuntimeError/ReferenceError/StopIteration/StopAsyncIteration/OSError` → 不重试；
   其余 → 重试（`langgraph/libs/langgraph/langgraph/_internal/_retry.py:1-29`）。
   重试上限 `max_attempts=3`，带 `backoff_factor` 与 jitter（`types.py:434-447`），到上限直接 `raise`
   （`pregel/_retry.py:677-681`）。
3. **最后问 oracle 判过没有**。OSWorld 的判据只有一句：`scored = result.txt 存在`；
   `retryable: not scored`（`OSWorld/lib_run_errors.py:26-37`）。已判分的 attempt 不因清理错误重跑，
   未判分的才可重跑，且重跑前把旧产物移到 `attempts/`（`lib_run_errors.py:63-73`；
   `run.py:248-250`）。

**三路分类的源码锚点**：

| 分类 | 判据 | 源码 | 处理 |
|---|---|---|---|
| 原地重试（同计划） | 传输错误/5xx，且副作用未发生 | `langgraph/_internal/_retry.py:5-10`；`pregel/_retry.py:677-681` | 退避重试 ≤3；不换计划 |
| 原地重试（同子任务，换路） | `suspected_noop`/grounding 失败，oracle 未判过 | 我们的 ADR-007 阶梯 1–2；信号来自 `browser-use/browser_use/ax.py:803` 的 `no change` | 换 grounding 档/重读状态，重试 1 次 |
| 改计划 | 执行器显式 `FAIL`，或子任务 oracle 判失败 | Agent-S `agent_s.py:287-299`；s1 `AgentS.py:251-262` | `requires_replan=True`，带 failed/completed/remaining 重规划 |
| 改计划（结构性变化） | 目标窗口/应用消失、前台被抢、前提不成立 | Agent-S 只覆盖「子任务失败」，结构性变化需我们在 T2 里判 | 先标记剩余行为 `todo`，再重规划；已完成行保留 |
| 放弃/终止 | 预算耗尽、显式 `FAIL`、终止工具、测试超时、上下文超限 | Agent-S `code_agent.py:253-260`；τ-bench `envs/base.py:108-109` + `envs/airline/env.py:37`（`transfer_to_human_agents`）；OSWorld `desktop_env.py:506-511`；Terminal-Bench `failure_mode.py:4-15` | 写 `failed` + reason + evidence，零重试 |
| 带部分结果终止 | 步数/时间预算到点 | browser-use `loop.py:430-438`；`1313-1317` | 停止规划，交付 partial，状态标 `budget_exhausted` |

**τ-bench 的反面教材**：所有工具异常都被 `except Exception` 吞成 observation（`envs/base.py:100-106`），
没有任何重试上限或分类；在沙箱 benchmark 里可以，在真实桌面会变成「无限重试同一个副作用」。
我们只抄「把错误文本给模型」，不抄「无分类、无上限」。

**给实现的判定顺序（设计，不是代码）**：

```
if side_effect_possible:                 -> 只读确认，禁止自动重发（阶梯 0）
elif retryable_error && attempts < 2:    -> 原地重试 / 换 grounding（阶梯 1–2）
elif subtask_verify_failed && replans<2: -> 重规划 failed + completed + remaining（阶梯 3）
else:                                    -> ask_user 或 fail + evidence（阶梯 4–5）
```

**两个必须避开的坑（源码直接证明）**：

1. **Agent-S 的步数在每次重规划时归零**：`reset_executor_state()` 把 `step_count` 重置为 0
   （`Agent-S/gui_agents/s2/agents/agent_s.py:205-208`，在 `:294-295` 被调用）。
   这意味着「失败→重规划」可以无限续命，任务级预算形同虚设。我们的 `maxSteps` 必须由
   `mind-kernel/arbiter` 单调递减，重规划**不返还**。
2. **browser-use 有重复指标但没有熔断**：`_struggle()` 算出 `repeat_code_steps / repeat_fail_steps /
   max_err_streak / last_progress_step / wasted_steps`（`telemetry/recorder.py:359-405`），
   但这些字段只进 `telemetry/views.py:170-176`，没有代码据此中止。**可观测 ≠ 已熔断**；
   我们要把计数接到动作层，而不是只写报告。

**WebArena 的 `is_equivalent` 值得直接抄**：它按动作类型分别比较——
`NONE` 恒等、`SCROLL` 比方向、`KEY_PRESS` 比组合键、`MOUSE_CLICK` 比坐标、
`KEYBOARD_TYPE` 比文本、`CLICK/HOVER/TYPE` 优先比 `element_id`，退化为 `element_role+name`，
再退化为 `pw_code`（`browser_env/actions.py:277-303`）。
我们的动作面是 `click/type/key/hold/scroll/drag/...`，可以写一张同构的等价表，
用 `(action,target,args)` 做键，比「全屏 dHash 不变」更早发现「同一个按钮点了三次」。

#### Q5 验证 oracle：任务级 vs 子任务级，怎么判 subtask 完成

| 仓库 | 子任务级 | 任务级 | 读什么 | 源码 |
|---|---|---|---|---|
| OSWorld | **没有**。`step()` 里 `reward=0`、`done=False` 明写 TODO（`desktop_env.py:498-499`） | 有。`evaluate()` 用 `(result_getter, expected_getter, metric)` 三元组，支持多 metric 的 `and/or`（`:533-587`） | 文件、VM 状态、应用数据（getter） | `OSWorld/desktop_env/desktop_env.py:533-587`；infeasible 只在最后动作是 `FAIL` 时给 1（`:545-549`） |

**三条硬结论**：

1. **没有任何仓库有可信的子任务级 oracle**。Agent-S 的 `DONE` 是 actor 自评；它自带的 evaluator prompt
   是死代码。τ-bench/OSWorld/WebArena/Terminal-Bench 全部只在任务结束时判一次。
   这直接证明 ADR-007 的 T2（声明式 `{getter, predicate}`）不是重复造轮子，而是补空白。
2. **任务级 oracle 的共同形状**是 `(读外部状态, 期望, 比较器, 组合方式)`：
   OSWorld 的 `(result_getter, expected_getter, metric, conj)`、WebArena 的 evaluator 相乘、
   Terminal-Bench 的 all-pass，本质同构。我们的 T3 直接采用这个形状。
3. **「结果等价」优先于「轨迹一致」**：τ-bench 只比最终 DB hash（`base.py:137-140`），
   不要求动作序列相同；这正是我们文件类任务该用的判据——比对文件内容/窗口状态，不比对点击顺序。

### 4.1 给 `--deep` 的 3 条恢复任务设计输入（只写设计，不写代码）

**共同约定**：都复用现有 `tasks.mjs` 的 `{id,title,setup,run,verify,cleanup,hostVerify}` 形状；
故障注入必须是**确定性、本机、无 LLM**；`verify` 必须由 Node `hostVerify` 读外部状态（文件字节/窗口矩形/UIA 文本），
不能读工具返回值。三条任务分别打恢复阶梯的三个不同档位，防止「全都测成重规划」。

#### 任务 A：`recover_focus_steal_retry`（瞬时失败 → 原地重试，不重规划）

- **目标**：在记事本夹具里输入唯一标记并保存；最终文件内容精确等于标记。
- **故障注入**：`run` 第一步 `app focus` 到夹具窗口后，调用评测专用助手把另一个已知窗口（如第二个记事本标签/资源管理器）
  切到前台；随后的第一次 `keyboard_type` 打空。注入点是确定的 hwnd，不依赖时序竞态。
- **期望判定**：T1 读回文本为空/不匹配 → 归类 `transient_grounding`（不是 `plan_invalid`）。
- **期望恢复**：重新 `app focus` 目标窗口 → 重试一次输入；**不产生新的 plan 行，不调用重规划**。
- **oracle**：`hostVerify` 读取文件内容，断言 `content === marker` 且 `marker` 只出现 1 次；
  另断言 `plan.replan_count === 0`、工具调用次数 ≤ 6。
- **预算**：`maxSteps=8`、`maxWallMs=45000`、`maxLlmCalls=2`。
- **防作弊**：标记每次随机；检查文件里没有重复标记；检查最终前台窗口是夹具窗口。
- **证明什么**：分类器不会把「可原地修复的 grounding 失败」误判成「计划错了」，避免过度重规划。

#### 任务 B：`recover_window_closed_replan`（结构性变化 → 重规划剩余）

- **目标**：四步链：打开记事本 → 输入 `part1` 保存到 `a.txt` → 输入 `part2` 保存到 `b.txt` → 校验两个文件。
- **故障注入**：在 `part1` 保存成功、`part2` 尚未输入时，runner 按 hwnd 关闭记事本（不保存）。
  此时世界状态发生结构性变化：窗口没了，未保存内容丢失；但 `a.txt` 已经存在。
- **期望判定**：T2 对「窗口存在且标题含 b.txt」失败 → 归类 `environment_drift`；
  `completed=[保存 a.txt]`，`remaining=[输入 part2, 保存 b.txt, 校验]`。
- **期望恢复**：重规划一次：重新打开记事本 → 只补做 `part2` → 保存 `b.txt`；
  **不得重新写 `a.txt`**（否则是重复副作用），也不得从头重跑四步。
- **oracle**：`a.txt` 内容仍为 `part1`（未被改写）；`b.txt` 内容精确为 `part2`；
  `plan.replan_count === 1`；`completed` 里 `a.txt` 行仍为 `done`；总工具调用 ≤ 12。
- **预算**：`maxSteps=12`、`maxWallMs=70000`、`maxLlmCalls=3`（首次规划 + 1 次重规划 + 余量）。
- **防作弊**：两个文件都用随机标记；检查 `a.txt` 的 mtime/内容未被二次写入；检查没有第三次启动记事本。
- **证明什么**：`failed_subtask + completed[] + remaining[]` 三个字段真的驱动了「只补剩余」，
  而不是「整任务重来」；同时验证 T2 能发现窗口消失。

#### 任务 C：`recover_uncertain_side_effect`（不确定副作用 → 先验证再重试）

- **目标**：在已存在的文件末尾追加一行唯一标记（打开文件 → 光标到末尾 → 输入 → 保存）。
- **故障注入**：第一次保存动作实际成功，但工具层返回超时错误（模拟 `withTimeout` 的
  「不再等，但动作可能已完成」，对应 `tool-executor.js:16-17`）。
- **期望判定**：错误文本是超时，但 `action_sent` 语义为「已发出、未验证」→ 归类 `uncertain_side_effect`，
  **禁止原样重试**。
- **期望恢复**：先只读确认（重新打开/读取文件，或 `read_text`）→ 发现标记已存在 → 不重复输入；
  只补做「若未保存则保存」的必要步骤。
- **oracle**：文件里标记出现次数恰好 1；其余内容与初始内容逐字节一致；`plan.attempts` 记录到
  `uncertain` 分支；总工具调用 ≤ 8。
- **预算**：`maxSteps=8`、`maxWallMs=45000`、`maxLlmCalls=2`。
- **防作弊**：标记随机；`hostVerify` 统计出现次数而不是布尔包含；检查文件没有多出空行/重复内容。
- **证明什么**：`action_sent=true && verified=null` 的闸门真的在动作层生效，
  而不是只写在 `verify-contract.js:23-24` 的注释里；这是当前最大的缺口（见 §4 #3）。

**runner 需要的设计级改动（下一轮实现，不在本轮写代码）**：

1. `run` 失败时也执行 `verify`/`hostVerify`（当前 `runner.mjs:755-758` 会跳过），否则恢复任务无法区分「没做」和「做了一半」。
2. 记录 `attempt` 与 `replanTrace`（由 mind-kernel 通过评测专用事件回传），报告里至少要有
   `replan_count / failed_subtask / completed / remaining / error_kind`。
3. 增加 `expectedRecovery` 字段（`retry_in_place | replan | verify_before_retry | ask_user | fail`），
   让「恢复是否正确」成为独立断言，而不是只看最终文件对不对。
4. 故障注入助手只允许在 `setup/run` 的评测上下文里调用，且必须在报告里留 evidence（注入了哪个 hwnd/哪个动作）。

## 5. 未解问题 / 需实测的假设

1. **计划对象对 happy path 到底有没有增益？** 假设：3 条 ≥8 步任务里，plan 主要降低「第 5 步忘了第 2 步」的重复动作，
   对一次性短任务无感。实测：同任务开/关 plan，比较步数、重复动作计数、token；若步数不降，plan 只保留给恢复路径。
2. **T2 断言的合理粒度与成本**。已知 UIA 树热态约 140ms、`edit_text` 约 50ms（`runner.mjs:194-199` 的注释为历史实测），
   但文件读取/窗口矩形未测 p95。假设：T2 只在 plan 行边界跑可接受；每动作跑会拖慢 2–3 倍。需在真机测 30 次取 p95。
3. **重复动作阈值 k 取 2 还是 3？** WebArena 用 3（`run.py:107-110`），我们的 no-change 用 3（`runner.mjs:45`）。
   假设：桌面动作的合法重复（滚动、连续输入）比网页多，k=2 会误伤；需用 `calc_chain`/`notepad` 任务跑 20 次统计误报。
4. **重规划是否该带 `plan_code`？** Agent-S s1 带了（`AgentS.py:254`），s2 没带。
   假设：带上去能减少「换个说法又走同一条错路」；实测两次重规划后是否仍重复同一动作。
5. **重规划时是否该重置执行器对话？** Agent-S 每次都 `reset_executor_state()`（`agent_s.py:294-295`）。
   假设：对我们有害——会丢掉「刚才为什么失败」的上下文；应保留最近 2 轮工具结果，只重置计划。
6. **`retryable = not scored` 是否安全？** 未判分 ≠ 无副作用：动作可能已执行但 oracle 还没跑。
   假设：需要独立的 `side_effect_possible` 标志，不能只用 `scored`；用任务 C 验证。
7. **browser-use 的 90% delivery-only 能否用在语音？** 假设：可以，但必须与 TTS 队列协作，
   不能在句中被切断；需要测「预算到点 → 只读报告」的延迟与断句。
8. **原子 JSON 的写放大**。假设：plan 很小（≤8 行），Windows 上原子 rename p95 < 5ms；
   若超过，改为「每行变化追加 journal，任务结束 compact」。
9. **LLM judge 生成的 `gotchas` 是否稳定？** 假设：同一 trace 重跑 3 次，至少 2 次给出同一类教训才可入库；
   否则只写 `task-episodes` 不写 `skill-library`。
10. **恢复任务的注入是否可复现？** 焦点抢占/窗口关闭对时序敏感；假设：用固定 hwnd 而不是「等 200ms」，
    并且每条任务连跑 3 次全绿才进 CI；否则会变成 flaky 测试。
11. **是否需要为「等待用户输入」建图节点？** Agent-S 的线性队列无法表达「等用户确认」；
    我们的 `ask_user` 是阶梯第 4 级。假设：不需要图，`status=waiting_user` + 事件恢复即可；
    若出现并行分支（同时下载两个文件再合并）再评估 DAG。
12. **30 轮上限是否要随子任务数调整？** 当前是常数（`llm-handler.js:394`）。
    假设：应改为 `min(30, 4 × remaining_subtasks + 4)`，否则 8 步任务会在第 30 轮被硬切；需用 deep 任务实测。
