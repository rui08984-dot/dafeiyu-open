# 设计：工具面重塑（2026-11-14）

> 用户要求：「不只是电脑控制，整个项目所有的工具都要大规模重塑，收敛、加新工具、区域平衡，你自己看一下怎么弄合理一点。」
> 核心目标：**模型自然知道该用哪个**（不靠 skill 说明书）。

## 三、设计原则

1. **按用户意图分类，不按实现技术**
   - 「点击屏幕上的东西」是一件事。用 UIA 编号、OCR 找字、模板匹配、还是裸坐标，是**框架内部的选择**。
2. **一个工具 = 一个动作族**（`music(action, ...)` 而不是 4 个工具）
3. **`target` 自路由**
   ```
   click("#5")        → UIA Invoke（先 see 拿编号）
   click("文字:确定")  → OCR 找字点
   click("图片:按钮")  → 模板匹配点
   click("800,600")   → 坐标点
   ```
   模型只需要知道「要点什么」，不需要知道「用哪种技术点」。
4. **描述 ≤ 200 字**，具体细节放**错误信息里的 `nextIfFailed`**（已有机制）+ 元素清单（已有）
5. **进不去的工具不展示**：低频/危险的（`install_packages`、`profile_rebuild`）走「渐进披露」——
   默认不列，需要时通过 `tools_help(query)` 查（这是唯一允许的「说明书」，且它只在需要时占 token）

## 五、电脑控制四件套的设计（这是样板）

```js
// 看
see(window?, mode?)          // mode: tree(默认,文本编号) | image(标注图) | text(OCR全文) | state(数值)
  → { title, elements:[{id,name,type,rect}], image?, text? }

// 做
act(action, target?, ...)    // action: click/type/key/scroll/drag/paste/set_value/focus
  → 按 target 形态自动路由（#编号 / 文字:xx / 图片:xx / x,y）

// 应用
app(name, action?)           // action: launch(默认)/focus/list/close

// 游戏
game(mode, profile?)         // mode: start/stop/status/see/act
```

**为什么这样更好**：
- 模型只需要回答两个问题：**「看什么」** 和 **「做什么」**
- 不用再纠结「点这个按钮该用 click_element 还是 som_click」
- 每个工具描述 ≤ 200 字

## 六、分阶段落地

| 阶段 | 内容 | 风险 | 验收 |
|---|---|---|---|
| **P0** | 合并「纯数据类」：music(4→1) / schedule(6→1) / note(4→1) / diary(3→1) / profile(3→1) / core_memory(2→1) | 低（这些工具低频） | 工具数 51→37；每个合并工具跑一次真实调用 |
| **P1** | 合并 cowatch(6→1) + screenshot(2→1) + 统一键盘输入 | 低-中 | 51→28 |
| **P2** | 电脑控制四件套：click(5→1) + game_control(36 动作→see/act/app/game) | **中**（高频，要逐个验证） | 51→22；`click` 四种 target 形态各测一次 |
| **P3** | 渐进披露：`tools_help` + 低频工具收进「按需」 | 低 | schema 字符 ≤ 14K |

---

## 七、不做什么

- **不删功能**：所有能力保留，只是合并入口
- **不改实现**：底层的 UIA/OCR/模板/坐标路径全部复用
- **不靠 skill**：所有说明都在工具 schema 里（每次请求都带，压缩不丢）

### 8.2 为什么没到 22

剩下的候选是**跨插件强合并**（`web_search` + `open_webpage` → 一个 `web`；`sfx` + `music` → 一个 `audio`）。
它们各只省 1 个工具，但要求插件之间互相调对方的内部方法 —— **破坏插件边界，换来 2 个工具的收益**。

判断：**28 个是合理终点**。真正的收益在「语义清晰」而不是数字：
- 5 种点击 → `act click` **一个入口**（`#3` / `文字:确定` / `图片:按钮` / `500,300` 自路由）
- 6 个「一起看」→ `cowatch` 说得清
- 3 套记忆检索 → `note` / `core_memory` / `recall` 三个语义不重叠

### 8.3 向后兼容

- **所有旧工具名保留在 `executeTool` 的分支里**（技能库/脚本可能直接调）
- 新模型只在 `getTools()` 里看到合并后的名字
- 也就是说：**工具面瘦身，但接口没断**

### 8.4 验证

- `node --check` 全部通过
- 每个插件的自测：`getTools()` 返回 1 个工具 + 正确的 action enum
- **真机调用**（通过 pluginManager）：`see {mode:'windows'}` → 返回 20 个窗口；
  `game {action:'profiles'}` → 返回 minecraft profile；`act {action:'fly'}` → 明确报错
