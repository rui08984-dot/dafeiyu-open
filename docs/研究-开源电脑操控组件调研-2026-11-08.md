## 二、最佳可抄 Top3

### Top 1：yinkaisheng 的 [uiautomation](https://github.com/yinkaisheng/Python-UIAutomation-for-Windows)（Apache-2.0）——「UIA 5.1」路线的现成轮子

**抄什么**：直接放弃手写 pwsh Add-Type UIA（`System.Windows.Automation` 每个属性一次跨进程 COM 调用、无缓存、无等待逻辑、异常处理要自己撸），换 Python `uiautomation` 库（pip 一装，唯一依赖 comtypes，无编译无 GPU——满足"零重量级依赖"）。它给的东西：按 Name/ControlType/Compare 搜索控件、`Exists(timeout)` 等待、树打印工具、Click/SendKeys/Invoke 全套。Windows-MCP 和 Windows-Use 两个 MIT 项目都押在它上面，等于业界已替我们验过货。

**落到哪**：新建 `game_control` 同级的 `uia_control`（桌宠 Python 侧），作为感知+执行的第二通道；`list_windows` 的进程枚举可顺带换成 `auto.GetRootControl().GetChildren()` 拿真实窗口标题。

**最小代码形态**（可直接抄的骨架，~60 行能跑通"枚举树+按 Name 点按钮"）：

```python
import uiautomation as auto

def dump_tree(win, depth=0, max_depth=4):
    if depth > max_depth: return
    rect = win.BoundingRectangle
    print(f"{'  '*depth}[{win.ControlTypeName}] Name={win.Name!r} "
          f"Class={win.ClassName!r} rect=({rect.left},{rect.top},{rect.right},{rect.bottom})")
    for c in win.GetChildren():
        dump_tree(c, depth+1, max_depth)

def click_by_name(window_title, name, extra_names=()):
    win = auto.WindowControl(searchDepth=1, Name=window_title)
    if not win.Exists(3, 1):
        raise LookupError(f"window not found: {window_title}")
    names = (name,) + tuple(extra_names)          # 顺带兼容中英文按钮名
    btn = win.ButtonControl(searchDepth=6,
                            Compare=lambda c, d: c.Name in names)
    if not btn.Exists(2, 1):
        raise LookupError(f"button not found: {name}")
    try:
        btn.Invoke()                               # UIA pattern：不占鼠标
    except Exception:
        btn.Click(simulateMove=False)              # 兜底真点击
    return btn.BoundingRectangle

# 调试：Scripts 里自带 automation.py，一行打树
#   automation.py -t 0 -n     # 当前活动窗口全树
```

**预计实现量**：0.5–1 天（含和 game_control 的"盲发 SendKeys"并联：UIA 命中走 Invoke，未命中退回现有七动作）。注意两点：① 库作者建议管理员权限运行（否则部分窗口枚举不到）；② Electron/Chrome 类应用 a11y 树可能卡——学 Windows-MCP 加"每提供者超时 + 按进程排除"护栏。

### Top 2：Windows-MCP 的 Snapshot 协议形状——给 LLM 的"元素编号菜单"

**抄什么**：不抄它的 MCP 外壳，抄它的接口设计——`Snapshot` 产出 `[id, type, name, rect]` 的可交互元素列表（只收 Button/MenuItem/Edit/CheckBox/ListItem 等"可点类"，过滤装饰节点），LLM 看列表直接回 id，`click(id)` 再用 Top1 的库按 id 定位执行。这正是我们 semantic 语义键位协议的具象版：从"猜键位"升级为"报元素菜单"。全程零视觉模型（Windows-MCP 明确写"works with any LLMs, vision optional"），8090 的 llama.cpp 不用挪窝。

**落到哪**：`semantic` 协议层加一个 `snapshot` 动作（返回元素菜单）和一个 `click_element(id)` 动作；桌宠主循环把元素列表塞进现有 prompt。

**预计实现量**：1 天。核心新增 ~80 行（元素遍历+白名单过滤+id 稳定性：用"控件运行时 id 或 Name+路径"当 key，别用易变的数组下标）。另抄它的两个护栏常量：UIA 单次调用超时 5s、可配置排除进程列表（默认把 occupied 的 Chrome/VSCode 排掉）。

### Top 3：trycua/cua 的执行链优先级——从"盲发"到"pattern 优先、后台投递、SendInput 兜底"

**抄什么**：Cua Windows Driver 的动作分派次序（见其开源[技术博客](https://github.com/trycua/cua/blob/main/blog/inside-windows-computer-use.md)）：先 UIA pattern（Invoke/Toggle/Value/ExpandCollapse，"address the control, not a coordinate"）→ 不行再 `PostMessage` 后台投递（不抢前台焦点，桌宠边干活用户边用电脑）→ 最后才 `SendInput`，且要显式 opt-in 前台模式。我们 game_control 现在是纯"盲发 SendKeys + P/Invoke 坐标"，等于直接跳到最差一档。另可抄它的截图降级链：`PrintWindow`(GDI) → 黑屏（DirectComposition/UWP 窗口）就退 Windows.Graphics.Capture → 再退屏幕区域 `BitBlt` 并标记遮挡——click_text 的截图环节直接受益。

**落到哪**：`game_control` 的 click/type 动作改造：输入目标从"像素坐标"扩展为"窗口标题+控件名"（优先走 Top1 的 Invoke），`SendInput` 保留为显式 fallback；截图函数加 PrintWindow 分支（省去整屏截图，只截目标窗口，还能截被遮挡窗口）。

**预计实现量**：1.5–2 天。PrintWindow 单窗口截图 ~40 行 P/Invoke；动作分派重排 ~100 行。Windows.Graphics.Capture 那档太重（WinRT 互操作），先不做，黑屏窗口留给 OCR 兜底。

## 三、对我们三条现有路线的定位建议

### 路线 1：UIA（现"UIA 5.1"）→ **升级为主感知+执行通道，实现从 pwsh 换成 uiautomation 库**

业界四家主力（UFO²、Windows-MCP、Windows-Use、Cua）2026 年的共识全部是"Accessibility 树优先，视觉兜底"。方向我们本来就押对了，但实现层要换：pwsh `System.Windows.Automation` 的问题是每属性一次跨进程 COM 调用、无缓存、无等待——这正是社区反复吐槽"UIA 慢"的主因（[Stack Overflow 讨论](https://stackoverflow.com/questions/61324436/)下多家结论：慢的是用法和病态应用，不是 UIA 本身）。Cua 的 cache request（一次调用拉整棵子树的 Name/Type/Rect）+ 超时护栏是正确姿势。**注意**：游戏、自绘 UI（DirectX/Qt custom）、部分 Electron 面板没有 a11y 树，这正是其他两条路的存在意义。

### 路线 2：OCR（RapidOCR click_text）→ **保留为兜底，定位收窄**

OCR→点像素中心是所有开源方案里最弱的感知通道（Self-Operating Computer 纯视觉路线的可靠性即是前车之鉴），但它在两种场景不可替代：① 无 a11y 树的自绘/远程/游戏画面；② UIA 树有框无字（图标按钮）。建议收窄为兜底，并加一个零成本增强：UIA 树元素 bounds 与 OCR 文本框做**交叉验证**（文字落在某控件 rect 内→直接 Invoke 那个控件，别点像素中心）。截图环节顺手抄 Top3 的 PrintWindow 单窗口截图。

### 路线 3：VLM grounding（qwen3-vl:8b）→ **从"定位器"改职为"解释器"，SoM 编号法零成本接入**

不建议让 8B VLM 逐像素报坐标（这是 OmniParser/Holo1.5 这类专用 grounding 模型的工作，通用 VLM 干不稳）。改职为：① 看截图回答"哪个编号是 XX"（接 SoM 手法——把 UIA 树元素 rect 画框编号叠图上，VLM 按号选，等效拿到专用 grounding 精度而不加任何模型）；② 任务理解与失败诊断（为什么点错了/弹窗说什么）。若将来真要像素级 grounding，选型是 [Holo1.5-3B](https://huggingface.co/Hcompany/Holo1.5-72B)（4–8GB VRAM，社区流行"3B grounding + 大模型大脑"组合）或 [UI-TARS-1.5-7B](https://github.com/bytedance/ui-tars)（llama.cpp 可跑），而不是 OmniParser（见下）。

### OmniParser / SoM 值不值得上（结论：不整装上，抄思想）

- **重量**：`icon_detect`（YOLO 系，~76MB，**AGPL-3.0 许可**）+ `icon_caption`（微调 Florence-2-base，~0.2B，~230MB），盘上合计 ~320MB；检测单独跑 4GB 级 GPU 即可，带 caption 实操 4–6GB VRAM 起步，CPU 能跑但单图秒级延迟（[模型卡](https://huggingface.co/microsoft/OmniParser-v2.0)、[微软公告](https://www.microsoft.com/en-us/research/articles/omniparser-v2-turning-any-llm-into-a-computer-use-agent)）。
- **对我们的账**：我们有 UIA 树免费拿元素 rect，不需要用 YOLO 重新"发现"元素；VRAM 已被 8090 llama.cpp + qwen3-vl 占用；AGPL 对闭源分发不友好（自用无所谓但要记档）。**判定：不值得整装部署。**
- **值得抄的部分**：①"编号框叠图"的 SoM 手法（上面路线 3）；②"检测"那一步在我们架构里的替代品 = UIA 树（UFO² 的混合检测正是"UIA 优先、OmniParser 只补非标 UI"）。

## 四、给桌宠的合并路线图（一句话版）

```
感知：list_windows(进程) → uia_control 树(主) → click_text OCR(兜底)
执行：UIA Invoke/Toggle/Value(主) → PostMessage 后台(次) → 盲发 SendKeys/SendInput(兜底,显式前台)
语义：semantic 协议接 Snapshot 元素菜单；qwen3-vl 只做 SoM 选号+诊断，不做坐标
护栏：UIA 每提供者 5s 超时 + 病态进程排除表（抄 Windows-MCP）
```
