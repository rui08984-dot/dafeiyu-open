### 1.4 下一步最值得做的 3 条

#### A1（最高优先）把「完成」改成证据判定

- **抄什么**：OpenCode `judge.txt:3` 的「声称不算证据」+ `judge.txt:17-20` 的「疑点判 continue」；dispatch 现有的 `action_sent/effect/suspected_noop` 契约（`dispatch/verify-contract.js:18-24,57-67`）。
- **怎么落**：
  1. `doneWhen` 从自由字符串升级为 `{kind:'oracle', ref:'cmd:<命令>|tool:<工具>|file:<路径>', expect:'exit0|contains:<串>|hash:<sha>'} `；单步 dispatch 任务至少写 `ref:'tool:dispatch.verify'`。
  2. `finishGoal(id, {ok, verified, evidence, steps, llmCalls, wallMs})`：只有 `verified===true` 才允许 `done`；`ok===true && verified!==true` → `paused`，reason=`unverified`，并写 ledger。
  3. `evidence` 至少含 `{kind, ref, at, ok, digest}`；ledger 存 digest，不存正文。
- **判据**：10 个「执行器返回 ok 但实际没做」的故障注入用例，0 个被判 done；10 个真 verify 通过，10 个 done；ledger 100% 有 evidence 引用。

#### A2 分级计划 + 明确的重规划触发点

- **抄什么**：cetana `intentions.py:41-71` 的 cursor/`replace_remaining`、`agent.py:188-215` 的 `max_replans=2` + 先 `advance` 再替换；OpenCode `goal.ts:188-191` 的 stall 计数。
- **怎么落**：
  1. **不要给单步任务假装计划**：`kind:'single'` 保持 1 行；只有 `kind:'multi'`（用户明确的多步目标、或 dispatch 任务预估 >2 步）才生成 3–8 行 plan，每行带 `t2`（外部判据）。
  2. 生成时机：goal 创建时一次 LLM 调用（计入 `maxLlmCalls=1`），或由调用方直接传入 `plan`；失败则退回单行，不阻塞派活。
  3. 重规划只在三个点触发：① 同一行失败 2 次；② 前置条件失效（oracle getter 返回 false / 世界变化使 `done_when` 前提消失）；③ 已用预算 ≥50% 但完成行数 <30%。重规划走 `replaceRemaining(plan, newLines, {expectedRev})`，先 `advance()` 越过失败行，`replans+1`，>2 直接 failed。
  4. `stalls`：同一 `lastError` 连续 3 次或 30min 无进度 → paused，reason=`stalled`。
- **判据**：3 条 3–8 步的长任务，plan 行数 3–8；replan ≤2；文件 hash 证明没有重复副作用；前缀缓存命中 ≥90%（现有 `_probe/cache-probe.cjs` 可复用）。

#### A3 让预算与生命周期成为真值，并且用户看得见

- **抄什么**：Letta CronTask 的 `last_run_outcome/missed_count/failed_count`（`cron-file.ts:66-112`）；OpenCode 的 `WAIT_LIMIT`（`goal.ts:240-264`）与 GUI 状态机（`gui-plugins/src/goal/machine.ts:18-85`）；现有 `speech-budget.request()`（`js/core/speech-budget.js:164`）。
- **怎么落**：
  1. **真实记账**：dispatch 每次心跳/阶段回报 `steps/llmCalls`；`finishGoal` 必须检查 `consume()` 的返回值，`budget_exhausted` 时写 `paused` 而不是 `done/failed`。
  2. **进度看门狗**：goal 增 `lastProgressAt`；dispatch 每次状态变化 touch；30min 无 touch → paused（`reason:'no-progress-30m'`）。
  3. **可见性**：每次状态迁移（started/paused/failed/done/budget）用 `speech-budget` 说一句（≤20 字，例如「那个下载我卡住了，先停一下」）；再加只读 `goal_status` / `goal_cancel` 工具（这是对「不新增工具」硬边界的**有意放宽**，只读+取消，不执行）。
  4. `expiresAt` 要么真的写入（open_loop 7 天），要么删掉这条规则，别留死分支。
- **判据**：模拟挂起任务 31min → 100% paused 且恰好 1 句播报；预算超限 100% 被阻断；`goal_status` p95 <5ms；播报 ≤6 次/小时（不刷屏）。

**多目标优先级（不在 top3，但建议同期做）**：`priority = base(source)`（user 80 / open_loop 60 / dispatch 50 / curiosity 30）`+ deadlineUrgency`（≤24h +30、≤1h +60）`+ aging`（排队每小时 +1，封顶 +20）。判据：3 个不同来源/期限的 goal，启动顺序 3/3 正确；排队 >2h 的 goal 不被饿死。

**最重要的机制差异**：GA 的反思不是「把新增事件压缩成结论」，而是**先选焦点、再检索相关旧记忆、再对着一批相关材料生成洞察**。我们只做了前半段（新增条目）没有后半段（焦点 + 检索），所以模型只能复述卡片。

### 2.4 下一步最值得做的 3 条

#### B1（最高优先）加焦点 + 检索扩展，把「复述」变成「洞察」

- **抄什么**：GA `reflect.py:21-35` 的 focal points（n=3）+ `reflect.py:113` / `retrieve.py:199` 的「每个焦点检索 30 个节点」；GA 的提问方式「high-level insights」。
- **怎么落**：
  1. 从游标后的新条目里，用一次轻量 LLM（或规则：取 importance 最高的 3 条 fact）生成 1–3 个焦点，例如「他最近的工作节奏」「他和家人的关系」。
  2. 每个焦点从 `用户事实 + episodes + insights + 最近对话` 检索 top 10–20（复用 `memory-recall` 的 BM25+向量 RRF，`memory-recall/index.js:799-827`），与新条目一起进 prompt。
  3. 改 prompt：要求每条 insight 必须回答「**变化 / 矛盾 / 预测 / 未解**」之一；禁止纯复述；必须含 ≥1 条本轮新条目作为证据；`depth ≤3`；`importance ≥4`（observation 类可 3）。
  4. 把 `focal_point` 真正写进每条 insight（现在 prompt 的输出格式没要求它，字段基本恒空，`reflect.js:247`）。
- **判据**：人工评 20 条 insight，「非琐碎（包含变化/因果/预测/未解）」≥70%（当前 2/2 琐碎，样本小，先扩到 20）；evidence 覆盖 100%；同主题重复率 <10%。

#### B2 写入端去重/合并 + insight→fact 双闸

- **抄什么**：mem0 的「归一化 + 精确/近精确去重 + linked ids」（`main.py:1022-1026`、`prompts.py:506-516`）；MemOS 的合并字段（`merged_from/importance=max/access_count=sum`，调研 §2.3）；ChatGPT Memory 的「更新 summary 而不是无限追加」。
- **怎么落**：
  1. 文本归一化（去空白/标点、小写）后精确重复 → `occurrences += 1`、`last_seen = now`，不新增。
  2. 2-gram Jaccard ≥0.72 或余弦 ≥0.85 → 合并：保留旧 id，`occurrences+1`、`importance=max`、`evidence_ids` 并集（≤8）、`text` 取更具体的一条；**不要**用 0.95（MemOS 在 184 条上 merged=0，已证明是死阈值）。
  3. 语义冲突（否定/偏好翻转）→ 新 insight + `supersedes: [old]`，旧条 `status:'superseded'`、`superseded_by`。
  4. insight→fact 双闸：`occurrences ≥2` 且跨 ≥2 个不同日期；与 active fact 不冲突；每周 ≤5 条；`source:'reflection'`、`confidence≥0.7`、`evidence_ids` 必填。复用 `persona-layers.js:98-117,126-145` 的跨天/周配额逻辑。
- **判据**：100 对人工标注的 insight 对，合并 precision ≥0.9、recall ≥0.7、F1 ≥0.8；抽 50 条现有 insight 重复率 <10%；`stale_leak=0`（回答里不出现 superseded 内容）；每周 fact 晋升 ≤5。

#### B3 让反思被用上：召回 + 关系时间线 + 金集评测

- **抄什么**：GA thought 参与 retrieve；Graphiti 四时间字段（`edges.py:228-253`）；LongMemEval 的 `recall_any/recall_all/nDCG@k`（`LongMemEval/src/retrieval/eval_utils.py:12-29`）。
- **怎么落**：
  1. `memory-recall` 的 `_rebuild()` 增加 `insights.jsonl` 来源：只索引 `status==='active'`、`importance≥4`、`confidence≥0.6`；来源重要度排在「事实」之后、「对话」之前；每轮最多注入 1 条、≤60 字。
  2. `user-facts` 扩字段：`subject`（默认「用户」）、`predicate`（受控词表：叫/住在/工作于/喜欢/讨厌/养/承诺/关系）、`object`、`recorded_at`、`expired_at`、`evidence_ids`、`episode_ids`；按 `(subject,predicate)` 分组即时间线视图，不建图库。`_promoteEpisodeFacts` 必须把 `ep:<line>:<at>` 写进 `evidence_ids`。
  3. 固定 36 题金集（沿用调研 §2.6 的题型配比：user 8 / preference 5 / temporal 8 / knowledge-update 6 / multi-session 5 / abstention 4），加 `stale_leak=0`、`evidence_coverage=100%` 两个门禁。
- **判据**：金集 `recall_any@5` 比接入前 +5 个点；nDCG@5 不降；20 道时间线题 ≥18 正确；20 条 insight 的证据 20/20 能点回原 episode/fact。

**论文/ADR-009 原案**（我们自己的审计文档）：

- 三层去重：精确 guid/link → 跨源 MinHash LSH（`threshold=0.85, num_perm=64`）→ 同源标题 Jaccard；命中合簇，保留最早一条并记 `also_seen`（`docs/adr/ADR-009-信息流显著性与今日简报.md:23-24`）。
- 打分：`0.45*recency(24h 半衰) + 0.25*sourceWeight + 0.20*interestMatch + 0.10*clusterSize`，最后 MMR（λ=0.7）去冗余（`ADR-009:25-27`）。
- 简报一天一次：08:00 后第一次 `idle≥10min` 触发；输入 top12（≤1200 tokens），输出 ≤200 tokens；存 `今日简报.jsonl`，不进 system（`ADR-009:28-30`）。
- 抓取：串行、8s 超时、200KB 上限、ETag/Last-Modified、失败指数退避 ≤6h（`ADR-009:104`）。
- 反馈：简报条目的「有用/没用」写回 `sourceWeight`（`ADR-009:108`）。

**论文复核（一个诚实的纠正）**：ADR-009 本身没有引用一篇专门的「信息流显著性」论文；它引的是近重复检测（Manku et al., *Detecting near-duplicates for web crawling*, WWW 2007，DOI `10.1145/1242572.1242592`）和 datasketch 的 MinHash LSH 实现。所谓「显著性」5 因子公式是 ADR 自己的启发式，不是论文结论——因此不能拿「论文说」来为 0.45/0.25/0.20/0.10 背书，权重必须用我们自己的 20 条人工排序校准。

MinHash LSH 的本地参考：`_research/world-perception/datasketch`，HEAD `c7eaaeea3f39909f906a9cf8ad4d21a878cb4e07`（2026-10-09），`datasketch/lsh.py:51` 类 `MinHashLSH`。

| 投递语义 | 选中≠送达 | `_maybePush` 直接 `pushed=true` 并写 last（`index.js:797-803`）；`world-extras` 只在 12h 内、且有 LLM 请求时读取（`world-extras:104-119`） | 「已推送」是假账；world-extras 关闭或 12h 无对话，条目已被消费但用户没看到 |
| 反馈闭环 | Feedly/Inoreader 的已读/收藏/board；ADR 的有用/没用回填 | `clickCount` 硬编码 0（`index.js:716`）；`source_trust` 只来自 feeds.json | 权重永不学习；冷启动永远冷启动 |
| 抓取礼貌 | ADR：ETag/Last-Modified/304、8s、200KB、指数退避 | 无 ETag/304；10s 超时；串行；失败只记 lastError，不降频 | 30 源 × 每 45min 全量下载，带宽/限流风险；一个慢源拖住后面所有源 |
| 源健康 | — | 无 `last_ok_at`/连续失败计数/自动停用 | 死源永远在抓，日志噪声 |
| 性能上限 | — | 串行 fetch + 同步正则解析在主线程 | 总 CPU 约 75ms 解析 + 24ms 打分（实测，解析被 30 次 await 分散）；连续阻塞点是 `_scoreAll` 24ms，>20 源/1000 条建议分片或 worker |

### 3.4 下一步最值得做的 3 条

#### C1（最高优先）去重：URL 归一化 + 跨源合簇 + 同窗口 MMR

- **抄什么**：ADR-009 的三层去重（`ADR-009:23-24`）；datasketch `MinHashLSH` 的参数形状（`datasketch/lsh.py:51`）；Feedly 的「deduplicate repetitive news」。
- **怎么落**：
  1. `normalizeUrl()`：小写 host、去 fragment、去 `utm_*/fbclid/gclid/mc_cid` 等追踪参数、保留 path/必要 query；id 用 `sha1(normalized_link)`，guid 优先。
  2. 跨源：标题+摘要做 3-gram shingle，MinHash（`num_perm=64`）banding；阈值 0.85。条目量 ≤500 时也可以直接 pairwise Jaccard（400 条 = 8 万对，JS 几十 ms），**先不引 LSH 服务**。
  3. 同窗口：选完一条后把它的标题加入 `recentTitles` 再选下一条；或直接 MMR（λ=0.7）在候选集上迭代选 top3。
  4. 记录 `cluster_id` / `also_seen`，简报只展示簇的代表条。
  5. 若做簇，显著性可改为 `0.40 recency + 0.20 interest + 0.15 source_trust + 0.10 novelty + 0.15 clusterSize`；权重先用 20 条人工排序校准，不拍脑袋。
- **判据**：固定语料 20 条、5 组重复 → 簇数 15±1；同一头条 10 个源 → 只出 1 条；top3 互不同事件 100%。

#### C2 抓取礼貌 + 反馈闭环

- **抄什么**：ADR-009 的 ETag/304/退避（`ADR-009:104`）；Feedly/Inoreader 的「用户动作回填权重」思路；现有 `speech-budget` 的 accepted/ignored/negative 账本。
- **怎么落**：
  1. `feeds.json` 增 `etag/last_modified/last_ok_at/fail_count/next_retry_at`；请求带 `If-None-Match/If-Modified-Since`；304 直接跳过解析。
  2. 失败退避 1h→2h→4h→6h；成功清零；连续 5 次失败标记 `disabled`（不删除）。
  3. 并发 3–4 个源；单源 10s 超时；整 tick 预算 120s，超时把剩余源留到下轮。
  4. 反馈：`world-extras` 注入世界行时写 `exposed`（item ids + at）；用户追问/点开/说「第 2 条」→ `opened`；下一个窗口仍无互动 → `ignored`。`source_trust = (opened+1)/(exposed+2)` 与 feeds.json 的先验按 0.7/0.3 混合；`interest` 词表按 opened 标题加权。
- **判据**：30 源 24h 下载字节下降 ≥70%；死源 5 个周期内停止抓取；两周后至少 10 个源的 `source_trust` 有 >0.05 的方差；点击率 ≥15%。

#### C3 简报形态与源管理：一天一次 + 世界行/卡片分离 + OPML

- **抄什么**：ADR-009 的「一天一次 + 失败降级」（`ADR-009:28-30`）；Readwise triage 的「先收件箱、再展开」；Feedly/Inoreader/Readwise 的 OPML。
- **怎么落**：
  1. **一天一次**：把 `max_push_per_day` 改成「简报次数」而不是条数；每次简报取 top3–5，不再让第一个窗口吃掉全天配额。或者保留 3 窗口但每窗口只推 1 条。
  2. **世界行只报数量**：`今早有 5 条，要听吗？`（≤20 字）；用户说「听」/「第 2 条」再展开 3 条卡片（标题+源+一句摘要），走 `speech-budget` 的 offer 通道；用户忽略则不重复。
  3. **投递两阶段**：`selected → delivered`；只有 `world-extras` 真正注入/播报后才 `delivered=true`，否则下轮可重试。避免「world-extras 关闭时静默消费」。
  4. **OPML**：支持导入/导出 `<outline xmlUrl>`；导入时逐源抓一次校验，失败源标灰；`doctor` 显示源健康。
  5. 可选：`feeds.json` 增 `mute[]/boost[]` 关键词规则（Inoreader Rules 的最小版）；mute 直接剔除，boost 给 interest +0.1。先不做「标记已读/通知/删除」等复杂动作。
- **判据**：每天主动提及 ≤1 次；用户「听」后的接受率 ≥35%、负反馈 ≤8%；OPML 导入 30 源成功率 ≥90%；死源 100% 被标记。

## 4. 语言 / 性能结论

### 4.1 本机合成基准（2026-11-20，Node 实测）

| 操作 | 实测 | 说明 |
|---|---|---|
| `arbiter.decide()`，4 个 goal × 20,000 次 | 20.5ms → **1.0µs/tick** | 纯函数；30s tick 的 CPU 占比可忽略 |
| `parseFeed()`，197KB RSS（100 条）× 20 次 | 50.7ms → **2.53ms/feed** | 含 CDATA/实体/HTML 剥离 |
| `scoreItem()`，400 条 × 20 个已推送标题 | **23.9ms/轮** | 含中文 2-gram + Jaccard |
| 反思 e2e（3 卡片） | 1702 tokens / **12.9s** | prompt 392 + completion 1310；LLM 占 99.9% |

> 基准脚本为临时 stdin 运行，不落盘；数字是本机单次测量，用于量级判断，不是 benchmark 套件。

### 4.2 三句话结论

- **JS 够**：三个功能的瓶颈都不是 JS 语言本身——arbiter 1µs/tick、RSS 解析 2.5ms/200KB、打分 400 条 24ms；反思 12.9s 是 LLM 延迟。判据：单次同步 CPU <16ms（一帧）且无持续堆增长 → 不换语言；当前唯一接近红线的是「`_scoreAll` 400 条连续 24ms」（>1000 条约 60ms），解法是分片/`worker_threads`，不是 Rust。
- **Rust 现在不需要**：只有满足任一才下沉——(a) 持续解析 >10MB/s 或 >200 个源；(b) 需要 <10ms 定时抖动/系统级 hook；(c) 内存/CPU 成为笔记本电池瓶颈。三个功能都不满足。将来最值得下沉的候选是「RSS 解析 worker」和「本地向量批量相似度」，但先做 worker_threads。
- **Go 现在不需要**：Go 只在「要独立常驻服务」（多源抓取代理、跨进程调度器）时比 Node 划算；我们的架构明确不新增进程/端口（ADR-011 边界），所以不引入。

### 4.3 容量阶梯（RSS 是唯一需要规划容量的）

| 规模 | 结论 |
|---|---|
| ≤50 源、≤1000 条/轮 | 当前 JS 零依赖架构够用；先做 ETag/304，收益最大 |
| 50–200 源，或 >2MB/轮 | 解析/打分进 `worker_threads`；fetch 并发 3–4；仍不需要换语言 |
| >200 源，或 >10MB/轮，或要常驻抓取服务 | 才考虑 Rust 解析器 / Go 抓取代理；且要先改「不新增进程」的架构决策 |

`scoreItem` 随条数近似线性：400 条 24ms（实测）→ 1000 条约 60ms、5000 条约 300ms（外推，未实测）。RSS 的 400 条池在 45min 间隔下没有压力；真正先到上限的是「源数 × 全量下载字节」，不是 CPU。

### 4.4 分功能的具体性能判断

| 功能 | 瓶颈 | 结论 | 如果变慢，先做什么 |
|---|---|---|---|
| A 认知内核 | 无。goals ≤4，tick 30s，状态迁移才写盘 | JS 绰绰有余；不需要 Rust/Go | 若 goals >1000 或 tick <1s，再把 `decide()` 放 worker；仍不需要原生 |
| B 记忆反思 | LLM 延迟 12.9s；completion 1310 tokens 偏多 | JS 解码/append <1ms；优化 prompt 与 `max_tokens`，不是换语言 | 加 `max_tokens`/`response_format`；把 completion 压到 ≤400；8090 embedding 加负缓存（现在服务挂了每轮白等 15s） |
| C RSS | 串行 fetch 的 head-of-line blocking；无 ETag 的重复下载；`_scoreAll` 的连续同步阻塞 | JS 够；解析是逐源 2.5ms（不会一次阻塞 75ms），真正的连续阻塞是 `_scoreAll` 400 条 24ms（>1000 条 60ms） | 先 ETag/304 + 并发 3–4 + 打分分片；>200 源再考虑 worker/原生 |

### 4.5 值得记住的两个「假性能问题」

1. **反思 12.9s 不是 JS 慢**：prompt 392 tokens、completion 1310 tokens；模型在 2 条短 insight 上花了 1310 completion tokens，说明输出冗余/可能带推理文本。先卡 `max_tokens` 和格式，能省 50%+ 成本。
2. **RSS 2.5ms/feed 不是瓶颈**：真正的成本是「每 45min 全量重下 30 个源」。ETag/304 的收益远大于任何解析优化。

## 6. 未核实 / 需实测

1. **Rewind 官网被 Cloudflare 拦截**（2026-11-20），本文只引第三方资料；「连续录屏/录音/可搜索」未在官网逐字核实。
2. **Feedly 文档页 Last updated 2025-10-20**，部分能力可能按套餐分级；本文只核对了功能存在，不核对套餐边界。
3. **Inoreader 只取了 features 总览**，没有逐页读 Rules/Filters 的动作列表；`Rules` 的具体动作（标记已读/星标/通知/删除等）未逐条核实。
4. **OpenCode HEAD 是 2026-11-20 的 2.3.0**，非常新；行号与行为可能随上游变动。本文的机制结论（证据裁判、stall、WAIT_LIMIT、boot 重启）不依赖具体行号。
5. **反思质量样本只有 2 条**（交接 §90.4），不足以统计「琐碎率」；B1 的 20 条人工评审是待做实验，不是已有结论。
6. **RSS 基准是合成 197KB feed**；真实源的 XML 结构、编码、大小差异大，2.53ms/feed 只用于量级判断。
7. **mind-kernel 的「不可达」判断是静态的**：没有启动宿主、没有真实 dispatch 任务；如果将来有别的写入方（例如 open_loop 插件）给 `expiresAt`、`resumeRequested`、`_breaker` 赋值，结论会变。
8. **ChatGPT Memory 的行为按官方 FAQ 转述**；不同套餐/地区/客户端可能有差异。
9. **Motion/Amie 是 SaaS**，功能与措辞会随版本变化；本文只取 2026-11-20 当天页面。
10. **RSS「点击反馈」在桌宠上没有现成 UI**：需要先定义「什么算打开」（用户追问标题、说「第 2 条」、还是点链接），再谈回填；本文给的是可实施的代理信号，不是已验证的点击率。
