## 2. 六问直答

### Q1 流式并行的最小结构：谁决定“现在该听还是该说”

**Moshi 是模型级全双工，没有“谁说”的控制器。**

- Moshi 同时建模两条音频流：一条是用户，一条是 Moshi 自己；外加一条文本流（inner monologue）。`README.md:35-40`。
- 输入是用户音频的 Mimi codes（+ 上一时刻自己产出的 codes），输出同一时间步内的文本 token + 自己的音频 codes；`LMGen.step()` 每次推进一帧，`lm.py:786-792`。
- 编解码：Mimi，24 kHz、12.5 Hz 帧率（80 ms/帧），`loaders.py:82-84`；理论延迟 160 ms（80 ms 帧 + 80 ms 声学延迟），L4 实测可到 200 ms，`README.md:39-40`。
- 客户端同时开 `InputStream` 和 `OutputStream`，`client.py:37-48`；服务端循环 encode→LMGen.step→decode，`run_inference.py:141-176`。
- 因此“边说边听”不是管线调度的结果，而是**模型在同一个自回归步里同时消费用户音频、产出自己音频**；turn-taking 是学出来的，不存在 VAD 抢占或 turn controller。

**Pipecat / LiveKit 是管线级：由 turn controller + interruption policy 决定。**

- Pipecat：`UserTurnController` 汇总 start/stop 策略；默认 start = `[VADUserTurnStartStrategy, TranscriptionUserTurnStartStrategy]`，stop = `TurnAnalyzerUserTurnStopStrategy(LocalSmartTurnAnalyzerV3)`，`turns/user_turn_strategies.py:109-110`。用户 turn 一开始，若 `enable_interruptions` 为真就 `broadcast_interruption()`，`processors/aggregators/llm_response_universal.py:1558-1561`。
- LiveKit：`AudioRecognition` 同时跑 VAD、STT、EOT；`on_vad_inference_done` 里按 `speech_duration >= min_duration` 决定是否 `_interrupt_by_audio_activity()`，`voice/agent_activity.py:2646-2661`。

**我们可用的是管线级，而且比 Pipecat/LiveKit 更“串”。**

- VAD WS 常连，TTS 播放时是否处理 VAD 由 `voice_barge_in` 决定：`js/voice/asr-processor.js:106-118`；打断模式下仍持续向 VAD 送帧，`asr-processor.js:393-411`。
- 但 ASR 是“说完→整段 WAV 上传→离线识别”：`asr-processor.js:435-485`（finishRecording）、`asr-processor.js:523-608`（POST `/v1/upload_audio`）；**没有 partial**。
- TTS 是“文本段→整段合成→整段 blob 播放”：`js/voice/tts-request-handler.js:288-298`（`await response.blob()`）；合成线程与播放线程确实是分开的（`tts-processor.js:149-276` 处理线程、`278-311` 播放线程），所以**段与段之间**并行，但**首段必须等整段合成完**。
- 结论：SenseVoice 与 edge-tts 都是“utterance/clause 级”组件，**不存在模型级双流**；我们能做的是管线级并行（ASR 投机、LLM 预生成、TTS 分块播放），上限受 edge-tts 首包约 1.2 s（`edge-tts/tts_server.py:13`）约束。具体差在：Moshi 的输入流是用户音频的**连续 Mimi codes**，输出流在**同一个自回归 step** 生成自己的 codes（`lm.py:786-792`）；SenseVoice 的输入是**整段 WAV**、输出一次性文本（`asr-processor.js:523-608`），edge-tts 的输入是**完整分句文本**、输出音频（`tts_server.py:240-263`），两者之间没有共享的流式状态，所以“边说边听”只能靠调度错峰，不能靠联合建模。

| 能力 | 模型级（Moshi） | 管线级（Pipecat/LiveKit） | 我们现状 |
|---|---|---|---|
| 同时听+说 | 模型内双音频流，原生 | VAD 持续收音 + 打断策略 | 收音持续，但 ASR 不产 partial |
| 谁决定轮次 | 模型学出来 | TurnController / EOT 模型 | 固定静音窗口 + 260 ms 犹豫期 |
| 首响现状 | 160–200 ms（论文/README） | 取决于 VAD/STT/LLM/TTS 串联 | 首音日志口径 3.17–6.59 s（代码内实测注释）；端到端再加约 3 s |
| 换声线/换引擎 | 必须用 Moshi 声线 | 可插拔 | 硬约束：edge-tts 不动 |

### Q2 turn detection：VAD-only vs 语义 vs 混合

**Pipecat：默认是“VAD 起点 + 语义 EOT 终点”的混合。**

- VAD 参数默认：confidence 0.7、start 0.2 s、stop 0.2 s、min_volume 0.6，`audio/vad/vad_analyzer.py:25-28`。
- VAD 一报 start 就开 turn：`turns/user_start/vad_user_turn_start_strategy.py:27-28`。
- VAD 报 stop 时调用 EOT 模型：`turns/user_stop/turn_analyzer_user_turn_stop_strategy.py:235`；模型返回 COMPLETE 才结束，INCOMPLETE 就继续等。
- 本地 EOT 模型是打包的 ONNX `smart-turn-v3.2-cpu.onnx`（Whisper log-mel 特征、16 kHz），`audio/turn/smart_turn/local_smart_turn_v3.py:28-60`；参数 `stop_secs=3` 只是“最长静音硬上限”，`audio/turn/smart_turn/base_smart_turn.py:27-29`，达到 3 s 静音才无条件 COMPLETE，`base_smart_turn.py:133-138`。
- 纯超时兜底策略是 `SpeechTimeoutUserTurnStopStrategy(user_speech_timeout=0.6)`，`turns/user_stop/speech_timeout_user_turn_stop_strategy.py:49-55`。

**LiveKit：默认是“VAD + 语义 EOT + min/max endpointing”的混合。**

- Silero VAD 默认：`min_speech_duration=0.05`、`min_silence_duration=0.55`、`prefix_padding_duration=0.5`、`activation_threshold=0.5`，`livekit-plugins/livekit-plugins-silero/livekit/plugins/silero/vad.py:63-67`。
- endpointing 默认 `min_delay=0.5 s`、`max_delay=3.0 s`，`voice/turn.py:138-143`；流式模式 0.3/2.5，`turn.py:145-150`。
- 真实决策链：VAD EOS 后先等 `min_delay`（`voice/audio_recognition.py:1673`），跑 EOT 模型；若 `P(EOT) < unlikely_threshold`，判为“还没说完”，把等待延到 `max_delay`（`audio_recognition.py:1758-1764`），然后 sleep 到该延迟（`audio_recognition.py:1891-1899`）。
- EOT 模型推理要求至少 200 ms VAD 静音，单次预测超时 1.0 s，`livekit-agents/livekit/agents/inference/eot/base.py:33-38`；turn-detector 插件是 `livekit/turn-detector` 的 q8 ONNX，按语言取阈值，`livekit-plugins/livekit-plugins-turn-detector/livekit/plugins/turn_detector/models.py:6-9` 与 `livekit-plugins/livekit-plugins-turn-detector/livekit/plugins/turn_detector/base.py:240-258`。

**TEN：VAD 阈值 0.5、静音 1000 ms、hop 16 ms；另有文本语义 turn detector（Wait/Finished），强制兜底 5000 ms。**

- `ai_agents/agents/ten_packages/extension/ten_vad_python/config.py:6-8`。
- `ai_agents/agents/ten_packages/extension/ten_turn_detection/config.py:7,11`；判定与强制兜底 `ai_agents/agents/ten_packages/extension/ten_turn_detection/extension.py:126-176`。

**我们缺什么：**

1. 只有 Silero VAD（threshold 0.5、min_silence 0.25 s、min_speech 0.15 s，`asr/asr_server.py:102-104`），没有语义/韵律 EOT。
2. 客户端在服务端 250 ms 静音之后又叠加 500 ms 定时器（`js/voice/asr-processor.js:57,214-239`），endpointing 实际约 750 ms，且是“双重计时”。
3. 没有 partial transcript，无法用“文本是否成句”辅助判断。
4. 没有 backchannel（“嗯/啊”）抑制；只有固定 260 ms 犹豫期 + `gap < 200 ms` 的粗糙判据（`asr-processor.js:156-175`）。该判据可能恒不成立，见 Q4 末尾的静态读码疑点。

#### 500 ms 目标的现实瓶颈

1. **可纯靠参数/管线省掉的：合并窗口 2.0 s + 客户端二次静音 0.5 s ≈ 2.5 s。** 这是当前最大、最便宜的一块。
2. **省不掉的地板：edge-tts 首包约 1.2 s + LLM TTFT 0.6–1.2 s ≈ 1.8–2.4 s。** 在不换 TTS、不换 ASR 的硬约束下，**“用户说完→第一句语义音频”不可能做到 500 ms**。
3. 500 ms 只能定义为“第一声可听反馈”（语气词、呼吸、短确认），由本地预置音频或极短 filler 在 VAD EOS 时立即播放；语义首响的现实目标应设为 p50 ≤ 1.5 s、p90 ≤ 2.2 s（在完成第 5 节改造 1–2 后）。
4. 若要做“边说边听”的语义级并行，唯一路径是**投机 ASR + 预生成 LLM**：在用户还没说完时用 SenseVoice 反复解码最近 3–4 s，文本稳定就先把 LLM 请求发出去；最终文本不同再取消重发。这把 LLM TTFT 移出关键路径，但 TTS 仍从“拿到最终文本”才开始，1.2 s 首包无法绕过。

### Q4 barge-in / 打断：检测到用户说话后怎么取消 TTS、清队列、保留文本

**Pipecat（帧广播模型）：**

- 用户 turn 一开始，立即 `broadcast_interruption()`（可配置 `enable_interruptions`），`processors/aggregators/llm_response_universal.py:1558-1561`。
- TTS 服务收到 `InterruptionFrame`：丢弃所有 `interruptible` 的音频上下文，保留 `uninterruptible`（如工具播报）；重置聚合器与词时间戳，`services/tts_service.py:1548-1600`。
- 输出传输层：保持音频任务运行，但清空所有可打断帧的播放缓冲；已写入设备的当前块保留，`transports/base_output.py:609-640`。
- 保留已生成文本：`InterruptionFrame` 是系统帧，会插队到已排队的文本帧之前；实现上再排一个 `_AssistantTurnInterruptedFrame` 到这些文本帧之后，确保“用户已经听到的那些词”先进入上下文再关闭本轮，`llm_response_universal.py:2240-2263`。

**LiveKit（对象生命周期模型）：**

- `interrupt()`：取消预生成、当前 speech、后台 speech、队列中 speech（按优先级排序，遇到不可打断的就停），`voice/agent_activity.py:1980-2037`。
- 音频活动打断：`min_duration` 门槛（默认 0.5 s）通过才触发；`_interrupt_by_audio_activity()` 调 `speech.interrupt(source="audio_activity")`，`agent_activity.py:2506-2573`。
- 假打断恢复：默认先 `audio_output.pause()` 而不是销毁队列；若用户在 `false_interruption_timeout=2.0 s` 内没继续说，`_restore_paused_speech_state()` 恢复播放，`agent_activity.py:2553-2566,5196-5208,5266-5281`；`voice/turn.py:193-201`。
- 文本保留：speech 句柄被标记 interrupted，但已经产出的 chat message 留在上下文里（`SpeechHandle` + `_record_interruption`，`agent_activity.py:252-260`）。

**TEN：**

- `_interrupt()` 清空当前句缓冲、`agent.flush_llm()`、向 TTS 发 `tts_flush`、向 RTC 发 `flush`，`examples/voice-assistant/tenapp/ten_packages/extension/main_jev_python/extension.py:388-398`。
- 触发条件不是固定延时，而是“ASR 文本 final 或长度 >2”，`extension.py:162-172,195-198`。

**我们当前：**

- VAD 检测到人声 → 260 ms 犹豫 → 若 `gap < 200 ms` 判真打断 → `ttsProcessor.interrupt()`，`js/voice/asr-processor.js:156-175`。
- `interrupt()` 做六件事：发 `TTS_INTERRUPTED` 事件、`shouldStop=true`、`abortGeneration++`、`abortAllRequests()`、`playbackEngine.stop()`、清空 `textSegmentQueue/audioDataQueue/_fallbackQueue`，`js/voice/tts-processor.js:553-607`。
- `playbackEngine.stop()` 直接 `pause()` + `src=""`，不可恢复，`js/voice/tts-playback-engine.js:509-537`。
- 保留文本：只留最后 60 字到 `__petInterruptedText`（`tts-processor.js:558-559`），并用 `_pendingInterruptNote` 提示 LLM “你上一句没说完就被打断”（`js/ai/llm-handler.js:264`）。**没有把“用户实际听到了哪些词”写回上下文**，也没有“不可打断段”概念。
- 缺的三件事：pause/resume 假打断恢复、按段可打断/不可打断、已播出文本的精确入账。
- **静态读码发现的疑点（需实测确认）**：服务端只在 VAD 状态变化时发消息（`asr/asr_server.py:404-405`，`VadSession.feed` 返回 `changed` 才发），而客户端的 `lastSpeechTime` 只在 `handleSpeech()` 里更新（`asr-processor.js:192`）。也就是说它记录的是“开口时刻”，不是“最后一帧人声”。260 ms 后做 `gap = now - lastSpeechTime < 200` 判断时，gap 至少是 260 ms，**正常说话也会被判成“只是附和”**。这条语音抢话路径很可能从未真正触发；现有“能被打断”来自 PTT（`asr-processor.js:698-707`）、快捷键（`js/ipc-handlers.js:34-40`、`js/shortcut-manager.js:38-41`）以及“新请求开始时先停旧 TTS”（`js/ai/llm-handler.js:249-254`）。修复不需要换模型：让服务端在 `is_speech:true` 期间每 200 ms 补发一次 `speech_activity`（Pipecat 已有同款机制：`pipecat/src/pipecat/audio/vad/vad_controller.py:69-74,225-230`），客户端收到就刷新 `lastSpeechTime`。

### Q5 最小改造路径（不换 TTS、不换 ASR）

按“收益/成本”排序。成本按改动面估，收益按当前 p50 估算；所有改动都只动宿主 JS 管线，不碰 `asr_server.py` 的模型与 `tts_server.py` 的引擎。

#### 改造 1（最高优先）：拆掉“双重静音 + 2 s 合并窗口”

- 改哪里：
  1. `_incoming/my-neuro/live-2d/js/voice/asr-processor.js:57`：`SILENCE_THRESHOLD` 500 → 120–150 ms（服务端已经有 250 ms 静音判定，客户端这层是重复计时）。
  2. `_incoming/my-neuro/live-2d/js/ai/conversation/ASRController.js:72`：`merge_window_ms` 默认 2000 → 250–300 ms；或者改成“检测到新语音/新 VAD start 才续窗”，而不是无条件等 2 s。
- 怎么量首响：用第 5 节的 T0→T2→T3 打点，改造前后各采 30 轮，比较 `endpointing_ms + asr_ms + merge_ms` 的 p50/p90。
- 预期收益：**−2.05 至 −2.5 s**（二次静音 0.35–0.5 s + 合并窗口 1.7–2.0 s；其中 500→120–150 ms 这一段最多省 0.38 s，要到 0.5 s 需把客户端静音降到 0——审计 H-07 已修正算术）。风险：语速慢/停顿多的用户可能被切句；用“VAD 再次 start 时取消提交并续接”兜底。

#### 改造 2：首段真流式播放，不再等整段 blob

- 改哪里：`_incoming/my-neuro/live-2d/js/voice/tts-request-handler.js:288-298`：把 `await response.blob()` 改成读 `response.body.getReader()`，把 MP3 字节块通过 `MediaSource`（或 Web Audio 的 `AudioBufferSourceNode` 队列）交给 `tts-playback-engine.js`；服务端已经是边合成边写（`edge-tts/tts_server.py:257`），无需改引擎。
- 怎么量首响：在 `fetch` 返回后记录 `response.headers` 到达时间（T5.5）与第一个 `reader.read()` 的 chunk 时间（T6），再记 `onplay`（T7，现有 `lastPlayStartedAt`）；指标 `tts_ttfb_ms = T6 - T5`、`playout_ms = T7 - T6`。
- 预期收益：首段不再等整段合成，**−0.3 至 −0.8 s**（首段 4–14 字，整段合成 1.2–2.0 s，首块通常早得多；具体值需实测）。风险：MediaSource 对 MP3 分块的兼容性、播放引擎从 `<audio src=blob>` 改造的回归面；可先只对首段启用，后续段维持现状。
- 注意：这一步不会突破 edge-tts 首包约 1.2 s 的地板，只是把“首包之后还在合成”的时间从首响里拿掉。

#### 改造 3：在 VAD 停点加本地语义 EOT，替代固定静音

- 改哪里：在 `asr/asr_server.py` 的 Python 进程内新增一个本地 ONNX 推理入口（复用已有 16 kHz 音频帧），模型用 Pipecat 打包的 `smart-turn-v3.2-cpu.onnx`（`pipecat/src/pipecat/audio/turn/smart_turn/local_smart_turn_v3.py:28-60`），在 VAD `is_speech:false` 时对最近 ≤8 s 音频判“说完了吗”；宿主侧把 `asr-processor.js` 的固定 500 ms 改成“先等 150 ms，EOT=complete 立即提交，EOT=incomplete 延长到 1.2–1.5 s 上限”。
- 怎么量首响：`endpointing_ms = T_submit - T_last_speech`，同时记“误切率”（用户在下一次 VAD start 前 1 s 内补充说话的比例）与“假等待率”（EOT=incomplete 但用户其实已说完）。
- 预期收益：endpointing 从约 750 ms 降到 250–400 ms，**−0.35 至 −0.5 s**；更大的价值是允许把静音窗口调得更短而不误切，给改造 1 兜底。成本：新增 ONNX 模型与一次推理（CPU 单线程，量级几十 ms），需要标定中文阈值；模型许可需单独确认（Pipecat 代码 BSD-2，模型权重随包分发，未在 repo 内声明单独许可）。

#### 可选第 4 条（成本高，第二阶段）：投机 ASR + LLM 预生成

- 在用户说话期间每 400–600 ms 用 SenseVoice 解码最近 3–4 s（RTF 0.082，成本可接受），连续两次文本稳定就发 LLM；最终文本不同则取消并重发，模式照抄 LiveKit 的 `_preemptive_generation`（`voice/agent_activity.py:2766-2836,3082-3105`）。
- 预期收益：把 LLM TTFT（0.6–1.2 s）移出“说完之后”的关键路径，语义首响可再降 0.5–1.0 s；代价是 ASR 重复计算、请求取消逻辑、以及“预生成答案与最终问题不一致”的对话一致性风险。

### Q6 明确否掉的方案

见第 4 节表格；核心结论：

- **Moshi 端到端**：模型级全双工确实能到 160–200 ms，但 7B 参数、需 GPU 常驻（README 的实测延迟以 L4 为基准），repo 未提供中文权重/中文对话能力说明，声线固定，且与 edge-tts 硬约束冲突；桌面外放还会形成“自己声音被麦克风收回去”的回授，需要 AEC，成本远超收益。
- **TEN 全量框架**：许可附加条款限制“不得部署在终端用户设备上”（`LICENSE:9-16`），而我们是 Windows 桌面端；且 438 MB、graph/extension 模型要求重写宿主插件体系。
- **LiveKit Agents 全套**：需要 LiveKit room/WebRTC 服务与云端 EOT；官方模型是 proprietary（`MODEL_LICENSE:1-5`），本地单进程桌宠引入媒体服务器属于架构倒置。
- **Pipecat 全套**：Python 服务 + WebRTC transport，同样要重写宿主；但其单文件机制（smart-turn、interruption 策略、TTFB 指标）可选择性移植（BSD-2，保留版权声明即可）。

## 5. 首响基线怎么量（可执行的最小测量方案）

目标：把“用户说完 → 第一声可听”拆成 7 个点，先量出现状，再逐项验证改造。**不改生产代码**，用 DevTools 运行时 monkey-patch + 现有字段。

### 5.1 打点定义

统一用 `Date.now()`（现有 `lastPlayStartedAt`、`__petInterruptedAt` 都是 Date.now，避免 `performance.now()` 混用）。

| 点 | 含义 | 打点位置（现有代码） |
|---|---|---|
| T0 | 服务端判定“用户说完”（VAD EOS，已含 250 ms 静音） | `js/voice/asr-processor.js:102-118` 收到 `{type:"vad", is_speech:false}` 时 |
| T0s | 用户最后一个语音帧（真实说完时刻） | **当前拿不到**：`lastSpeechTime` 是“开口时刻”而非“最后一帧”（`asr-processor.js:192`，服务端只发状态变化 `asr/asr_server.py:404-405`）。基线先用 T0 代替，真实 EOS ≈ T0 − 0.25 s（服务端静音窗口） |
| T1 | 客户端开始收尾录音 | `ASRProcessor.prototype.finishRecording` 入口（`asr-processor.js:435`） |
| T2 | ASR 文本返回 | `ASRProcessor.processRecording` 返回点（`asr-processor.js:523-608`）或 `ASRController` 的 `onSpeechRecognized` 回调（`ASRController.js:111`） |
| T3 | 提交给 LLM（合并窗口结束） | `inputRouter.handleVoiceInput` 调用点（`ASRController.js:99`）或 `llm-handler` 的 `_lat.sendAt`（`llm-handler.js:572`） |
| T4 | 首个 LLM token | `llm-handler.js:585-590`（`_lat.firstTokenAt`） |
| T5 | 首个 TTS 文本段入队 | `tts-processor.js:427`（`_firstSegmentAt`） |
| T6 | TTS 首字节到达客户端 | `fetch` 到 9883 后 `response.headers` / 首个 `reader.read()`（需在诊断脚本里包一层 `window.fetch`） |
| T7 | 真正出声 | `tts-playback-engine.js:356-358`（`onplay` 里设 `lastPlayStartedAt`） |

### 5.2 指标定义

- `endpointing_ms = T1 - T0`（客户端视角：500 ms 二次静音；若要“从真实说完起算”，再加服务端 250 ms）
- `asr_ms = T2 - T1`
- `merge_ms = T3 - T2`
- `llm_ttft_ms = T4 - T3`
- `seg_ms = T5 - T4`（首段成段等待）
- `tts_ttfb_ms = T6 - T5`
- `playout_ms = T7 - T6`
- **首响（可听）`first_audible_ms = T7 - T0`**（加 250 ms 即“从真实说完起算”）
- **首响（语义）`first_semantic_ms`**：若首段是垫场，需要额外标记；当前没有字段，建议在诊断脚本里按文本匹配 `FILLER_POOL`（`latency-filler.js:33-35`）区分。
- 误切率：一次 turn 内出现第二次 `VAD is_speech:true` 且距离 T0 < 1 s 的比例。

### 5.3 采样与判定

- 每个场景 30 轮：短句（≤6 字）、中句（7–20 字）、长句（>20 字，含自然停顿）各 10 轮。
- 报 p50 / p90 / max，不报均值（延迟分布长尾，均值会骗人）。
- 基线判据：
  - 首音日志口径现状应为 3.2–6.6 s（与 `tts-request-handler.js:106` 的注释一致）；端到端（T0 起算）预期 6–9.6 s（再加 endpointing 0.5 s + ASR 0.3–0.5 s + merge 2.0 s），以实测为准；
  - 改造 1 后 p50 应下降 1.7–2.3 s；
  - 改造 1+2 后 p50 应 ≤ 2.5 s；
  - 改造 1+2+3 后 p50 应 ≤ 2.0 s，语义首响 p90 ≤ 2.2 s。
- 反作弊：不要用“`⏱️ 首音` 日志”单独当基线，它的起点是 LLM 请求（`llm-handler.js:570`），天然漏掉 endpointing + ASR + merge；必须从 T0（客户端收到 VAD EOS）起算，若要“真实说完”口径再加服务端 250 ms 静音窗口。

### 5.4 DevTools 诊断脚本（非生产，粘贴即用）

在桌宠窗口 DevTools 里执行；只包现有函数、不改文件。字段挂在 `window.__voiceLat`，每轮 `console.log` 一行 JSON。

```js
(() => {
  const L = window.__voiceLat = window.__voiceLat || { turns: [] };
  const vc = window.voiceChat;
  const ap = vc && vc.asrProcessor;
  const tp = vc && vc.ttsProcessor;
  if (!ap || !tp || !ap.ws) return 'voiceChat not ready';

  const mark = (k) => { if (L.cur) L.cur[k] = Date.now(); };

  // T0：VAD EOS（服务端 is_speech=false）
  const origOnMsg = ap.ws.onmessage;
  ap.ws.onmessage = (ev) => {
    try {
      const d = JSON.parse(ev.data);
      if (d.type === 'vad' && d.is_speech === false) {
        L.cur = { t0: Date.now() };
      } else if (d.type === 'vad' && d.is_speech === true) {
        // 误切统计：一次 turn 内 1s 内再次开口
        if (L.cur && L.cur.t0 && Date.now() - L.cur.t0 < 1000) L.cur.reopened = 1;
      }
    } catch (_) {}
    return origOnMsg && origOnMsg.call(ap.ws, ev);
  };

  // T1：开始收尾录音
  const origFinish = ap.finishRecording.bind(ap);
  ap.finishRecording = async (...a) => { mark('t1'); return origFinish(...a); };

  // T2：ASR 文本返回（包 processRecording 的返回值，比 onSpeechRecognized 更稳）
  const origRec = ap.processRecording.bind(ap);
  ap.processRecording = async (...a) => { const r = await origRec(...a); mark('t2'); return r; };

  // T3：提交 LLM（合并窗口结束）
  const ir = vc.inputRouter;
  if (ir) {
    const origHandle = ir.handleVoiceInput.bind(ir);
    ir.handleVoiceInput = async (...a) => {
      mark('t3');
      return origHandle(...a);
    };
  }

  // T7：真正出声（任何一段音频的 playing 事件；首段即首响）
  if (!L._playPatched) {
    L._playPatched = true;
    const origPlay = HTMLMediaElement.prototype.play;
```

## 6. 未解问题 / 需实测的假设

1. **edge-tts 单句首包到底多快？** `tts_server.py:13` 写“约 1.2 s”，但没有区分 4 字/14 字/34 字。需实测：对 4/8/14/34 字中文各发 20 次 `/tts`，记 `response.headers` 与首块时间。假设：首包主要花在握手，短句不会显著更快；若成立，改造 2 的收益上限就是“整段合成时长 − 首包”，而不是“首包变短”。
2. **客户端 500 ms 二次静音是否真的必要？** 服务端已经有 250 ms 静音；如果去掉客户端计时后误切率没有上升，改造 1 可直接省 0.5 s。需 A/B 30 轮。
3. **`merge_window_ms=2000` 的真实动机**：是为了“卡壳续说”，还是历史遗留？如果多数用户不会在 2 s 内续说，应改成“VAD 再 start 才续接”，而不是固定 2 s。需统计 `onSpeechRecognized` 之后 2 s 内再次 VAD start 的比例。
4. **smart-turn v3 对中文的效果**：模型卡未在 repo 内说明训练语种；需用我们的中文语音样本（`语音样本/`）标定阈值与误切率。若中文效果差，退回“VAD + 短固定窗口 + 文本长度”的混合规则。
5. **SenseVoice 投机解码的成本**：每 500 ms 解码最近 3–4 s，2 线程 int8 的 CPU 占用与发热是否可接受；需在真实桌宠进程里测 RTF 与 CPU。
6. **流式 MP3 播放的兼容性**：Electron/Chromium 的 `MediaSource` 对无 `Content-Length` 的 chunked MP3 支持是否稳定；若不稳，退回 Web Audio 队列（每块 `decodeAudioData` 可能有 gap，需要预排）。
7. **“首响 <500 ms”到底指什么**：是“任何可听声”还是“第一句语义回复”？两者差一个数量级。建议产品口径拆成 `ack_ms`（目标 <300 ms，用预置语气词/呼吸）与 `semantic_ms`（目标 p50 ≤1.5 s），否则 500 ms 会被误读为“语义回复 500 ms”，在当前硬约束下不可达。
8. **打断后“已听到文本”如何精确入账**：`playbackEngine.displayedText` 是显示进度，不等于音频已播完的词；需要词级时间戳或按段粒度入账。Pipecat 的做法（系统帧插队 + 已排队文本先入上下文，`llm_response_universal.py:2240-2263`）可作参考，但我们没有词级时间戳。
9. **许可风险**：Pipecat 的 smart-turn 模型权重是否允许随桌面应用分发、LiveKit 的 `MODEL_LICENSE` 是否允许本地离线使用，需在落地前单独确认；本文只确认了代码仓库 LICENSE，未替模型权重做法律判断。
