# 竞品调研：别人是怎么做的（2026-11-07）

调研方式：GitHub README / 官方文档 / 公开架构分析文章（WebSearch + WebFetch + GitHub API）。
基准：我们「大肥鱼桌宠」= Live2D 皮套 + 真情绪引擎 + 记忆 + 一起看 + 游戏直控 + 主播陪玩 OCR 解说 + TTS 情绪韵律。
原则：查不到的写「未查到」，不编造。

## 1. Open-LLM-VTuber（14.6k★，MIT）— 最接近我们的开源竞品

Python 后端 + Web 前端 + 桌面客户端，定位「离线 AI 伴侣 / 虚拟主播」，为在非 Windows 平台复刻 neuro-sama 而生。

| 维度 | 做法 |
|---|---|
| 直播对接 | **内置 BiliBili 直播客户端接收弹幕互动**（官方文档确认）；其他平台可自建接口接入 |
| 游戏陪玩 | 无 |
| 表情动作 | Live2D Cubism 5，表情由后端控制；点击/触摸互动；「AI 内心 OS」：表情、想法、动作**可见但不朗读** |
| 记忆/人设 | 长期记忆基于 **Letta**；聊天记录持久化、可切换历史会话；自定义 Agent 可换 Mem0/HumeAI EVI |
| TTS | MeloTTS / GPT-SoVITS / CosyVoice / Fish Audio / Edge TTS / Azure / sherpa-onnx 等；支持音色克隆、**TTS 翻译**（中文聊天日语声线）；**语音打断**（AI 听不到自己的声音，不用戴耳机） |
| 其他 | 视觉感知（摄像头/录屏/截图）、MCP 工具调用、群组聊天（多 AI 角色）、AI 主动说话、桌宠模式（透明+置顶+鼠标穿透） |

做得好的：
1. **桌宠模式三件套**（透明背景/全局置顶/鼠标点击穿透）做得最成熟。
2. **AI 内心 OS**——表情动作想法走「可见不朗读」通道，解决了"AI 自言自语很吵"的问题。
3. 记忆直接接 Letta 现成方案，打断、主动说话等对话体验细节全。

它没做的：游戏陪玩、唱歌、直播运营玩法（礼物/SC/积分）、主播 OCR 解说（只有屏幕感知用于聊天）。
许可：MIT（但自带 Live2D 示例模型归 Live2D Inc. Free Material License，商用单独授权）。

来源：https://github.com/Open-LLM-VTuber/Open-LLM-VTuber · https://docs.llmvtuber.com/docs/intro

## 2. Ikaros-521/AI-Vtuber「Luna」（4.6k★，GPL-3.0 + README 声明商用抽成 10%）

B 站向直播虚拟主播，功能以弹幕互动为核心。

| 维度 | 做法 |
|---|---|
| 直播对接 | **B 站直连：blivedm 库（已内置 vendor/）+ bilibili-api-python**；其他平台走「直播弹幕监听助手」油猴脚本，WebSocket 推送到 127.0.0.1:5001；支持 B站/抖音/快手/视频号/斗鱼/淘宝/YouTube/Twitch/TikTok 等 11 平台 |
| 唱歌/点歌 | **弹幕点歌模式：匹配本地歌曲库，支持中途取消，点歌与聊天并行**（弹幕进队列不阻塞）；so-vits-svc / DDSP-SVC 做变声/翻唱 |
| 表情动作 | 皮套支持 Live2D / VTube Studio / UE5+Audio2Face / xuniren / MuseTalk / Sadtalker 等 |
| 记忆/人设 | **未查到**长期记忆机制（仅本地问答库 + chat_with_file 文档问答） |
| LLM/TTS | LLM 30+ 家（GPT/Claude/Gemini/智谱/千问/Kimi/Ollama/Dify/火山…）；TTS 15+（Edge/VITS/ElevenLabs/GPT-SoVITS/ChatTTS/CosyVoice/F5-TTS…） |
| 游戏陪玩 | 无（仅 pyautogui 桌面自动化依赖）；另有 Gemini/glm-4v 看电脑画面分析讲解、SD 协同作画 |

做得好的：
1. **弹幕接入工程化**——blivedm 直连 + 油猴脚本中转的多平台方案，礼物/弹幕/点赞事件分型处理。
2. **点歌流水线**（弹幕→曲库匹配→svc 变声演唱→弹幕聊天队列不中断）。
3. 工程质量：uv 锁定、pytest + CI + 冒烟测试，功能按 core/llm/tts/asr/platform/visual 分组。

它没做的：长期记忆、游戏陪玩、桌宠形态。
许可：**GPL-3.0 + 商用抽成 10% 条款**——代码只能看设计不能抄实现。

来源：https://github.com/Ikaros-521/AI-Vtuber · 文档 https://ikaros521.eu.org/site

## 3. Neuro-sama（闭源，看公开分析 + 官方 SDK 逆向其做法）

| 维度 | 做法（可考证部分） |
|---|---|
| 组成 | 模块化流水线：自托管微调 LLM（参数量/量化为社区传言，未证实）+ Azure TTS「Ashley」声线**音调上移 25%** + Live2D（画师 Anny）+ STT（连麦用）+ **独立唱歌 AI 模型** |
| 游戏陪玩 | **分层代理：LLM 不碰底层输入**。官方 **Neuro SDK**（WebSocket 三原语：Context 游戏发状态文本 / Registered actions 游戏声明动作+JSON schema / Forced actions 限定只选一个）；游戏侧集成 Slay the Spire 2 / Inscryption（Harmony 补丁钩事件）/ Buckshot Roulette / Hollow Knight / Cyberpunk 2077（LLM 只给意图，Redscript 注入按键）/ Pokémon Platinum；另有 CV 把游戏画面转结构化文本；**回合制游戏效果最好，高 APM 只控高层动作** |
| 记忆 | 仅会话内上下文；疑似 RAG；Vedal 自认记忆是难题；人格走**权重路线**：部署→收集转录→人工筛选→离线微调（疑似 LoRA）→重部署，无在线学习 |
| 直播互动 | 读 Twitch 弹幕；2023 年不当言论后加强黑名单审核过滤 |
| 延迟 | 自托管 GPU，目标 1–3 秒响应（直播可用的底线） |

做得好的（最值得抄）：
1. **Neuro SDK 把「游戏陪玩」定义成协议而非逐游戏硬写**——游戏方按 schema 声明动作，AI 只做选择。官方 Unity/Godot SDK + Rust/JS/Python/Lua/Ren'Py 等 10+ 社区 SDK，889★。
2. 意图与执行分离（LLM 选高层动作，寻路/小游戏求解器/游戏内置系统兜底）。
3. 唱歌与说话完全分离成两个模型。

它没做的：持久记忆（未证实）、桌宠形态、B 站。

来源：https://github.com/VedalAI/neuro-sdk（含各游戏集成仓库链接）· 架构分析 https://lin-guanguo.github.io/llm-memory-research/neuro-sama.research · https://vedal.ai

## 4. kimjammer/Neuro（2.1k★，MIT）— 消费级硬件能跑的 Neuro 复刻，架构参考价值最高

7 天写成的全本地 Neuro-sama：RTX 4070 12GB 即可复现。

| 维度 | 做法 |
|---|---|
| 管线 | **RealtimeSTT**（faster-whisper tiny.en，边说边转写）→ text-generation-webui + Llama3 8B EXL2 4bpw → **RealtimeTTS**（XTTSv2 + DeepSpeed，**边生成边播**）→ **虚拟声卡进 VTube Studio 做口型** |
| 直播对接 | pyTwitchAPI 读 Twitch 弹幕；OBS 接 VTube Studio 画面（Spout2） |
| 记忆 | **RAG：对话过程中自动生成长期记忆**（跨重启持久），可手动添加 |
| 视觉 | 自动截图 + 多模态模型（MiniCPM-V int4，8GB VRAM） |
| 架构 | 单 signals 对象全局共享状态；每个模块独立线程独立事件循环；**prompter.py 集中决策何时提示 LLM**（人类在说话吗/AI 在想吗/新弹幕/静默多久）；模块可注入带优先级的 prompt Injection |
| 唱歌 | 预生成 RVC 翻唱文件播放（非实时合成） |

做得好的：
1. **signals + modules + prompt injection 优先级**的事件驱动架构——弹幕、语音、视觉全部变成带优先级的 prompt 注入，谁插话、何时开口集中调度。这是把多输入源揉进一个对话流的干净解法。
2. prompter.py「何时说话」决策器（弹幕到了≠马上回，考虑静默时长和说话占用）。
3. 流式 STT/TTT/TTS 全链路降低感知延迟。

它没做的：B 站、情绪表情映射（只靠 VTS 口型）、实时唱歌。

来源：https://github.com/kimjammer/Neuro · 前端 https://github.com/kimjammer/neurofrontend

## 6. AI-YinMei 吟美（1k★，开源 1.8.1 为 BSD-2-Clause；完整版 3.0.1 闭源）— 直播运营玩法最全

做得好的：1) 直播运营闭环（积分+抽奖+SC+欢迎词）；2) 意图前置路由省 LLM 调用；3) 学歌流水线。

## 7. 传统桌宠对比：VPet / Shimeji（交互形态参照系）

**VPet 虚拟桌宠模拟器**（Steam 免费发行，代码 Apache-2.0，动画素材单独授权）：
- 交互 = **数值养成 + 物理感**：摸头、提起/拖拽、爬墙、喂食/饮料、自定义工作、生病状态；点击弹工具栏，有说话栏。
- 动画 = 图片帧序列（宣称 32 状态 × 4 × 3 种）；Steam 创意工坊 MOD 生态（动画/物品/工作/说话文本/主题）；代码级插件系统（可插 Live2D/Spine、闹钟、记事板）；**内置 ChatGPT 设置窗口**（AI 对话是它的插件级功能，不是核心）。
- 来源：https://github.com/LorisYounger/VPet

**Shimeji-ee**（MIT）：桌面小人爬窗沿/挂在窗口上/被鼠标扔出去/成群活动；行为全靠 `conf/actions.xml`（动作+动画序列）+ `conf/behaviors.xml`（行为逻辑与触发频率）**纯 XML 声明**；无 AI。后继 fork（kilkakon 等）加了交互区域/小人之间互动 affordance。
- 来源：https://github.com/Shimeji-ee/Shimeji-ee

结论：传统桌宠的强项是「**活着的感觉**」——饿了会闹、拖拽有物理反馈、闲时有小动作；全部是状态机+数值，与 LLM 无关。这恰是 AI 桌宠普遍缺失的一层。

## 差距分析

### A. 别人有、我们没有（按值得抄的程度排序）

| # | 抄什么 | 谁做得最好 | 抄到哪个模块 |
|---|---|---|---|
| 1 | **B 站弹幕接入**：blivedm 直连（开源 LLM-VTuber 也内置了 B 站弹幕客户端）+ B 站直播开放平台官方 WebSocket；礼物/SC/点赞分型事件 | Ikaros AI-Vtuber / 吟美（聚合 9 渠道） | 直播对接模块（新增） |
| 2 | **游戏陪玩协议化**：Neuro SDK 的 WebSocket 三原语（Context/Registered actions/Forced actions），游戏方声明动作 schema、AI 只做选择；回合制优先，高 APM 只控高层意图 | VedalAI/neuro-sdk（Unity/Godot SDK + 6 个官方游戏集成） | 游戏直控模块——把我们「逐游戏硬写」改成「协议 + 游戏侧适配器」 |
| 3 | **何时说话的集中决策器**：弹幕/语音/视觉/静默计时全部变成带优先级的 prompt 注入，一个 prompter 决定开不开口；AI 内心 OS（表情动作想法可见不朗读） | kimjammer/Neuro + Open-LLM-VTuber | 对话管线/调度模块 |
| 4 | **唱歌流水线**：弹幕点歌→本地曲库/搜歌→学歌（吟美 150s/首，GPT-SoVITS 系）或 so-vits-svc 变声→演唱；切歌指令；与聊天队列并行 | 吟美（学歌）+ Luna（点歌+svc） | TTS/歌声模块（新增歌声子链） |
| 5 | **意图前置路由**：小模型（~10ms）先分意图+情感，点歌/画画/切歌/表情不过 LLM | 吟美 | 情绪引擎/调度——省 token 且降低延迟 |
| 6 | **直播运营玩法**：观众积分（聊天/点赞/送礼加分，点歌扣分）、抽奖、欢迎词、SC 感谢；aituber-onair 的 kizuna 羁绊包（积分/成就/等级/情绪加成）做成独立可复用包 | 吟美 + aituber-onair | 主播陪玩模块 + 记忆（观众关系持久化） |
| 7 | **弹幕选择策略**：不是每条都回——挑一条最值得回的、不安全屏蔽、被忽略的弹幕摘要进上下文（AI 知道刚才漏了什么） | aituber-onair/comment-intelligence | 直播对接模块 |
| 8 | **桌宠「活着感」**：摸头/拖拽/喂食/闲时小动作/数值状态（VPet 的 GameSave + 状态机；Shimeji 的 XML 行为声明）；吟美桌宠自带麦克风 VAD/AEC/声纹 | VPet / Shimeji / 吟美 | 桌宠交互层——给 Live2D 加状态机层，情绪引擎输出映射到养成状态 |
| 9 | **全链路流式**：STT 边说边转写、TTS 边生成边播、吟美宣称 600ms 语音响应 | kimjammer/Neuro + 吟美 | TTS/音频模块 |
| 10 | **窥屏主动关心**：自动识别屏幕状态（工作/游戏/挂机）主动开口 | LingChat / Open-LLM-VTuber（录屏感知） | 主播陪玩 OCR 解说——我们已有 OCR，补「状态判定→主动触发」 |
| 11 | **RAG 自动记忆**：对话中自动生成长期记忆条目 + rolling summary（每 10 对消息摘要一次） | kimjammer/Neuro / z-waif | 记忆模块 |

### B. 我们有、别人没有（卖点，保持并放大）

1. **真情绪引擎的「持续性 + 影响决策」**——市面「情绪」全是单句分类驱动立绘切换（LingChat/ZcChat/吟美意图+情感分类），没有把情绪做成**随时间演化的状态**并反过来影响 TTS 韵律、表情、行为决策。这是最大差异点。
2. **TTS 情绪韵律**——所有竞品 TTS 只换音色不控韵律；吟美的 cosyvoice2 情感微调最接近，但不是「引擎情绪状态→韵律参数」的闭环。
3. **一起看**——无任何竞品做「共享内容共感」（看视频/看直播一起反应）。空白市场。
4. **主播陪玩 OCR 解说**——竞品的视觉感知都是「AI 自己看屏幕陪用户」，不是「辅助真人主播的解说/弹幕应答副驾驶」。
5. **桌宠 + 游戏直控合一**——做游戏直控的（Neuro/AIRI/z-waif）全是主播皮套形态，做桌宠的（VPet/LingChat/ZcChat）全不能打游戏。我们两头都占。
