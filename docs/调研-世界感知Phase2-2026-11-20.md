## 2. 三个必答问题

### Q1 浏览器 tab/URL：扩展还是 CDP？

#### 扩展路径的真实实现（aw-watcher-web）

| 机制 | 源码 | 要点 |
|---|---|---|
| MV3 service worker + MV2 兼容 | `aw-watcher-web/src/manifest.json:27-34` | Chrome/Safari 用 `service_worker`，Firefox 用 `scripts` + `persistent:true`；同一份 TS 编三份清单 |
| 权限最小集（Chrome） | `aw-watcher-web/src/manifest.json:46-54` | `tabs`（读 url/title）、`tabGroups`、`alarms`（定时心跳）、`notifications`、`activeTab`、`offscreen`、`storage`；另有 `host_permissions: ["<all_urls>"]`（`:62`）——**我们自建时不需要 `<all_urls>`**，`tabs` 权限足以拿到活动 tab 的 url/title |
| 三类触发源 | `aw-watcher-web/src/background/main.ts:70-85` | `alarms.create` + `tabs.onActivated`（切 tab）+ `tabs.onUpdated`（url/title/groupId 变化）；三个监听器都在 `:74-85` 注册 |
| 定时心跳 60s | `aw-watcher-web/src/background/heartbeat.ts:168-180`；`config.ts:4-7` | `heartbeatAlarmListener`：alarm 到点 → 取当前活动 tab → 发心跳；周期在 `config.ts:6` 的 `intervalInSeconds: 60` |
| 切 tab 立即心跳 | `aw-watcher-web/src/background/heartbeat.ts:184-193` | `tabActivatedListener`：激活即上报，不等下一个 alarm |
| url/title 变化立即心跳 | `aw-watcher-web/src/background/heartbeat.ts:194-219` | `tabUpdatedListener`：只有 `changeInfo.url/title/groupId` 三者之一存在才处理；且**只上报当前活动 tab**（`activeWindowTab?.id !== tabId` 直接 return） |
| 心跳字段（最小集） | `aw-watcher-web/src/background/heartbeat.ts:60-64, 80-99` | 只取 `url/title/audible/incognito` + `groupId`；显式丢弃 `favIconUrl`（大 base64 导致内存无界增长，注释引 issue #222）；`tabCount` 单独统计 |
| URL 归一化 | `aw-watcher-web/src/background/heartbeat.ts:15-36` | `decodeURL()`：解析失败原样返回；对 http(s) 做解码/规范化 |
| 心跳串行化 | `aw-watcher-web/src/background/heartbeat.ts:150-155` | `heartbeatQueue = heartbeatQueue.then(task)` + `.catch(()=>undefined)`：后一个心跳不会因前一个失败而丢，也不会并发乱序 |
| 活动 tab 查询（含回退） | `aw-watcher-web/src/background/helpers.ts:50-75` | 先 `{active:true,currentWindow:true}`，空了再退 `{active:true}`（多窗口场景） |
| 用户开关门 | `aw-watcher-web/src/background/heartbeat.ts:70-72` | 未启用直接 `return`，不产生事件 |

**它解决的问题**：在「浏览器全屏/被遮挡、系统级前台窗口只报浏览器名」时，仍然知道用户在看哪个站点。这正好补 Phase 1 的洞。

**但它不适合直接装**：
- 它是 ActivityWatch 的 watcher，上报到 `127.0.0.1:5600/5666`（`manifest.json:43-44`），要额外跑 aw-server；
- `host_permissions: <all_urls>` 权限过宽；
- 我们只需要「活动 tab 的域名 + 标题」，不需要完整 URL/query（隐私）。

#### CDP 路径的真实能力（官方协议核实）

- `Target.setDiscoverTargets`：官方描述为「Controls whether to discover available targets and notify via `targetCreated/targetInfoChanged/targetDestroyed` events.」
- `Target.targetInfoChanged`：「Issued when some information about a target has changed.」
- `Target.getTargets`：「Retrieves a list of available targets.」
- 以上来自官方 `browser_protocol.json` 的 Target 域（2026-11-20 抓取，逐字核对）。

**可行性边界**：
- 需要浏览器以 `--remote-debugging-port` 启动（或 Electron 自己开 CDP）。用户日常开的 Edge/Chrome **默认没有**这个端口；
- CDP 给的是「浏览器级 target 列表」，拿 url/title 要处理 target 类型（page/iframe/worker）与窗口归属；
- 与「system 零改动」约束冲突：要么改用户浏览器启动方式，要么常驻一个调试端口（安全面变大）。

#### 结论（推荐）

**主路径：自建一个极轻量 MV3 扩展**（约 150 行），照 aw-watcher-web 的三触发源 + 心跳串行化 + 字段最小集，但：
1. 只上报 `host`（域名）+ `title` + `audible` + `active`，**不上报 path/query/fragment**；
2. 上报到我们宿主本机端口（带 token），不引入 aw-server；
3. 权限只要 `tabs` + `alarms`（不要 `<all_urls>`、不要 `offscreen`）；
4. 用户可一键暂停（扩展 popup 一个开关），暂停即零采集。

**CDP 列为「受控浏览器」备选**：只有当我们自己启动浏览器（或用户明确同意带调试端口启动）时才用，不做主路径。

**明确否掉**：
- 直接安装 aw-watcher-web + 跑 aw-server：多一个常驻服务 + 多一套数据落盘，违反「不新增进程/端口」；`<all_urls>` 权限过宽。
- 让宿主 Electron 代劳读浏览器 tab：Electron 读不到其他进程的浏览器内部状态（不是 UIA 能拿到的语义）。
- 依赖 CDP 作为唯一来源：用户浏览器默认不开调试端口，会静默零数据（最坏的假成功）。

### Q2 RSS「今日简报」的显著性怎么算？

#### rss-parser 能提供什么（只到解析层）

| 机制 | 源码 | 要点 |
|---|---|---|
| URL 拉取 + 重定向跟随 | `rss-parser/lib/parser.js:73-116` | `parseURL(feedUrl, cb, redirectCount)`；3xx 时取 `newLocation` 递归，最多若干次（同一函数内） |
| Atom `updated` → `lastBuildDate` | `rss-parser/lib/parser.js:148-149` | `xmlObj.feed.updated[0]` 直接作为 `feed.lastBuildDate` |
| 条目时间兜底 | `rss-parser/lib/parser.js:166-167` | 先 `published`，没有再用 `updated` |
| 统一 `isoDate` | `rss-parser/lib/parser.js:341-344` | `item.pubDate || item.date` → `new Date(...).toISOString()`；解析失败会抛/留空 |

**它不提供**：去重、显著性、与用户兴趣的匹配、跨源排序。这些必须我们自己做。

**现状**：项目内没有任何 RSS/feed 代码（见 §1 的 grep），所以这是全新能力，不存在「复用旧实现」。

#### 显著性排序公式草案（字段级，可落地）

对每条新条目算 `score`：

```
score = 0.40 * recency + 0.25 * interest + 0.20 * source_trust + 0.15 * novelty
```

- `recency = exp(-age_hours / 18)`：半衰期约 12.5h；超过 72h 直接剪掉（不进候选）。
- `interest`：从「用户事实 + 核心记忆 + 最近 14 天对话关键词」抽 30–80 个词（中文 2-gram + 英文词），
  在 `title + summary` 上算命中率并归一化；命中 0 条 → 0。
- `source_trust`：用户显式置顶的源 = 1.0；用户手动标记「不想看」的源直接剔除；
  其余 = 0.5 + 0.1 * min(过去 30 天该源被点开次数, 5)（冷启动恒 0.5）。
- `novelty = 1 - max_jaccard(title_tokens, 最近 7 天已推送标题)`；Jaccard ≥ 0.7 视为重复，直接丢弃。

**冷启动（没有点击数据）**：只用 `recency + interest`（权重 0.6/0.4），每天最多 3 条；
第一周记录「用户点开了哪条」作为 `source_trust` 的反馈，第二周起启用完整公式。

**世界行怎么写（≤100 tokens）**：不写条目正文，只写
`📰 3 条新：<最相关标题≤40字>（<源名>）`；其余条目留在可检索的记忆里，用户问起再展开。

**明确否掉**：
- 每条都调 LLM 打分：一天几十条 × 一次调用，成本与延迟都不值得；规则分先跑，只有前 3 条可选做一次轻量摘要。
- 抄 karakeep 的实现：AGPL-3.0，传染性许可，只做行为参照。
- 用「已读/未读」当唯一信号：RSS 客户端大多不回报已读，拿不到。

### Q3 系统通知监听的最小包身份方案

#### 现有底座（已读清单与脚本）

| 机制 | 源码 | 要点 |
|---|---|---|
| 稀疏身份包清单 | `_packaging/identity/AppxManifest.xml.template:50-62` | `Application Executable="__EXECUTABLE__"` + `uap10:TrustLevel="mediumIL"` + `uap10:RuntimeBehavior="win32App"` |
| 外部内容 | `_packaging/identity/AppxManifest.xml.template:34` | `uap10:AllowExternalContent>true`：清单可从外部目录注册（不必把 exe 打进包） |
| 能力声明 | `_packaging/identity/make-identity-package.ps1:13` | `uap3:Capability Name="userNotificationListener"`；同时有 `runFullTrust` + `unvirtualizedResources`（`:11-12`） |
| 生成参数 | `_packaging/identity/make-identity-package.ps1:380` | `capabilities = @('runFullTrust','unvirtualizedResources','userNotificationListener')` |
| 注册方式 | `_packaging/identity/register-identity-admin.ps1:77-78` | 管理员 `Add-AppxPackage -Register $ManifestPath -ExternalLocation $dir`；脚本明确提醒「失败是**非终止错误**，必须复查 Get-AppxPackage」（`:75`） |
| 通知监听验证命令 | `_packaging/identity/register-identity-admin.ps1:97-99` | `[Windows.UI.Notifications.UserNotificationListener, Windows.UI.Notifications, ContentType = WindowsRuntime]` + `UserNotificationListener.Current` + `RequestAccessAsync()`（会弹一次用户授权，`Allowed` 才真正能读通知） |

#### 最小方案（字段级）

1. **前置**：注册身份包（管理员一次），确认 `Get-AppxPackage *dafeiyu*` 有 `Status: Ok`。
2. **授权**：首次运行时调用 `RequestAccessAsync()`，用户点「允许」；结果持久化（`Allowed/Denied/Unspecified`），Denied 后不再骚扰。
3. **采集**：只取最近 24h、且 `UserNotificationListener.GetNotificationsAsync(NotificationKinds.Toast)`；
   每条只留 `app_name`（`AppInfo.DisplayInfo.DisplayName`）、`title`、`body`（截断 ≤120 字）、`creation_time`。
4. **过滤**：跳过我们自己的包（`dafeiyu`）、跳过系统噪音（Windows Security 等白名单外）、同一 `(app_name,title)` 30 分钟内去重。
5. **落盘**：append 到 `data/notifications.jsonl`，字段：`ts/app/title/body_hash/body_excerpt/source:"toast"`；
   正文不进世界行，只进可检索记忆。
6. **世界行**：只写「<app> 弹了 <N> 条」或「<app>：<title≤30字>」，每天最多 3 次，且只在用户非游戏/非全屏时。

#### 关键未解（必须实测，不能纸面通过）

- `UserNotificationListener` 的调用**必须发生在有包身份的进程里**。我们的 Electron 主进程是通过稀疏包的 `Application Executable` 获得身份的（`uap10:TrustLevel=mediumIL` + `win32App`），
  但这条链路**从未跑过**：注册脚本只给了 PowerShell 里的验证命令，没有在 Electron 里验证过。
- 若 Electron 进程拿不到身份：降级为「PowerShell 子进程（带包身份上下文）轮询 + 写 jsonl，宿主只读文件」，代价是多一个短命进程（非常驻，可接受）。
- 若两种都失败：**不做通知监听**，世界行不写通知。不假装有。

**明确否掉**：
- 轮询 `wpndatabase.db`：SQLite 被系统占用 + 需要 SYSTEM 权限 + 表结构无承诺，脆弱。
- UI Automation 读操作中心：能读但语义差（无 app 名结构化字段）、依赖窗口打开。
- 用第三方通知库硬闯：引入原生依赖与杀软误报面。

## 5. 三条能力的最小实现（字段级）

### 5.1 浏览器 tab（扩展 → 宿主）

扩展上报（每 60s 或 tab 激活/变化时，串行）：

```json
{ "v": 1, "ts": 1763600000000, "host": "example.com", "title": "标题≤80字",
  "audible": false, "incognito": false, "tabCount": 7, "token": "<per-install>" }
```

宿主落盘（`data/browser-tabs.jsonl`，append）：

```json
{ "ts": 1763600000000, "host": "example.com", "title": "…", "audible": false,
  "incognito": false, "source": "ext", "day": "2026-11-20" }
```

世界行（只在 host 或 title 变化时写，≤100 tokens）：
`🌐 Edge：example.com — <title≤40字>`；incognito 一律只写 `🌐 浏览中（隐私）`，不写域名。

去重规则：同一 `(host,title)` 连续心跳不重复写；跨天重置。

验收：①扩展停用 → 世界行 5 分钟内不再出现浏览器行；②切 3 个 tab → 依次出现 3 行且无重复；③incognito → 只出现「隐私」字样；④无 token 的上报被 401 拒绝。

### 5.2 RSS 今日简报

```json
// feed 配置：data/feeds.json
{ "feeds": [ { "id": "hn", "url": "https://…", "name": "HN", "weight": 1.0, "enabled": true } ] }

// 条目：data/rss-items.jsonl
{ "id": "sha1(feed_id+link)", "feed_id": "hn", "title": "…", "link": "…",
  "published_at": "2026-11-20T08:00:00Z", "summary": "≤200字", "fetched_at": 1763600000000,
  "score": 0.0, "pushed": false }
```

流程：拉取（每 30–60 分钟）→ 解析（rss-parser 或自写 XML）→ 剪枝（>72h 丢）→ 去重（id / Jaccard≥0.7）→ 打分 → 取前 3 → 写世界行 + 标记 `pushed`。
每天最多推送 3 次（早/午/晚各一次窗口），用户正在游戏/全屏时顺延。

验收：①同一 feed 两次拉取不产生重复 id；②冷启动（无点击）只按 recency+interest 排序；③推送后 `pushed=true`，重启不重推。

### 5.3 通知监听

```json
// data/notifications.jsonl
{ "ts": 1763600000000, "app": "微信", "title": "…", "body_excerpt": "≤120字",
  "body_hash": "sha1", "source": "toast", "day": "2026-11-20" }
```

状态文件：`data/notification-permission.json` → `{ "status": "Allowed|Denied|Unspecified", "checked_at": … }`。

世界行：`🔔 微信：<title≤30字>`；同一 app 30 分钟内只写一次；游戏/全屏时不写。

验收（分两级）：
- **纸面级**：`Get-AppxPackage *dafeiyu*` → Status Ok；`RequestAccessAsync()` 返回 Allowed（PowerShell 里跑）。
- **真机级**：Electron 主进程发起一次读取，能拿到 ≥1 条真实 toast；拿不到 → 走 PowerShell 轮询降级；再拿不到 → 关闭该能力并打印原因（不许静默）。

## 6. 未解问题 / 需实测的假设

1. **Electron 进程的包身份是否生效**：稀疏包 `AllowExternalContent` + `TrustLevel=mediumIL` 的机制理论上让外部 exe 获得身份，但从未在 Electron 上验证。这是通知能力的唯一硬前提。
2. **扩展的分发方式**：自建扩展需要用户手动「加载解压的扩展」（开发者模式）；Chrome 商店上架需要审核与开发者账号。先用开发者模式，文档写清三步。
3. **扩展的上报端口与鉴权**：宿主需要开一个本机 HTTP 口（或复用现有 8103 加路由）。若复用 8103，要确认 CORS 与 token 方案（扩展的 `host_permissions` 需要包含该地址）。
4. **RSS 显著性公式的权重**：0.40/0.25/0.20/0.15 是草案，必须用 2 周真实数据校准；`interest` 的词表从用户事实抽取也可能噪声大。
5. **通知正文的隐私边界**：微信/邮件的正文可能包含敏感信息；默认只存 `body_hash + 前 40 字`，还是完全不存正文？需要用户拍板。
6. **incognito 的处理**：Chrome 扩展默认不能读 incognito tab（除非用户显式允许「在无痕模式中运行」）；即使允许，我们也不该记录域名。默认按「隐私」处理。
7. **世界行频率**：浏览器行可能在一天内产生上百次变化；必须做「同 host 5 分钟内只写一次」的节流，否则会挤占世界行预算。
