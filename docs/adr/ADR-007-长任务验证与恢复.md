# ADR-007：长任务的验证与恢复 —— 三级 oracle，五级恢复阶梯，先熔断再重规划

**Status:** Proposed（2026-11-18，待用户拍板）
**Date:** 2026-11-18
**Deciders:** 用户（产品方向）· 本轮调研（技术）
**相关:** `docs/adr/ADR-004-世界感知与推理成本.md` · `docs/复盘-真假成功与系统性治理-2026-11-09.md` · 调研 §2.2/§2.3

## Context

现状是**动作级验证已经很强，任务级验证为零**：

| 已有 | 位置 | 能力 |
|---|---|---|
| 统一结果契约 | `dispatch/verify-contract.js` | `ok / verified / effect / evidence / nextIfFailed / tier(L1/L2/L3) / action_sent` |
| 幂等与重试判据 | 同上（`EFFECT_MEANS_SENT`） | `action_sent=true && verified=null` 时**禁止重试**（会做两遍） |
| 动作级效果分类 | 同上 | `confirmed / confirmed_idempotent / suspected_noop / unverifiable` |
| 抽出式观测 | `dispatch/index.js` + `game-control.js` | snapshot 回读、click_text 前后 dHash、`evidence` 人话文案 |
| 技能退出校验 | `dispatch/skill-library.js` | `exitHash` 相似度 ≥0.75 才算成功 |

缺的是：**"整个任务成功了吗"**。现在只能用 `exitHash`（全屏 dHash）近似——用像素猜语义，
遇到"文件存对了但界面没变"或"界面变了但内容错"都会误判。

更要紧的是失败恢复的现状：`nextIfFailed`（"下一步试什么"的文案）**写得很好，但没有任何代码读它**。
没有消费者的建议等于注释。实测的恢复手段只有"再试一次相同动作"。

外部两条硬证据支撑本 ADR 的方向：
- OSWorld 把"任务成功"定义成 `(result_getter, expected_getter, metric)` 的纯函数，
  getter **读应用真实状态**（`desktop_env/desktop_env.py:533`），并有 26/368 个 `infeasible` 任务用"主动 FAIL"计分；
- browser-use 1.0 让每个动作**统一输出一行结论**（`navigated / page changed / no change`，`browser_use/ax.py`），
  这是 cycle 熔断唯一廉价且可靠的信号。

## Decision

**三级 oracle 负责"判断"，五级恢复阶梯负责"下一步"，两条硬熔断负责"别再试了"。**

### 1. 三级 oracle（逐级变贵，能用低的不用高的）

| 级 | 名字 | 读什么 | 成本 | 适用 |
|---|---|---|---|---|
| **T1 动作级** | `action effect` | 前后状态差（dHash / UIA 摘要） | 已有（L1/L2） | 每次动作后 |
| **T2 子任务级** | `subtask assert` | 声明式断言：`{getter, predicate}`，如"窗口标题含 X""文件存在且含 Y" | 8–40ms（L2 回读） | 计划条目完成时 |
| **T3 任务级** | `task oracle` | `{result_getter, expected, metric, conj}`，**只读外部真实状态** | 一次调用 + 可能的启动开销 | 任务结束时 |

三条纪律（不可协商）：
1. **禁止自证**：getter 不得读工具返回值、不得读 agent 自己的报告。
   可读源只有：文件内容、窗口标题/类名、UIA 文本、剪贴板、进程/端口、应用自身数据文件（如计算器显示区）。
2. **宁可漏判为失败，不可误判为成功**（WebArena 的 `eval_types` 相乘语义）：多判据用 `and` 串联；
   只有"两种合法做法"时才用 `or`（OSWorld 的 `conj:"or"` + 两份 gold 文件就是这个用法）。
3. **oracle 必须被 gold 解验证过**（Terminal-Bench 的 `solution.sh` 纪律）：每条任务附一条参考动作序列，
   证明 oracle 在正确解上为真、在当前状态下为假。

### 2. 五级恢复阶梯（代价递增，每上一档必须留 evidence）

```
0. 不重试        action_sent=true && verified=null  → 只能观测，不能重发（已有契约，补执行者遵守）
1. 幂等重试      effect=unverifiable 且动作幂等 → 重试 1 次
2. 换 grounding 档  effect=suspected_noop ×2 → 升档（UIA 直调 → UIA 编号 → SoM → 坐标），见 ADR-008
3. 重规划剩余子任务  子任务 failed → 用 failed_subtask + completed[] + remaining[] 重规划（ADR-006）
4. ask_user     需要密码/UAC/歧义选择/连续 2 次重规划仍失败 → 交回用户
5. fail         明确不可完成（目标不存在/权限不足）→ 主动失败 + 说明原因 + 零副作用
```

**为什么阶梯顺序是这样**：便宜且无副作用的先试（1、2），代价是时间和一次截图；
改计划的代价是 token 和抖动（3）；交回用户的代价是体验（4）；放弃的代价是任务本身（5）。
把 3 放在 2 之后，是因为"换 grounding 档"常常不需要改计划就能过（UIA 空壳换 SoM 的实测命中率高于重新规划）。

### 3. 两条硬熔断

- **no-change 熔断**：同一子任务内 `suspected_noop` 连续 2 次 → 禁止再发**同档**动作（必须升档或重规划）。
  依据：现在实测会出现"点同一个禁用按钮 4 次"，每次都返回 `ok:true`，模型据此认为在推进。
- **循环熔断**：同一 `(action, target)` 三元组在一次任务内出现 3 次 → 直接跳第 4 档（ask_user）。
  依据：Agent-S 的反射器（`procedural_memory.py:104`）专门只判"是否循环、是否偏离"，
  说明这是长任务的**头号失败模式**，且必须由外部计数强制，不能靠模型自省。

## Options Considered

### Option A（选中）：三级 oracle + 恢复阶梯（宿主侧实现）
| 维度 | 评估 |
|---|---|
| 实现 | 中（T1 已有；T2 是声明式断言 + 一批 getter；T3 每任务一条） |
| 成本 | 动作后 T1 已有；T2 8–40ms；T3 一次 |
| 可靠性 | 高（读外部状态，可被 gold 解验证） |
| 通用性 | 中（每个任务要手写 oracle，无法自动生成） |

**Pros**：把"真假成功"从文案变成可执行断言；与现有 `verify-contract` 天然衔接（T1 不动）。
**Cons**：**oracle 写起来是人力成本**（每个任务 20–60 行）；对"没有可读状态的应用"（自绘游戏）无能为力，
必须落回 T1 + 视觉兜底。

### Option B：VLM 截图判定（把首尾截图给视觉模型，问"完成了吗"）
| 维度 | 评估 |
|---|---|
| 实现 | 低（一次 VLM 调用） |
| 成本 | 云端按次计费；本地 Ollama 需 `free_mb ≥ 6000`（ADR-004 硬门） |
| 可靠性 | 中低（同图两次判定可能不一致；"看起来完成了"≠"数据正确"） |
| 通用性 | 高（任何应用都能问） |

**Pros**：零标注成本，能覆盖自绘应用。
**Cons**：① 与 ADR-004 的成本红线冲突（云端 ≤6 次/小时）；② 不可复现（评测会 flaky）；
③ 会把"打开对话框"误判成"已保存"。**只允许作为 T3 的最后兜底**，且必须在结果里标 `tier:'vlm'`，
不参与 CI 门禁判定。

### Option C：只靠模型自评（让模型在结束时说"我做完了"）
| 维度 | 评估 |
|---|---|
| 实现 | 0 |
| 可靠性 | 低（我们的复盘文档已经定过性：26 个 `ok:true` 里 24 个没验证） |

**Cons**：这正是 `docs/复盘-真假成功与系统性治理-2026-11-09.md` 要治的病；
`verify-contract.js` 头部也记着账：「26 个 `ok:true` 里 24 个没验证」。**否**。

### Option D：全自动脚本 oracle（每个任务自动生成一段校验脚本）
| 维度 | 评估 |
|---|---|
| 实现 | 高（要一个能写校验脚本的代码模型 + 沙箱） |
| 可靠性 | 未知（生成的脚本本身可能错，且错得静默） |

**Pros**：理论上可规模化到几百个任务。
**Cons**：**oracle 出错比没有 oracle 更危险**（会给出"绿灯"假象，且没人会去审计生成的断言）。
Agent-S 的 `STATE_EVALUATOR_SYSTEM_PROMPT` 让模型写 Python 去查，也只用于**评测期**而非产品运行时。**否**（评测期可试）。

## Trade-off Analysis

真正的权衡是**「覆盖 vs 可信」**：VLM 判定覆盖 100% 但不可信；声明式 oracle 可信但只覆盖"有状态可读"的应用。

选 A 的关键理由是**可归因**：oracle 失败时能指出"哪个 getter 读到了什么"，而 VLM 只能说"我觉得没完成"。
长任务的调试成本主要在归因而非判定。

代价有两个，都要接受：
1. **写 oracle 是人力活**。缓解：先只给 5 个任务写，验证"谎报注入"能被抓住，再推广；
   同类应用（记事本/写字板/浏览器）的 getter 可复用。
2. **恢复阶梯会让单次任务更慢**。升档要重截图（~31ms）+ 重读树（8–40ms）。
   缓解：阶梯只在失败路径上生效，成功路径零成本。

拒绝"每步都跑 T3"的原因很直接：T3 是任务级判定，每步跑等于每步做一次全量状态比对，
成本×步数，且会把"中间态"误判为失败（例如"另存为"对话框打开时文件还不存在）。

## Consequences

- ✅ 现有 `verify-contract` 不用改（T1 就是它）；新增的只是 T2/T3 的声明式断言与 getter
- ✅ 评测可复现（读外部状态），p50/p95 稳定，可进 CI 门禁
- ✅ infeasible 任务有了判据：`fail` + **副作用为零**（文件未变、窗口未关、剪贴板未动）
- ⚠️ **getter 本身可能读错**（例如读错窗口、读到缓存）。每条 getter 必须带"读到什么"的 evidence，
  并在 gold 解上验证一次（否则 oracle 的错误会被当成产品 bug 排查很久）
- ⚠️ **恢复阶梯会让"误伤"变多**：升档到坐标点击时可能点到别处。故 `ask_user` 必须在阶梯第 4 位而不是第 2 位——
  太早问会显得她笨，太晚问会误伤
- ⚠️ 循环熔断的计数是**按任务**而非按会话：否则连续两个相似任务会被误杀
- 🔁 要复查：T3 的 getter 清单是否需要缓存（同一任务内多次读同一文件）
