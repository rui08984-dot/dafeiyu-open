# ADR-012：技能沉淀与程序性记忆 —— 候选隔离、oracle 验收、两次独立成功才算「学会」

**Status:** Proposed（2026-11-18，待用户拍板）
**Date:** 2026-11-18
**Deciders:** 用户（她能不能「越用越强」）· 本轮调研（技术）
**相关:** ADR-007（验证与恢复）· ADR-008（grounding 阶梯）· ADR-010（记忆 v2）· ADR-011（目标栈）· `docs/复盘-真假成功与系统性治理-2026-11-09.md`

## Context

`skill-library.js` 已经是**正确的雏形**，不需要推倒：

| 已有 | 位置 | 作用 |
|---|---|---|
| 可重放白名单 | `skill-library.js:54 REPLAYABLE` | 排除 `click_element/som_click` 这类依赖运行时编号的动作 |
| Beta 后验 | `:313 reliabilityOf` | `successCount/attemptCount` + 均值 + 置信半宽 + `insufficient/reliable/unreliable` |
| 只认验证过的成功 | `:520-530` | 只有 `verifiedOk` 才 `successCount++` |
| 前置/后置画面 | `:470-490`、`:509-518` | `entryHash` 相似度 ≥0.9 才跑，`exitHash` ≥0.75 才算成 |
| 自动沉淀提示 | `:613 detectRepeatedSequenceIn` | 24h 内同序列成功 ≥2 次 → 提示（不自动建卡） |
| 病历 | `:152 recordPitfall` / `:176 getPitfalls` | 按应用记「以前踩过的坑」，失败时主动告诉模型 |

缺的是四样：
1. **候选态**：现在「一次成功」就能 `skill save`，没有隔离区；
2. **语义后置条件**：`exitHash` 是全屏 dHash，用像素猜语义（ADR-007 已定性）；
3. **降级/退役**：错了只能人工 `forgetSkill`，没有自动降级；
4. **任务级教训**：`pitfalls` 是按应用记的「坑」，不是「这类任务上次为什么失败、换哪条路成的」。

外部两条硬证据：
- Voyager 的技能入库**不是**「跑完就存」：`voyager/voyager.py:221` 先让 critic 判 `check_task_success`，
  只有 `success` 才在 `:353-354` 调 `add_new_skill`；`skill.py:61` 还会同名覆盖并保持向量库与 `skills.json` 同步。
- Reflexion 的教训**只对失败生成**（`alfworld_runs/generate_reflections.py:38`：`if not env['is_success']`），
  且 memory 只取最近 3 条、与当前任务绑定（`env_history.py:43`）——它没有把一次失败写成全局人格事实。

这两条合起来就是本 ADR 的底线：**入库前有闸，教训有作用域，一次成功不算学会。**

## Decision

**程序性记忆分三层：原语（工具，不可学）、技能（可执行，必须过闸）、教训（只读文本，不执行）。
技能走「候选 → 激活 → 可疑 → 退役」四态；「学会」= 两次独立成功 + oracle + 可重放 + 可降级。**

### 1. 三层与边界

| 层 | 是什么 | 谁写 | 能否执行 | 例子 |
|---|---|---|---|---|
| **原语** | 内置工具/动作（`act`、`see`、`app`…） | 产品代码 | 是 | `click`、`type`、`focus_window` |
| **技能** | 一串可重放的原语 + 前置/后置条件 | 技能沉淀（本 ADR） | 是（经 `runSkill`） | 「记事本写三行→另存到桌面」 |
| **教训** | 一句话经验 + 证据 + 作用域 | 任务结束/失败恢复 | **否**（只进提示词） | 「这个应用的保存框会遮挡，先按 Esc」 |

**为什么教训不能执行**：Reflexion 的教训是自然语言，模型每次理解可能不同；把它当动作执行等于把幻觉变成副作用。
教训只做「提示」，执行永远走技能或原语。

### 2. 技能对象（在现有 schema 上扩展）

```
skill = {
  id, name, version,
  status: 'candidate' | 'active' | 'suspect' | 'retired',
  preconditions: { app?, titlePattern?, entryHash?, scope: 'exact'|'any' },
  steps: [{ action, arg }],                  // 必须在 REPLAYABLE 白名单内
  postcondition: { oracle: OracleRef, weak?: true },   // T2/T3；dHash 只能标 weak
  provenance: { task_ids: [], created_by: 'sediment'|'manual' },
  stats: { successCount, attemptCount, lastRunAt, consecutiveFailures },
  history: [{ at, task_id, entryHash, exitHash, oracle_evidence, result }]
}
```

- `weak:true` 表示后置条件只有 dHash/像素，允许存在但**不参与自动晋升**，只能人工确认。
- 同名新版本不覆盖旧版：保留 `version` 与上一版，出问题可回滚（Voyager 的 `V2` 命名同理，但我们要能回滚而不只是留文件）。

### 3. 「学会」的五个条件（缺一不可）

1. **可重放**：所有 step 在 `REPLAYABLE` 白名单内；
2. **有前置**：至少声明 `app` 或 `titlePattern` 或 `entryHash` 之一；
3. **有后置 oracle**：T2/T3 的外部状态断言，不是工具返回值、不是模型自评；
4. **两次独立成功**：两次运行的初始状态不同（`entryHash` 不同；`scope:'any'` 的技能用不同 `task_id` 或不同前台应用/标题证明），
   且都过 oracle、都无 collateral。两次成功可以来自：① 模型在新任务里**自然重复**了同一序列（从执行历史检测 + oracle 证据）；
   ② 一次自然重复 + 一次候选提示后的受控运行。**不允许同一次运行拆成两段充数**；
5. **可降级**：连续 2 次在未变化的前置条件下失败 → `suspect`；再 1 次 → `retired`，保留墓碑与证据。

只有同时满足 1–5，`status` 才从 `candidate` 变 `active`，才允许被 t=0 检索进提示词。

**为什么是两次、且要求初始状态不同**：一次成功可能是巧合（弹窗刚好没出现、文件刚好已存在）。
Voyager 用 critic 判一次就入库，是因为它在游戏里有确定性 reset；我们的桌面没有 reset，必须用「不同初始状态」换置信。

### 4. 污染防线（七条）

1. **禁止自证**：`successCount++` 只能由 oracle 触发；工具返回 `ok:true` 不算（现有 `verify-contract` 的 `action_sent` 纪律延续）。
2. **候选隔离**：`candidate` 不以可执行技能出现（`runSkill` 拒绝）；最多以一行「以前这么做成过（候选，未验证）」提示进 t=0 检索，
   且必须标 `candidate`，不得被当作确定步骤。候选提示 ≤40 tokens，最多 2 条。
3. **禁止单次成功入库**：`detectRepeatedSequenceIn` 的「24h ≥2 次」只是**提示**，不是晋升；晋升要两次**独立验证**。
4. **禁止不可重放动作**：`click_element #3`、`som_click` 这类编号动作一旦进技能，换一代界面就点到别处（ADR-008 已把这条写成运行时校验）。
5. **禁止纯像素后置**：`weak:true` 的技能不能自动晋升；能补语义 getter（文件内容/窗口标题/UIA 文本）就必须补。
6. **反思结论不能直接变技能**：ADR-010 的 `insights.jsonl` 是 semantic，不是 procedural；要变成技能必须走完整的执行+验证链。
7. **高风险动作不自动晋升**：`RISKY` 正则命中（删除/格式化/关机/卸载…）的技能，`risk:'high'`，必须用户确认一次才 `active`。

### 5. 教训（lesson）与病历（pitfall）的分工

| | pitfall（已有） | task-lesson（新增） |
|---|---|---|
| key | 应用名/关键词 | `task_signature`（目标文本归一化 + 应用） |
| 内容 | 「这个坑在哪、怎么绕」 | 「上次为什么失败、换哪条路成功」 |
| 写入 | 拦截 GUI/launch 失败时（`game-control.js:3933`） | 任务结束/恢复成功后 |
| 读取 | 派发/拦截时按 target（`dispatch/index.js:976`） | t=0 技能检索时一起取 top3 |
| 作用域 | 应用级 | 任务级 |
| 生命周期 | 200 条滚动 | 90 天 TTL；被新证据推翻则 supersede |

**为什么教训也要证据**：一条「上次这么做成了」如果没有 task_id 与 oracle 证据，就是传说；
传说进提示词会变成新的跑偏源（Reflexion 的 memory 也只保留最近 3 条，正是怕旧教训压过当前观察）。

### 6. 检索策略

- **只在 t=0 检索一次**（Voyager `skill.py:114` 的纪律：任务开始时检索 top-k，执行中不反复召回）：一次任务只付一次召回成本；
- 输入：`goal.text + 前台应用 + 活动状态`；走已有 8090 嵌入；
- 输出：top3 技能（只取 `active`）+ top3 教训（按应用/任务签名）；总注入 ≤300 tokens；
- 日志必须记 `cited_skill_ids` / `cited_lesson_ids`，否则无法评估记忆是否真的有用；
- 运行中不重新检索（除 ADR-007 的「重规划」触发点，允许再检索一次，最多一次）。

## Options Considered

### Option A（选中）：候选隔离 + oracle + 两次独立成功 + 四态生命周期
| 维度 | 评估 |
|---|---|
| 实现 | 中（在现有 skill-library 上加 status/version/oracle/provenance，约 250–350 行） |
| 学习速度 | 慢（要两次独立成功） |
| 污染风险 | 低（候选隔离 + 外部 oracle + 可降级） |
| 可审计 | 高（每次运行有 entry/exit/oracle evidence） |

**Pros**：复用现有 Beta 后验、REPLAYABLE、pitfall；把「真假成功」的纪律延伸到程序性记忆；可评测（候选/晋升/降级都能单测）。
**Cons**：学习变慢；oracle 要人力写；`weak` 技能需要人工确认；技能版本管理增加存储与复杂度。

### Option B：每次成功自动存技能（Voyager 的简化版，去掉 critic）
| 维度 | 评估 |
|---|---|
| 实现 | 最低（现有 `saveSkillFromHistory` 直接调） |
| 污染 | ❌ 一次巧合就入库；错误步骤会被反复复用 |
| 归因 | ❌ 分不清「技能对」还是「这次运气好」 |

**Cons**：Voyager 自己都不敢省掉 critic（`voyager.py:221` 先判成功）；我们连 critic 都没有，更不能省。**否**。

### Option C：技能 = 模型生成的代码（Voyager code-as-action）
| 维度 | 评估 |
|---|---|
| 能力 | 表达力最强 |
| 安全 | ❌ 本机任意代码执行；删库/外发只差一行 |
| 可移植 | ❌ 依赖分辨率/窗口位置/DPI |
| 可验证 | ❌ 裸代码没有 pattern、没有回读，`verify-contract` 的 L2 失效 |

**Cons**：ADR-008 已明确否掉 code-as-action；我们的授权边界是「用户本机、用户身份」，没有 VM 隔离。**否**。

### Option D：只记教训，不存可执行技能（纯 Reflexion）
| 维度 | 评估 |
|---|---|
| 实现 | 低（写 JSONL + 检索） |
| 复用 | ❌ 每次都要重新推导步骤，长任务步数不会下降 |
| 一致性 | ❌ 同一任务两次做法不同，无法比较 |

**Pros**：没有技能污染问题。
**Cons**：放弃了「越用越强」的核心收益；教训只能提示，不能省掉探索成本。**否**（作为补充层保留）。

### Option E：维持现状（只手动 `skill save`）
| 维度 | 评估 |
|---|---|
| 实现 | 0 |
| 积累 | ❌ 依赖她/用户记得存；实测 24h 提示也只是提示 |

**Cons**：这正是「有技能库但不增长」的现状。**否**。

### Option F：用轨迹微调/LoRA 代替显式技能
| 维度 | 评估 |
|---|---|
| 能力 | 理论上泛化最好 |
| 数据 | ❌ 单机每天几条轨迹，远远不够 |
| 可审计 | ❌ 权重里改了什么不可见；出错无法回滚单条 |
| 成本 | ❌ 训练/部署/回滚三套工程 |

**Cons**：ADR-003 已定「先规则后学习」；程序性记忆先用显式技能，等数据攒够再谈 ranker。**否**。

## Trade-off Analysis

核心权衡是**「学得快 vs 学得对」**。自动沉淀（B）一天能攒十几条技能，但其中一半是「这次刚好」；
两次独立成功（A）可能三天才攒一条，但每条都能被 oracle 复现。

选 A 的理由是**程序性记忆的污染是复利**：一条错技能会被复用十次，每次都可能误伤数据；
而学得慢只是少省几步。对一个跑在用户真实桌面上的伴侣，**误伤的代价远高于笨一点**。

第二个权衡是**「oracle 人力成本」**。给每个技能写 T2/T3 是人力活；缓解：
- 同类应用复用 getter（记事本/浏览器/计算器先做一套）；
- 允许 `weak:true`（dHash）存在，但不自动晋升；
- 先只给 5 个高频技能写 oracle，验证「谎报注入能被抓住」再推广。

第三个权衡是**「教训的时效」**。90 天 TTL 会让老经验失效；这是故意的——桌面应用会更新，
三年前的坑可能已经不是坑。被新证据推翻的教训走 supersede，不删除，保留可追溯性。

## Consequences

- ✅ 复用现有 `skill-library` 的全部纪律，不新建技能库
- ✅ 每条技能可回答「哪两次成功、oracle 读到什么、谁验证的」
- ✅ 候选/激活/可疑/退役四态可单测；污染样本可回放
- ⚠️ **学习变慢**：两次独立成功意味着新技能至少跨两个任务；接受
- ⚠️ **oracle 是人力成本**：每个技能 20–60 行 getter；先覆盖 5 个高频技能
- ⚠️ **dHash 后置仍是弱判据**：`weak` 技能只能人工确认；不要用「相似度 0.75」冒充语义正确
- ⚠️ **版本与墓碑会让 skills.json 变大**：设上限（active ≤200、retired 保留 90 天），滚动清理
- ❌ 不做代码生成、不做微调、不做跨用户共享技能库（隐私与污染面都太大）
