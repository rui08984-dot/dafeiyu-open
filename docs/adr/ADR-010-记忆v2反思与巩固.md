# ADR-010：记忆 v2 的反思/巩固 —— 重要性触发、证据链、只 supersede 不删除

**Status:** Proposed（2026-11-18，Phase 3 设计）
**Date:** 2026-11-18
**Deciders:** 主会话 · 用户（记忆可删性）
**Depends on:** ADR-004（推理服务化/成本）；现有 `user-facts` / `episode-store` / `memory-evolve`

## Context

现有记忆链已经解决了「找得到」和「新旧矛盾」：

- `user-facts.js`：双时态（`valid_from/valid_to`）+ `supersedes/superseded_by`，只软失效不删除（`:159-170`）；
- `episode-store.js`：空闲 30 分钟 + ≥6 轮，把对话压成叙事卡片，游标不前进就不丢数据；
- `memory-evolve`：规则门控 + 8090 嵌入去重 + 每 6 轮巩固，0 LLM；
- `memory-recall`：召回走易变尾巴，冲突时有一次很小的 LLM 裁决。

缺的是**结论**：她记得「他周三说睡眠不好」「他周四 23 点还在打游戏」「他周五说困」，
但说不出「他这周作息很乱」。也记不住「他答应周末给我听新曲子」这种**未完成回路**。

直觉方案是「每晚定时总结所有记忆」。这有三个问题：
1. 用户作息不固定，固定时刻经常人在游戏/不在；
2. 全量总结的 token 随历史线性增长；
3. 没有证据链的总结就是幻觉，而且无法审计。

## Decision

1. **触发器用重要性累加器，不用时钟**（Generative Agents 的做法，`reflect.py:135` + `perceive.py:178`）：
   每条新事实/片段给 `importance ∈ 1..10`（规则权重 + 嵌入新颖度），累加；
   `acc ≥ 60` 且新增 ≥6 条 且 `idle ≥10min` 才反思；每天 ≤4 次、间隔 ≥1h。
2. **反思只读「游标之后」的新增条目**，输入 ≤1500 tokens；输出是 `insights.jsonl` 的追加记录，
   **必须带 ≥2 个 `evidence_ids`**，否则整条丢弃（GA 的 insights+evidence，`reflect.py:38`）。
3. **沉淀有两道闸**：insight 只能先进 `insights.jsonl`；要写进 `user-facts` 必须
   ①`confidence ≥0.75` 且 ②同一结论在 ≥2 次独立反思中出现（或 3 条以上证据）。
   写入用 `source:'reflection'`、置信度 `min(0.7, insight.confidence)`（反思结论永远低于用户明说），**只 supersede 旧事实，绝不删除**。
4. **矛盾处理复用现有裁决**：`memory-recall._adjudicateFact` 的小 LLM 调用，不新建第二套。
5. **开放回路搭 episode 的车**：规则先抽（承诺/待办句式），命中才在该 episode 的既有 LLM 调用里顺带抽；
   不额外增加调用。TTL 7 天，最多提醒 1 次/天，且只在 `working/idle`。
6. **不建图数据库**：关系时间线是 `user-facts + episodes` 的纯函数视图。

## Options Considered

### Option A：重要性累加 + 证据链 + 双闸沉淀（选中）

| 维度 | 评估 |
|---|---|
| 成本 | 0–4 次/天；没值得想的事就 0 次 |
| 质量 | 有证据可审计；双闸抑制一次性的过度概括 |
| 复杂度 | 中（importance 打分、游标、insight 存储） |
| 风险 | importance 是启发式，可能低估「安静但重要」的事 |

### Option B：每晚固定 3 点总结

| 维度 | 评估 |
|---|---|
| 实现 | 最低 |
| 成本 | 固定尖峰；历史越长输入越大 |
| 时机 | ❌ 3 点可能人在游戏/不在；反思结果没人看 |

**否掉原因**：把「什么时候值得想」交给时钟，是最贵的偷懒。

### Option C：每 N 轮反思一次

| 维度 | 评估 |
|---|---|
| 实现 | 低 |
| 质量 | ❌ 寒暄也会触发；6 轮里可能全是「哈哈哈」 |
| 成本 | 与对话量线性相关，不可控 |

**否掉原因**：轮次不等于信息量；`memory-evolve` 已经用规则门控证明了这一点。

### Option D：每个 episode 都反思

| 维度 | 评估 |
|---|---|
| 质量 | 及时 |
| 成本 | ❌ 一天可能十几个 episode；且相邻 episode 结论高度重复 |

**否掉原因**：反思的边际收益递减，重复结论会污染 `insights.jsonl`。

### Option E：直接上 Zep/Graphiti 图库

| 维度 | 评估 |
|---|---|
| 能力 | 多跳、时序查询最强 |
| 代价 | ❌ 图库进程 + schema + 备份 + 迁移；单机几十条事实用不上 |
| 依赖 | ❌ 与现有 JSON + 原子写体系并行两套真相 |

**否掉原因**：为几十条事实引入图数据库，是把运维成本当能力。

### Option F：把全部事实塞给模型总结

| 维度 | 评估 |
|---|---|
| 实现 | 低 |
| 成本 | ❌ 输入随历史增长，早晚爆上下文 |
| 可信度 | ❌ 无证据链，幻觉无法定位 |

**否掉原因**：违反 ADR-004 的「成本可控」与本文的证据链原则。

## Trade-off Analysis

- **重要性打分的代价**：规则权重会偏向「自述/偏好/计划」，可能漏掉「他今天很安静」这种弱信号。
  缓解：新颖度占一半权重；每月人工抽查 20 条 insight，漏检率 >30% 就调权重。
- **双闸沉淀的代价**：新结论要等第二次出现才进 `user-facts`，学习变慢（可能 2–3 天）。
  这是故意的：一次性的过度概括（「他讨厌工作」）比慢一点更伤。
- **证据链的代价**：每条 insight 多存 2–5 个 id，存储 +30%；换来的是任何结论都能点回原话。
- **不建图的代价**：回答不了「他朋友的朋友」这类多跳问题；接受——当前产品没有这个场景。
- **开放回路搭车的代价**：episode 的提示词变长（+150 tokens），抽取质量受 episode 摘要质量影响；
  换来的是 0 额外调用。

## Consequences

- ✅ 反思成本上限 4 次/天（≤6k in / 1.6k out），无值得想的事时为 0
- ✅ 任何 insight 可审计（evidence_ids）；删除一条 insight 不影响原文与事实
- ✅ 与现有 `user-facts` 的双时态天然兼容，不需要迁移
- ⚠️ `insights.jsonl` 会缓慢增长（≤4 条/天），需要「已被取代/已过时」视图，否则越积越难读
- ⚠️ importance 打分是新的调参面；上线前两周必须有人看抽查结果
- ❌ 不做「自动删除低价值记忆」；只做 supersede/mark stale，删除永远由用户发起
