# ADR-001：进程分层 —— Electron 编排 / Rust 无状态内核 / Python 常驻模型

**Status:** Accepted（2026-11-17 复核确认，补记理由）
**Date:** 2026-11-17
**Deciders:** 用户（产品方向）· 主会话（技术）

## Context

桌面 AI 伴侣要同时干四类活：**渲染**（60fps Live2D）、**系统操作**（截图/键鼠/UIA）、
**模型推理**（ASR/TTS/SER/嵌入/记忆）、**编排**（LLM 链、插件、日程）。

三类活的性质完全不同：
- 渲染必须和 UI 同进程、帧内完成（跨进程 1ms 往返就把 60fps 吃掉一半）；
- 系统操作要**微秒–毫秒级**、常驻、不能每次 spawn（实测 spawn 50ms vs 常驻 1ms）；
- 模型推理**启动慢**（cv2 import 750ms、SenseVoice 加载秒级），必须常驻预热。

## Decision

三层固定分工，**新功能按性质入座**：

| 层 | 语言 | 只做 | 绝不做 |
|---|---|---|---|
| 渲染/编排 | JS（Electron 渲染层 + 主进程） | 帧内采样、插件、LLM 链、状态机 | 阻塞式模型推理、重 IO |
| `pet-core` | Rust | 无状态、Win32 直调、微秒级（截图/窗口/键鼠/UIA/世界快照/知识检索） | 业务状态、调度、决策 |
| 常驻 Python | Python | 有状态、模型、慢启动（ASR/TTS/SER/MemOS/嵌入/声纹） | 帧内调用 |

协议：Node ↔ Rust 用 stdin/stdout 单行 JSON（`pet-core serve`）；Node ↔ Python 用 HTTP/WS 或常驻子进程 NDJSON。

## Options Considered

### Option A：全 Node（用 ffi/napi 直调 Win32）
| 维度 | 评估 |
|---|---|
| 复杂度 | 中（ffi 类型/内存手工管理） |
| 成本 | 低（少一层） |
| 性能 | 中（napi 调用 ~µs，但截图/UIA 的 COM 生命周期容易踩内存） |
| 团队熟悉度 | 高 |

**Pros**：少一个进程、少一份类型契约。
**Cons**：COM/UIA/截图在 Node 里极易崩主进程（主进程崩 = 她整个死）。

### Option B：全 Rust 内核接管编排
| 维度 | 评估 |
|---|---|
| 复杂度 | 高（要重写 LLM 链/插件系统） |
| 成本 | 高 |
| 性能 | 高 |
| 团队熟悉度 | 低 |

**Pros**：性能最好、单进程。
**Cons**：插件生态（23 个 JS 插件）全部作废；迭代速度断崖。

### Option C（选中）：三层混合
| 维度 | 评估 |
|---|---|
| 复杂度 | 中高（三次跨进程） |
| 成本 | 中 |
| 性能 | 各取所长（面板 3.8ms / 截图 31ms / 渲染 60fps） |
| 团队熟悉度 | 中 |

**Pros**：渲染不阻塞、系统操作够快、模型常驻、插件生态保住。
**Cons**：三份类型契约要维护（已踩过 camelCase/snake_case 静默忽略）。

## Trade-off Analysis

真正的权衡点是**崩溃半径**：所有系统调用如果都在 Node 主进程，一次 COM 崩就让整个她消失；
放进 Rust 子进程，崩了可以重启子进程（`pet-core-client` 已有超时即重启）。
性能上 Rust 层不是「更快」，是「**稳定在 1–40ms 且不会拖垮渲染**」。

## Consequences

- ✅ 渲染帧稳定（doctor：白写 0/0、零抢写）
- ✅ 系统操作常驻 1ms，工具不再「慢到不敢用」
- ⚠️ **三份契约**：JS↔Rust 走过 `holdMs`/`arg`/`id` 类型三个真 bug → 已有契约测试（53 断言）
- ⚠️ **两套前端入口**（风险 1）：standalone `pet-runtime/vts-server.mjs` 与宿主 `petbridge/` 分叉
- 🔁 要复查：新增常驻服务时是否真的「慢启动」——不是就别进 Python 层
