# ADR-005：浏览器与通知源的接入方式 —— 事件推送优先，通知默认不做

**Status:** Proposed（2026-11-18，Phase 2 设计）
**Date:** 2026-11-18
**Deciders:** 用户（隐私边界）· 主会话
**Supersedes:** 无（在 ADR-004 的采样分级下新增两个源）

## Context

Phase 1 的四个便宜源（前台/空闲/SMTC/剪贴板）能回答「在干什么应用」，但回答不了
「在浏览器里看什么」「刚被什么通知打断」。这两件事信息密度最高，也最敏感。

三条既有约束压着：

1. **渲染层不碰外网、不做重活**：世界感知插件在渲染进程（`world-sense/index.js`），
   而 8103 现在是 `Access-Control-Allow-Origin: *` 且无鉴权（`petbridge/vts-server.mjs:367-369`），
   任何本机进程都能 POST。新增入口不能沿用这个口子。
2. **ADR-004 的 1s/5ms 纪律**：不能为了拿 tab 标题去 UIA 轮询浏览器（>5ms），也不能常驻截图。
3. **用户可单源关闭、`privacy=true` 全停**：现有 `world_sense.sources` 语义必须延续。

浏览器侧还有一个现实：Chrome/Edge 的 MV3 service worker 会被挂起，
`alarms` 是可用的周期唤醒；常驻 content script 能拿 DOM，但权限与攻击面都上一个台阶。

Windows 通知侧有一个硬门槛：`UserNotificationListener` 要求 app manifest 声明
User Notification Listener capability（MS Learn「Notification listener」），
而我们发的是 electron-builder 的可执行目录（入口 `大肥鱼.cmd`，`scripts/electron-ui-package/package.json:6`），
没有 MSIX 包身份。

## Decision

1. **浏览器走 MV3 扩展 + 本地事件推送**，不走 native messaging，也不做常驻 DOM 抓取。
   - 扩展只在 `tabs.onActivated/onUpdated`（url/title/audible 变化）+ 60s alarm 时发一条；
   - 目标端口新开 `POST /world/browser`，要求 `X-World-Token`（启动时生成，写入用户目录，扩展设置里粘贴一次）；
   - 只接受白名单字段，服务端丢弃多余字段；只写事实，不触发任何发言。
2. **字段最小化**：默认只存 `{site(origin), title, audible, incognito, tabCount}`；
   不存 path/query（搜索词、视频 id、邮箱 uid 都在里面）；denylist 域连 title 都不存；incognito 只留一个布尔。
3. **选中文本只在用户显式触发时采集**（右键菜单 `info.selectionText`，参考 karakeep `background.ts:108-123`），
   不做「选中即上报」。这是产品语义：她「被允许看」，不是「一直在看」。
4. **通知默认不做**。若做，必须是独立的稀疏 MSIX helper（external location）拿到 package identity，
   按应用 allowlist，默认只上报 `{app,title,at,count}`，正文单独开关；不碰 `wpndatabase.db`。
5. **所有新源都进 `WorldStore` 的事实表**（TTL 120s/10min），复用 `sourceRank` 与 `privacy` 开关；
   不新建第二套状态机。

## Options Considered

### Option A：MV3 扩展 + 本地 HTTP 推送（选中）

| 维度 | 评估 |
|---|---|
| 实现 | 中（扩展 + 一个带 token 的端点） |
| 延迟 | 事件驱动，切 tab 即到（本地回环，无外网） |
| 权限 | `tabs` + 可选 `activeTab`，不申请 `<all_urls>` 常驻注入 |
| 隐私 | 字段可在扩展侧先裁剪，服务端再裁一次 |
| 失败模式 | 扩展没装/被禁用 → 少一个字段，主链不受影响 |

### Option B：native messaging

| 维度 | 评估 |
|---|---|
| 实现 | 高：每个浏览器写注册表 + host manifest + 路径白名单 |
| 安全 | 最好（不走网络端口） |
| 代价 | 换机器/换浏览器/升级路径都要重装；调试要重启浏览器 |

**否掉原因**：单机自用场景，收益（省一个本地端口）小于运维成本；token + 只读事实已够。

### Option C：UIA 轮询浏览器地址栏 / 通知中心

| 维度 | 评估 |
|---|---|
| 实现 | 中 |
| 成本 | 每次 >5ms（违反 ADR-004），且窗口最小化/多显示器就取不到 |
| 稳定性 | 浏览器 UI 改版即挂 |

**否掉原因**：把「便宜源」做成「贵源」，还更脆。

### Option D：读浏览器 History SQLite

| 维度 | 评估 |
|---|---|
| 实现 | 低 |
| 数据 | 只有历史，没有「当前」；DB 被浏览器锁，需复制快照 |
| 隐私 | 全量 URL 落盘，比扩展方案更差 |

**否掉原因**：拿不到实时状态，隐私更差。

### Option E（通知）：直接读 `wpndatabase.db`

| 维度 | 评估 |
|---|---|
| 实现 | 低（SQLite） |
| 稳定性 | 无文档、schema 随版本变、多半 ACL 拒绝 |
| 风险 | 行为与恶意软件取证路径一致，出问题无法解释 |

**否掉原因**：不可依赖、不可维护。

## Trade-off Analysis

- **选 A 的代价**：多一个需要用户手动安装的扩展；扩展被禁用时世界行会少「浏览器」这一段。
  这是可接受的降级——ADR-004 已经规定「采样器坏了只影响一行字」。
- **选 token 而不是 native messaging 的代价**：token 存在用户目录，本机同用户进程可读；
  但它只授予「写浏览器事实」，不授予 `/say`、不授予读记忆，最坏情况是伪造一次「他在看 B 站」。
- **不做通知的代价**：她不知道「刚被邮件打断」，主动关心会显得迟钝；
  换来的是不接触 2FA 验证码、私信、银行提醒这类最高敏感文本。
- **只存 origin 的代价**：分不清 B 站首页和某个视频；用白名单首段 path 折中，默认不开。

## Consequences

- ✅ 浏览器源 0 LLM、一次本地 HTTP（数 ms，与 8103 现有控制口同量级）；默认不落盘，`privacy=true` 一秒内停
- ✅ 8103 新增端点必须带 token，且只写事实（不新增任何「让模型说话」的入口）
- ⚠️ 扩展需要单独分发/更新；Chrome Web Store 审核与 Manifest 变更会成为维护项
- ⚠️ `title` 仍可能含敏感信息（邮件主题、文档名）→ denylist + 单站点暂停是必须的，不是可选的
- ❌ 通知源在 MVP 不存在；`/world` 要如实返回 `notifications: null`，不能假装有
