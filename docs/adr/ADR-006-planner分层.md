# ADR-006：长任务的 planner 放哪一层 —— 计划对象进宿主，不进帧循环、不新建服务

**Status:** Proposed（2026-11-18，待用户拍板）
**Date:** 2026-11-18
**Deciders:** 用户（产品方向）· 本轮调研（技术）
**相关:** ADR-001（进程分层）· ADR-004（世界感知与推理成本）· `docs/调研-电脑操控Agent-2026-11-18.md` §2.1

## Context

「没有 planner」这句话需要先校准，否则会把已经有的东西重造一遍：

- 宿主**已有** 30 轮连续工具调用循环：`live-2d/js/ai/llm-handler.js:377`（`maxIterations = 30`），
  带用户打断（`appState.isInterrupted()`）、连续空响应恢复（`consecutiveEmptyResponses`）、上限兜底回复。
- 也就是说**执行循环不需要新建**，缺的是三样东西：
  1. **计划是隐式的**：只存在于 `voiceChat.messages` 里，跨过 5–6 步后模型就"忘了第 2 步做过什么"（上下文被工具返回噪声填满）；
  2. **没有子任务粒度**：模型不能在"子任务 A 完成"处停下判断，只能整体成功或整体沉默；
  3. **没有终止语义**：循环结束的条件是"模型不再调工具"或"到 30 轮"，两者在日志里几乎不可区分。

同时有三条既有红线约束方案（不是偏好，是已实测的成本）：
- ADR-004：>5ms 的推理不进帧循环；任何"每轮都不同"的内容不许进前缀（缓存命中 88–97% 是命脉）；
- ADR-001：`pet-core` 是**无状态**内核，不做调度与决策；
- 项目铁律：代码不能特异化（换一个应用不该改代码）。

## Decision

**计划对象（todo）由宿主插件持有，按"只写变化"注入易变尾巴；规划调用按需触发，不做前置 DAG。**

1. **形态**：`plan = [{id, text, status: todo|doing|done|failed, verify?: OracleRef}]`，
   存宿主操控插件（与 `skill-library`、`SOM_STATE` 同级），不落 `pet-core`，不进 system prompt。
2. **分层职责**：见下方「分层职责」表。
3. **触发时机**（三条，缺一不可）：
   - 首次：任务被判为"多步"（用户语句含序数/多个动词，或模型首轮就调用了 ≥2 个工具）；
   - 失败：某子任务 `status=failed`（由 ADR-007 的 oracle 判）；
   - 偏离：反射层报告"轨迹与计划不符"（ADR-007）。
4. **不做 DAG**：Agent-S 的 `_generate_dag` + 拓扑排序（`manager.py:225/:263`）解决的是并行依赖，
   我们的任务是线性的；DAG 的代价是两次额外 LLM 调用 + 一个必须容错的 JSON 解析器，
   收益在 3–8 步任务上趋近于零。等真出现并行子任务（如"同时下载两个文件再合并"）再议。
5. **计划可失效**：计划条目必须带 `verify`（指向 oracle），没有可验证条件的条目降级为 `note`，不参与完成判定。

**分层职责**

| 层 | 只做 | 绝不做 |
|---|---|---|
| 渲染层/宿主插件 | 持有 plan、diff、生成 ≤80 tokens 注入文本、状态机（doing/done/failed） | 调 LLM 做规划、等模型 |
| 现有 LLM 循环 | 消费注入的计划行，产出下一步工具调用 | 维护计划真值（不能只靠上下文） |
| 规划调用（同一个 LLM client） | 首次分解 + 失败重规划（输入 `failed_subtask + completed[] + remaining[]`） | 每步都调用 |
| `pet-core` | 无 | 任何 plan 状态 |

## Options Considered

### Option A（选中）：宿主插件持有计划对象 + 差分注入
| 维度 | 评估 |
|---|---|
| 实现 | 中（要写 diff + 预算裁剪 + 状态机，与 `world-sense` 同一套纪律，可复用） |
| 延迟 | 0（规划调用只在 3 个触发点） |
| 前缀缓存 | ✅ 不动前缀（计划行只进最后一条 user 的尾巴） |
| Token | 每轮 0–80；全都没变则 0 |
| 崩溃半径 | 计划丢了只影响本次任务，不影响对话主链 |

**Pros**：不新增进程/端口；复用已有的 30 轮循环与打断；前缀纪律与 ADR-004 一致；可单测（diff 是纯函数）。
**Cons**：计划真值在 JS 里，跨进程调试要看日志；`status` 的推进依赖模型自觉（派发 `done` 信号），
不诚实时只能用 oracle 兜（→ ADR-007）。

### Option B：独立 planner LLM 调用 + DAG（Agent-S 原样）
| 维度 | 评估 |
|---|---|
| 实现 | 高（prompt + DAG 解析 + 拓扑排序 + 重规划上下文拼装，参考实现约 320 行 Python） |
| 延迟 | 首次 +1–3s（两次调用：plan + DAG） |
| 成本 | 每任务多 2 次 LLM 调用；重规划时再 ×2 |
| 收益 | 仅在并行/依赖型任务上显著 |

**Pros**：结构化最强，重规划输入干净（`manager.py:173` 那套）。
**Cons**：**为 3–8 步的线性任务付 DAG 的复杂度**；DAG 无法表达"等用户输入"这类交互节点（我们恰恰需要）；
多一个必须容错的 JSON schema。

### Option C：常驻 Python 服务做 planner（服务化）
| 维度 | 评估 |
|---|---|
| 实现 | 高（新进程/端口/生命周期/健康检查） |
| 延迟 | 管道/HTTP 数 ms（可接受） |
| 成本 | 常驻内存 + 一套新契约 |
| 必要性 | ❌ 规划本身是 LLM 调用，不是"慢启动模型" |

**Pros**：与 ADR-004 的"推理服务化"表面一致。
**Cons**：ADR-004 服务化的是**加载慢的模型**（ASR/TTS/嵌入），规划是**一次 API 调用**，
放常驻服务只增加跳数与故障面。**否**。

### Option D：维持现状（计划只在上下文里）
| 维度 | 评估 |
|---|---|
| 实现 | 0 |
| 失败模式 | 步数一长就丢；无法归因；技能库拿不到子任务边界 |

**Cons**：这正是本文要解决的问题本身。**否**。

## Trade-off Analysis

核心权衡是**「计划的真值放在哪」**：放上下文（D，免费但不可靠）、放 LLM 的产物（B，结构强但贵）、
还是放宿主的一个小对象（A，可靠且便宜，但要自己维护状态机）。

选 A 的代价是"状态机要人来写"，收益是**计划可以被子任务 oracle 逐条验收**——
这是 B 做不到的：DAG 的节点完成与否仍然只能问模型。而 ADR-007 已确定"验收必须读外部状态"，
所以计划必须有一个**宿主可读、可改、可与 oracle 对齐**的表示，A 是唯一同时满足的选项。

第二个权衡是「规划频率」：每步重规划（ReAct 原始形态）会让 token 成本翻倍且引入抖动；
只在首次/失败/偏离时规划，代价是"计划可能过时"——由第 3 条的偏离触发兜住。

## Consequences

- ✅ 新增的都是宿主侧纯函数（plan diff、状态推进），可单测，不需要真机
- ✅ 与 ADR-004 同一条纪律：计划行只在变化时进易变尾巴，前缀 hash 不变
- ⚠️ **模型可能不派发 `done`**：会表现为"计划永远停在 doing"。兜底是 oracle 轮询（ADR-007），
  但会有一次额外的状态读取成本（L2 约 8–40ms）
- ⚠️ **计划粒度过细会拖慢**：8 步任务拆成 15 个 todo，注入行数反而超预算。硬约束：todo ≤ 8 条，超出合并
- ⚠️ 计划对象与 `skill-library` 的技能是两种东西（前者是一次性的，后者是可复用的），
  不要把 todo 直接存成技能（未验证的步骤会污染技能库）
- 🔁 要复查：30 轮上限是否需要随"子任务数"调整（现在是常数 30）
