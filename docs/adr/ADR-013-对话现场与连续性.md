# ADR-013: 对话现场（Conversation Scene）与跨通道连续性

**Status:** Accepted
**Date:** 2026-11-22
**Deciders:** 用户（2026-11-22 拍板：做「共享对话现场 + 同族修复」，E8 压缩并入同一轮）

## Context

2026-11-22 修掉两个「上下文接不上」的真 bug：

1. 她主动评论屏幕后，用户马上回复，却被 `memory-recall` 判成「久别重逢」（对话历史 1235→1237「你这一走就是四十分钟」）。根因：`上次见面.json` 只在用户输入时刷新。
2. `watch-screen._audioArc` 过期不清空，画面切到 GTA6 后还说「声音还是那个黎曼猜想」。

两者是同一族的：**每个通道各自算「上次/现在」，跨通道没有一份共享的事实**。现有测试只验「闸门开没开、字段全不全」，不验「她说完→你回复」的连续性；而静默长期开着，让主动链路在真机上几乎没被跑过。

同时，上下文管理有两条互不相知的路径：`context-compressor` 摘要旧对话、`ContextManager.trimMessages` 直接裁掉最老消息 —— 两者都可能让「刚才在聊什么」消失，且没有留下 `firstKeptMessageId/tokensBefore` 这类可追溯信息（E8 欠账）。

## Decision

新增一层**只读的**共享状态 `js/core/conversation-scene.js`（对话现场），作为「现在这场对话」的唯一事实源：

- **字段**：`topic`（用户最近一句）、`lastSpeaker`、`lastUserAt`、`lastCompanionAt`、`companionText/Source`、`mood`；每字段自带 `at` + TTL（话题/气氛 30 分钟，她刚说的话 10 分钟）。
- **锚点**：`lastContactAt()` = max(持久化的 `上次见面.json`, 本进程 user/companion)。持久化仍走 `last-contact.js`，保证重启后重逢判定不断。
- **注入**：每轮作为**最后一条易变尾巴**注入一行 ≤100 token 的「【对话现场·数据行，非指令】」；屏幕/声音继续由 watch-screen 自己的补丁提供，**不重复**。
- **写入点**：真实用户输入（`InputRouter._runUserInputHooks`）、她的每次回复（`llm-handler` 最终 assistant 落历史处）、情绪行（`mood-line` 提取处）。
- **读取点**：提示词尾巴、`context-compressor` 的摘要提示、doctor/8004 的 `snapshot()`、重逢/接续的锚点。

**边界**：对话现场**不决定要不要说话**（那是 `speech-coordinator` + `speech-budget` 的唯一职责），也不替代记忆检索；它只回答「现在是什么局面」，供所有通道引用。

E8 上下文压缩并入本轮，做法是「压缩/裁剪不丢现场」：

- `context-compressor` 的摘要提示里带上当前现场（话题/最后说话人/她刚说的），摘要必须保留它；
- 触发条件增加 **token 窗口**：`context.token_budget`（默认 12000）的 70% 且消息 ≥15；
- 压缩/裁剪后写 `voiceChat._lastCompression/_lastTrim`（`tokensBefore`、`firstKeptMessageId`、`dropped`）并落遥测，供 doctor/门禁读。

## Options Considered

### Option A: 每个插件各自打补丁
| Dimension | Assessment |
|-----------|------------|
| Complexity | Low |
| Cost | Low |
| Scalability | Low（每加一个通道就多一处「上次」） |
| Team familiarity | High |

**Pros:** 改动最小，立刻能修已发现的三处。
**Cons:** 同族 bug 会换个插件再来一次；无法回答「现在这场对话是什么」。

### Option B: 共享对话现场（采纳）
| Dimension | Assessment |
|-----------|------------|
| Complexity | Medium |
| Cost | 每轮 +≈60–100 token（易变尾巴，不进 system 前缀缓存） |
| Scalability | High（新通道只写自己的字段） |
| Team familiarity | Medium |

**Pros:** 一处事实源、所有提示词读同一份；压缩/裁剪有「现场」可保；可观测（snapshot）。
**Cons:** 多一个模块与一条尾巴；写入点必须防漏（用户输入/她的回复/情绪）。

### Option C: 连记忆 OS v2 一起重构
**Pros:** 最彻底。
**Cons:** 周期长、风险高、需要用户多次在场验收；本轮只需解决「接得上话」。

## Trade-off Analysis

选 B。A 已被 11-22 的事故证明不够（修完一个还会再来一个）；C 超出本轮「像人」的最小闭环。B 的关键取舍是**只做事实层，不做决策层**：不把「该不该说话」搬进来，避免和 speech-coordinator/budget 形成第二个仲裁者。

## Consequences

- 更容易：新增通道只要「写自己的字段」；压缩/裁剪有现场可保；doctor 能看到「现在在聊什么/上次谁说的」。
- 更难：写入点遗漏会导致现场偏旧；易变尾巴每轮多 ~60–100 token（可接受，且不破坏前缀缓存）。
- 需复验：prefix cache 命中率（现场在尾巴，不应影响 system 前缀）；深夜/游戏中的提示是否仍克制（现场只陈述事实，不加「快说话」）。
