## 1. 数据流：从一句想法到 Agent 开干，再到结果回来

### 1.1 先记住：它不是一条链，是三条

| 链路 | 触发 | 执行器 | 会话 | 入口代码 |
| --- | --- | --- | --- | --- |
| **P1 新任务 → 转发** | 用户说一件要执行的事，且没选中已有 T3 任务 | Codex 已有任务，或新建 DeepSeek Harness 会话 | Codex 复用原 thread；Harness 每次新建 `session-<uuid>` | `code/desktop-pet/harness/desktop-work.ts:314` routeInput → `code/desktop-pet/harness/forwarding.ts:101` confirm |
| **P2 选中已有 T3 任务 → 续聊** | 桌宠/管理页选中了某条 T3 任务后再说话 | T3 背后的 provider（`codex`/`dsh`） | 同一个 T3 thread | `code/desktop-pet/harness/desktop-work.ts:316-355` → `code/desktop-pet/app/workbench-service.ts:1345` |
| **P3 新建 T3 任务 → 首轮** | 管理页显式建项目/线程 | T3 provider | 新建 T3 project + thread | `code/desktop-pet/app/workbench-service.ts:358` → `396`/`406` |

三条都在同一处汇合：**输入先过工作路由，再决定是否进入陪伴对话**。这是整个设计的骨架。

### 1.3 逐段说明

1. **入口优先级**：`code/desktop-pet/core/dialogue-pipeline.ts:81` 在用户消息落库之前调用 `work.route()`；返回 `handled` 就直接结束这一轮，不写陪伴记忆、不调陪伴模型。返回 `companion` 才继续原来的聊天管线。这一点非常关键：**工作输入不会污染人格记忆**。
2. **路由不是关键词硬判**：`code/desktop-pet/providers/work-intent.ts:10` 的系统提示要求「只判当前这句话的意图，不做执行」；`:17` 明写「这个判断不发送任何任务，宿主永远要求另一次精确目标的确认」。输出只有 `companion|work|clarify` 和一句澄清问题（`:29-34`）。
3. **成卡与路由分离**：`code/desktop-pet/providers/work-plan.ts:28` 的 planner 只产出 `kind/executor/title/text/reason/targetId/projectId/projectVersion/question/spokenSummary`；`:8` 的系统提示反复强调「不要执行、不要编 ID、项目和目标目录必须匹配、Harness 没有 target、Codex 必须有 target」。
4. **草稿与转发单分离**：`StoredWorkDraft`（`code/desktop-pet/harness/receipts.ts:21`）保存 `originalText`、对话、`canonicalTask`；`ForwardRequest`（`code/desktop-pet/contracts/harness.ts:6`）保存真正要发出去的 `text`、执行器、目标、项目、阶段。草稿可以改，原始话术永远不被覆盖（`code/desktop-pet/harness/receipts.ts:197` 有强制校验）。
5. **确认是唯一的发送授权**：`code/desktop-pet/harness/forwarding.ts:101` 的 `confirm()` 若发现 `phase !== 'awaiting_confirmation'` 就只回读，不重发（`:103-104`）；真正发送前再次执行 `validatePrepare`（`:106`）并核对项目版本（`:107-111`）。
6. **发送边界 exactly-once**：`code/desktop-pet/harness/forwarding.ts:145` 的 `sendConfirmed()` 用 `dispatchAttempted` 做不可逆去重（`:149-151`）；一旦写失败就落到 `unknown`，提示「不会自动重发」（`:170-172`）。
7. **回执与结果**：简单转发路径是 2 秒轮询；结果只存在回执行里，并通过 `announce()` 播报。T3 路径另有事件分页与工作记录，见第 5 节。

## 2. 任务卡 + 用户确认

### 2.1 数据结构（三层）

| 层 | 类型 | 位置 | 关键字段 |
| --- | --- | --- | --- |
| 展示层草稿 | `WorkDraft` | `code/desktop-pet/contracts/desktop-work.ts:9` | `id/version/text/question/projects/targets/executor` |
| 持久化草稿 | `StoredWorkDraft` | `code/desktop-pet/harness/receipts.ts:21` | `status: open/prepared/confirming/confirmed/dismissed`、`originalText`（不可覆盖，`:28`）、`conversation`、`canonicalTask`（`:34`）、`previousDraftId`、`lastPlanningFailure` |
| 转发单 | `ForwardRequest` | `code/desktop-pet/contracts/harness.ts:6` | `id/version/phase/text/executor/target/project/plan/createdAt/confirmedAt/appTurnId/harnessSessionId/result/detail` |
| T3 续聊卡 | `WorkbenchContinuationDraft` | `code/desktop-pet/contracts/workbench.ts:262` | `id/version/state: open/claimed/dismissed/task/input/commandId` |

阶段枚举 `ForwardPhase`（`code/desktop-pet/contracts/harness.ts:5`）：

```
awaiting_confirmation → forwarding → accepted → completed
                                   ↘ unknown / unavailable
```

注意 `accepted` 与 `completed` 是两件事：前者只代表「执行器收下了」，后者才是「这一轮真的结束」。UI 文案也这么写（`code/desktop-pet/management/ui/tasks-view.mjs:5`：`已接收 · 尚未确认完成`）。

### 2.2 确认交互

- **网页**：`code/desktop-pet/management/ui/tasks-view.mjs:103` 的「查看并确认」→ `:107` 弹窗展示最终发送正文 → `:85` POST `/api/tasks/confirm`，带 `id + expectedVersion`。
- **接口**：`code/desktop-pet/management/task-routes.ts:25` 只接受 `id + expectedVersion`，服务端再校验；没有「直接发送」接口。
- **语音**：`code/desktop-pet/harness/desktop-work.ts:178` 播报安排，文案固定为「准备交给 X，项目是 Y，任务是 Z：……。你可以说确认，或者继续修改。」；用户说「确认」后由 `interpretWork` 判为 `confirm`（`code/desktop-pet/providers/work-conversation.ts:36`、`code/desktop-pet/harness/desktop-work.ts:264`），且还必须满足「这张卡确实被完整呈现过」的绑定校验（`code/desktop-pet/harness/desktop-work.ts:162-168`）。
- **绑定防伪**：`WorkInputBinding`（`code/desktop-pet/contracts/desktop-work.ts:17`）把 `draftId + draftVersion + requestId + requestVersion` 冻结；语音说「确认」不能确认一张没被念过的卡，也不能确认已经改过的卡。

### 2.3 拒绝 / 修改 / 取消路径

| 动作 | 触发 | 代码 | 结果 |
| --- | --- | --- | --- |
| 改正文 | 网页编辑 / `revise` action | `code/desktop-pet/harness/desktop-work.ts:428-436` | 只允许 `status=open` 且版本匹配；改后回到 `selecting`，必须重新准备 |
| 重新整理 | `replan` / 说「重新整理」 | `code/desktop-pet/harness/desktop-work.ts:245-300`、`:413-426` | 旧确认单置为 inert（`code/desktop-pet/harness/receipts.ts:155`），草稿重开，保留旧记录 |
| 补充要求 | 语音/文字补充 | `code/desktop-pet/harness/desktop-work.ts:245` + `:284-300` | 走 `canonicalTask`：原始要求 + 已有问答 + 按顺序的修正，**追加而不是替换**（`code/desktop-pet/harness/desktop-work.ts:221-229`） |
| 取消 | 说「取消」 | `code/desktop-pet/harness/desktop-work.ts:272-275` | `dismiss` 草稿，播报取消；已确认的任务不会被取消 |
| 不确认、直接关掉 | UI | `code/desktop-pet/harness/desktop-work.ts:398-406` | 草稿 `dismissed`；转发单从未生成 |
| 确认后再反悔 | — | 没有 | `code/desktop-pet/workbench/capabilities.ts:8-36` 把 `stop_turn` 标为 `unsupported/unverified`；简单转发路径没有可靠的取消语义 |
| 审批拒绝 | T3 原生 approval | `code/desktop-pet/workbench/commands.ts:43-46`、`:82-110` | `thread.approval.respond` 支持 `decline/cancel`，但只在 T3 Codex 精确请求上可用 |

一个很值得注意的取舍：**「拒绝」只发生在确认之前**。确认之后，它宁可显示 `unknown` 并让人去原生会话核对，也不提供「撤销/重发」，因为重发可能造成双执行。

### 3.3 会话与工作目录的关键规则

1. **Codex 不新建会话**：只能对「真实用户在 Codex App 里存在的 thread」派活（`code/desktop-pet/harness/codex-app.ts:91` 过滤掉 `agent_path`/`agent_nickname` 的内部记录），发送前用 `ensureAvailable()` 做一次可逆的原生导航（`:100-110`）。
2. **Harness 每任务一个 session，但 preset 固定**：`createWorkSession()` 强制 `agentPreset='desktop-pet-work-v1'`、`model='deepseek-flash'`、`reasoningEffort='high'`（`code/desktop-pet/harness/connection.ts:63-82`）；不匹配就报 `incompatible`，不会退回默认。
3. **T3 项目与工作区强绑定**：`createNativeTask()` 先 `realpathSync(workspaceRoot)`，再要求 T3 原生 project 的 `workspaceRoot` 完全相等（`code/desktop-pet/app/workbench-service.ts:379-410`）；`verifyProjectLocation()` 在每次派发前复核（`:321`）。
4. **不信任标题/目录名作为身份**：`code/desktop-pet/contracts/workbench.ts:5-6` 明确「标题和匹配的目录名永远不能识别任务」；任务身份是 `taskId + environmentId + t3ProjectId + threadId + providerInstanceId`。

## 5. 结果回执：怎么收、怎么判、怎么落

### 5.1 收法

| 路径 | 机制 | 频率/方式 | 源码 |
| --- | --- | --- | --- |
| P1 简单转发 | 轮询 `refreshReceipt(id)`；桌面每 2 秒一次，且单次只取最多 5 条活跃记录 | 2 秒定时器 | `code/desktop-pet/harness/desktop-work.ts:129`、`:483-500`；`code/desktop-pet/harness/receipts.ts:97`（`observationPage` limit 1-20） |
| P1 Codex | 读该 thread 的 rollout JSONL（大小上限 128MB、必须在 `sessions/` 根内、uid 相同），找 `event_msg.task_complete` 的 `turn_id` | 每次刷新读一遍尾部文件 | `code/desktop-pet/harness/codex-app.ts:148-182` |
| P1 Harness | `session/list` 找唯一 session → 校验 `agentPreset`/非 subagent → `session/page` 最多 16 页、每页 6 条，从后往前翻 → 在 turn 事件里按 `source.rpcId === requestId` 绑定轮次 | 每次刷新一次有界冷读 | `code/desktop-pet/harness/connection.ts:118-215` |
| P2/P3 T3 | `GET /api/orchestration/commands/:id/receipt` 读命令回执；`GET /threads/:id/events` 读元数据事件页；`GET /threads/:id` 读 thread 快照 | 拉取式，服务端分页 | `code/workbench/integration/t3-http-client.mjs:99/173`；`code/desktop-pet/app/workbench-service.ts:1197-1211` |
| 终态入库 | 服务启动后 `recoverTerminalDelivery()` 把 outbox 逐条投给项目记忆；跨库幂等 | 后台 setImmediate + 启动恢复 | `code/desktop-pet/app/workbench-service.ts:1302-1320` |

**不是流式**。AAAAGENT 这一层没有把 provider 的 token 流接进桌宠；它只读「轮次结束/工具审批/运行中」这类结构化状态。T3 自己内部有实时事件，但桥接层是分页拉取。

### 5.2 成功/失败判定（重点：不把「收到」当「做完」）

| 后端 | completed | failed | unknown / 其他 |
| --- | --- | --- | --- |
| Codex | 找到 `task_complete` 且 `turn_id` 精确匹配 → 取 `last_agent_message`（截 4000 字） | 不直接判 failed；`turn_aborted` → `unknown(reason=interrupted)`；后续出现别的 turn → `unknown(continued_elsewhere)` | 其余一律 `unknown`（`code/desktop-pet/harness/codex-app.ts:171-180`） |
| Harness | `turn/end.reason === 'completed'` 且无 pending approval | `error/aborted/blocked/max-tokens/interrupted` → failed | 有 pending approval → `approval`；队列中 → `working`；证据不全 → `unknown`（`code/desktop-pet/harness/connection.ts:185-190`） |
| T3 | `latestTurn.state === 'completed'` 且 `completedAt` 非空 | `state === 'error'` | `interrupted` → cancelled；无 turn → accepted；缺 `completedAt` → unknown（`code/desktop-pet/workbench/t3-read.ts:32-36`） |

判定原则写得很清楚：

- 「命令回执」只是传输事实，不代表 provider 解决了请求（`code/desktop-pet/workbench/commands.ts:81`、`:99`）。
- 「unknown 永远不授权第二次发送」：`code/desktop-pet/workbench/commands.ts:178-190` 的 `readback` 只读账本/回执；`code/desktop-pet/harness/forwarding.ts:170-172`、`:199`、`:240` 都重复这句话。
- **慢的 unknown 不能覆盖快的 completed**：`code/desktop-pet/harness/forwarding.ts:206-207` 在写回前重读最新行。

### 5.3 落工作记录

- P1：从现有代码看，只落 `ForwardRequest`（`phase/result/detail/appTurnId/harnessSessionId`），列表只留最近 50 条 + 未完成（`code/desktop-pet/harness/receipts.ts:90-91`）。**没有看到 P1 的项目记忆抽取路径**；这是它的一个空缺，不是优点。
- P2/P3：终态事件进 `workbench_terminal_outbox` → `ProjectTerminalEvidence`（`code/desktop-pet/workbench/events.ts:56-68`）→ `projectMemory.enqueueTerminal()`（`code/desktop-pet/app/workbench-service.ts:1311`）→ 后台模型抽取 → `project_memory_items` 的 candidate；只有用户明确来源才能 accepted（`code/desktop-pet/projects/project-memory-sqlite.ts:305-306`）。
- 抽取任务本身有独立计费账本与重试保护：`code/desktop-pet/management/project-terminal-processing.ts:18-37` 用 `project-terminal:<hash>:<attempt>` 作为幂等 operationId，上一次费用未结算就不允许重试。

### 6.3 与我们现在的 `dispatch_to_dsh` 对照

我们现在（`_incoming/my-neuro/live-2d/plugins/community/dispatch/index.js`）：

```
_start(task,cwd,wait)                         :970
  → classifyTask() 只拦 GUI 类              :80
  → 并发上限 / 同意图 10 分钟刹车            :1005 / :1015-1027
  → _run(): POST 127.0.0.1:8103/dispatch     :1060-1064
  → 响应 data.ok ? 'done' : 'failed'         :1074
  → _receipt() 主动播报结果                  :1107
  → _check() 查内存 Map                      :1127
```

| 维度 | AAAAGENT | 我们 | 结论 |
| --- | --- | --- | --- |
| 入口 | 路由 → 成卡 → 确认 → 发送 | 一次工具调用直接发 | **缺确认层**，最该补 |
| 任务记录 | sqlite 持久化 + 版本 | 内存 `Map`（`_incoming/my-neuro/live-2d/plugins/community/dispatch/index.js:131`）+ `dispatch-history.jsonl` | 重启即丢；补一张 sqlite/JSON 表 |
| 成功判定 | accepted / completed / failed / unknown 四态 + 证据 | HTTP 响应 `ok` 即 done | **把「收下」当「做完」**，最危险 |
| 重发 | `dispatchAttempted` + unknown 不重发 | 超时后模型可再次调用 `_start` | 会双执行；补 `attempted` |
| 取消 | 确认前 dismiss；确认后无可靠取消 | 无 | 至少补「确认前可取消」 |
| 项目/工作区 | 项目索引 + realpath 校验 + T3 绑定 | `cwd` 字符串直接透传 | 补根路径存在性 + 别名索引 |
| 审批 | T3 approval/question 卡片 | 无（DSH 自己在原生会话批） | 可后置；先不做 |
| 语音回执 | 安排播报 + 完成/失败/审批播报 | `_receipt` 已有一句话播报 | **我们这块不弱**，保留 |
| 防跑飞 | 同意图刹车在 AAAAGENT 没有 | 我们有 10 分钟 2 次刹车（`_incoming/my-neuro/live-2d/plugins/community/dispatch/index.js:1015`） | **我们更强**，保留 |
| GUI 误派 | 靠 planner 的 executor 选择 | 硬拦截 + 查运行状态（`_incoming/my-neuro/live-2d/plugins/community/dispatch/index.js:80`、`:129`） | **我们更强**，保留 |
| 结果记忆 | 项目记忆 candidate/accepted | 仅 `dispatch-history.jsonl` | 中期再做，不急 |

一句话：**AAAAGENT 强在「确认、持久化、终态判定、幂等」，我们强在「硬拦截、刹车、即时播报」**。不要为了对齐它而丢掉我们的刹车和 GUI 拦截。

### 6.4 关于「目标 / 计划 / 审批 / 工作区 / 新对话 / 插件开关」

| 概念 | AAAAGENT 有没有 | 形态 | 对我们的建议 |
| --- | --- | --- | --- |
| **目标（goal）** | 没有独立实体 | 只有任务卡的 `plan.title/reason` 和 `WorkTaskReference.originalRequest`（`code/desktop-pet/contracts/desktop-work.ts:24-28`、`code/desktop-pet/contracts/harness.ts:14`） | 不要引入长期 goal 对象；用「任务卡标题 + 原话」就够 |
| **计划（plan）** | 有，但不持久 | planner 生成 `WorkPlan`（`code/desktop-pet/providers/work-plan.ts:28`）；T3 侧 `ThreadPlanProgress` 只是内存里的当前步骤（`t3-source/apps/server/src/orchestration/ThreadPlanProgress.ts:1-40`） | 可以做「一次性 plan 预览」，不要做可编辑的长期计划树 |
| **审批（approval）** | 有，分两层 | ①用户确认任务卡（`code/desktop-pet/harness/forwarding.ts:101`）；②T3 原生工具审批（`code/desktop-pet/workbench/commands.ts:43`、`code/desktop-pet/management/ui/tasks-view.mjs:101`） | 第一层必须抄；第二层等 DSH 有稳定审批协议再做 |

| **新对话（new task）** | 有 | `thread.create` / `project.create`（`code/desktop-pet/app/workbench-service.ts:396/406`；T3 `t3-source/apps/server/src/orchestration/decider.ts:226/379`） | 我们不需要新建「对话」；需要的是「新任务卡」 |
| **插件开关** | 没有用户级插件开关 | 只有 provider `enabled`、presentation preset `enabledIds`（`code/desktop-pet/management/ui/presentation-view.mjs:33`） | 我们已有插件体系，不必借鉴；能力矩阵（6.1 #8）比开关更有用 |

## 附：一句话总结

AAAAGENT 的派活不是「一个更聪明的 dispatch」，而是**把「说清楚 → 看一眼 → 点确认 → 只发一次 → 只认证据 → 记下来」拆成了六个可验证的状态**。我们最该补的不是后端能力，而是这六段之间的**确认、幂等和终态判定**。
