# 架构重设计：GUI 操控分层（2026-11-09）

> 基于实测数据的架构改造方案。核心思想：**按「延迟 × 可靠性」分三条通道，快通道优先，慢通道兜底。**

---

## 一、实测数据（改造依据）

| 能力 | 实测延迟 | 可靠性 | 瓶颈 |
|---|---|---|---|
| `press_key`（SendInput 常驻） | **19ms** | 高（游戏可识别） | 无 |
| `hold_key` / `click_at` | ~50ms | 高 | 无 |
| `UIA /elements`（常驻服务） | **134-609ms** | 高（Chromium 也能扫） | 遍历树深度 |
| `snapshot`（接入常驻后） | **474ms** 中位 | 高 | 同上 |
| `som_snapshot`（UIA/OCR + 画框） | **1433ms** | 中（OCR 兜底） | Python 启动 744ms |
| `launch_app` | 3330ms | 高 | 程序启动时间 |
| 云端 LLM 决策 | **1807ms** | 高 | 网络 + 模型 |

**关键结论**：
1. **「怎么动」已经很快**（19ms），不是瓶颈
2. **「怎么看」中等**（134-1433ms），是优化重点
3. **「怎么想」最慢**（1807ms），但这是云端 LLM 的物理限制

---

## 二、三条通道的设计

```
用户说话 / 她决定做什么
        │
        ▼
┌───────────────────────────────────────┐
│  路由器：这个任务该走哪条通道？          │
│  （纯本地判断，<1ms）                  │
└───────┬───────────────┬───────────────┘
        │               │               │
   ┌────▼────┐    ┌─────▼─────┐   ┌────▼─────┐
   │ ① 快通道 │    │ ② 中通道   │   │ ③ 慢通道  │
   │ 结构化   │    │ 混合       │   │ 纯视觉    │
   └────┬────┘    └─────┬─────┘   └────┬─────┘
        │               │               │
   19-500ms         500-1500ms      1500-4000ms
```

### ① 快通道（结构化 API）—— 优先

**适用**：有 UIA 树的应用、有官方 API 的游戏、已知坐标的固定操作

| 能力 | 延迟 | 用什么 |
|---|---|---|
| 按键 / 点击 / 输入 | **19-50ms** | SendInput 常驻 :8104 |
| 找元素 / 点元素 | **134-609ms** | 常驻 UIA :8106 |
| 游戏状态（Minecraft）| **50ms** | RCON :25575 |
| 游戏状态（LOL/CS2）| ~10ms | 官方 API :2999 / Valve GSI（**待接**）|
| 固定坐标操作（PvZ 种植物）| **19ms** | pvz plant（已标定网格）|

**判据**：`窗口 class 不是自绘 && 有 UIA 树` → 走这条

### ② 中通道（SoM + 结构辅助）

**适用**：UIA 部分可用、需要视觉确认的场景

| 能力 | 延迟 | 用什么 |
|---|---|---|
| SoM 标注截图 | **1433ms** | uia/ocr + 画框 |
| 点标注编号 | **~40ms** | som_click |

**判据**：`UIA 扫到 <5 个元素` 或 `需要看画面内容` → 走这条

### ③ 慢通道（纯视觉）

**适用**：Qt 自绘（微信）、DirectX 游戏（PvZ）、画面理解

| 能力 | 延迟 | 用什么 |
|---|---|---|
| 全屏截图 + VLM 理解 | **1800ms+** | 云端多模态 |
| OCR 找字 | ~1500ms | RapidOCR |

**判据**：`UIA 完全失明` → 走这条

## 三、现在的代码离这个设计差什么

| # | 差距 | 现状 | 要做什么 |
|---|---|---|---|
| 1 | **没有路由器** | 全靠 LLM 每次自己选工具 | 加 `guiRoute(窗口)` 判据函数，本地决定走哪条 |
| 2 | **慢通道每次起 Python** | som_annotate.py 每次 spawn，744ms 固定成本 | 改常驻 Python 服务 |
| 3 | **没有闭环** | 动作后不知道成不成 | 加 `verify()` 截图对比 |
| 4 | **知识硬编码** | 攻略写在 js 里 | 搬成 md/json 文件 + 检索 |
| 5 | **多开不支持** | 找第一个匹配窗口 | 用 pid 区分 |

## 四、路由器设计（核心新增）

```js
/**
 * GUI 通道路由：本地纯判断，<1ms，不调 LLM。
 * 返回 'fast' | 'mid' | 'slow'，决定用哪套感知方式。
 */
function guiRoute(windowTitle, windowClass) {
    // 已知有官方 API 的游戏 → fast（连截图都不用）
    if (/Minecraft/i.test(windowTitle)) return { ch: 'fast', via: 'rcon' };
    if (/League of Legends/i.test(windowTitle)) return { ch: 'fast', via: 'lol-api' };
    if (/Counter-Strike|CS2|Dota/i.test(windowTitle)) return { ch: 'fast', via: 'valve-gsi' };

    // 已知自绘窗口（UIA 一定失明）→ slow，别浪费时间试
    if (/Qt5|Qt6|QWindow/.test(windowClass)) return { ch: 'slow', via: 'ocr' };
    if (/Unity|Unreal|Godot|SDL/i.test(windowClass)) return { ch: 'slow', via: 'vision' };

    // 已知有 UIA 树（含 Chromium 系）→ fast
    if (/Chrome_WidgetWin|Tauri|ApplicationFrame/.test(windowClass)) return { ch: 'fast', via: 'uia' };

    // 不确定 → 先试 fast（UIA 有 300ms 超时），空了自动降级
    return { ch: 'fast', via: 'uia-probe' };
}
```

**为什么这是关键**：现在每次都是「LLM 自己猜用哪个工具」，而 LLM 只知道工具名不知道「这个窗口有没有 UIA 树」。
加了这个路由器后：
- 微信 → 直接走 OCR，不浪费 300ms 试 UIA
- ZCode → 直接走 UIA（60 个元素，474ms）
- PvZ → 直接走视觉（DirectX，UIA 一定空）

## 五、闭环判断设计（解决「她不知道成功没」）

```js
/**
 * 动作后验证：截图前后对比，判断画面是否真的变了。
 * 这是「她真的种上了吗」这个问题的唯一可靠答案。
 */
async function verifyAction(beforeHash, { timeoutMs = 1500, expectChange = true }) {
    const t0 = Date.now();
    while (Date.now() - t0 < timeoutMs) {
        await sleep(300);                    // 给游戏一帧时间渲染
        const nowHash = await quickHash();   // 感知哈希，~50ms
        if (expectChange ? nowHash !== beforeHash : nowHash === beforeHash) {
            return { ok: true, changed: true, elapsed: Date.now() - t0 };
        }
    }
    return { ok: false, changed: false, hint: '画面没变化——可能卡槽冷却/位置不对/被弹窗挡住' };
}
```

**感知哈希怎么做**（~50ms，不用 VLM）：
- 截图 → 缩到 16×16 灰度 → 算 dHash（64 bit）
- 对比汉明距离 > 5 就算「变了」

**为什么这比调 VLM 好**：VLM 要 1800ms 且贵；dHash 只要 50ms 且免费。
只在「变化了但不知道变成什么」时才调 VLM。

## 六、知识库设计（解决「游戏更新怎么办」）

**现在**：攻略写在 `game-control.js` 的字符串里 → 改攻略要改代码

**改成**：`data/游戏知识/<游戏名>.md`

```markdown
# 植物大战僵尸

## 基本
- 目标：别让僵尸走到最左边
- 资源：阳光（天上掉 + 向日葵产）

## 开局顺序
1. 前 2 列种向日葵
2. 第 3 列种豌豆射手
3. 阳光富余加坚果墙

## 注意
- 铁桶僵尸要多放豌豆
- 卡槽变灰 = 冷却中

## 我发现的新东西
<!-- 她可以自己往这里写 -->
- 2026-11-09：杂交版第 3 关有双发射手，比豌豆强
```

**她怎么用**：
1. 玩之前 `game_knowledge read 植物大战僵尸` → 拿到攻略
2. 玩完 `game_knowledge write 植物大战僵尸 "新发现..."` → 追加笔记
3. 游戏更新了 → 用户改 md 文件，不用改代码

**这就是你说的「像人一样边玩边探索」的最小实现**。

## 七、改造优先级

| 优先级 | 项 | 预期收益 | 工作量 |
|---|---|---|---|
| **P0** | 闭环判断（dHash 对比）| 解决「不知道成功没」 | 小 |
| **P0** | 路由器（guiRoute）| 省掉盲试的 300-1500ms | 小 |
| **P1** | 知识库文件化 | 支持热更新 + 她能写笔记 | 中 |
| **P1** | 常驻 Python OCR 服务 | som_snapshot 1433→700ms | 中 |
| **P2** | 多开支持（pid 区分）| 支持多开 | 中 |
| **P2** | 官方 API 接入（LOL/Valve）| 零风险读游戏状态 | 中 |

## 八、和调研的关系

等调研（GUI 操控加速）回来后会补充：
- 苹果 AX 接口的技术本质 → 确认我们的 UIA 方案是不是同一思路
- Codex 的加速方案 → 看有没有我们漏掉的招
- GUI 专用小模型（<1GB、<100ms）→ 能不能替代 1433ms 的 SoM

但**上面的 P0/P1 不依赖调研结论**——无论调研说什么，闭环判断和路由器都是必须的。
