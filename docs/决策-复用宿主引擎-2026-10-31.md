## 二、为什么这条路能走通

宿主引擎的所有驱动代码都走这条路：
```js
const coreModel = this.model?.internalModel?.coreModel;
coreModel.getParameterValueByIndex(i)
coreModel.setParameterValueById(paramId, value)
```

而我们 `desktop/renderer/index.js`（PIXI 7 + pixi-live2d-display）第 283 行返回：
```js
return { app, model, internalModel: internal, adapter, assets };
// 第 351-352 行：
internal = model.internalModel;
const coreModel = internal.coreModel;
```

**接口完全对得上。** 宿主引擎可以原样吃我们的 PIXI 舞台。

## 三、但有一个硬风险

`pixi-live2d-display` 的标准路径是给 Cubism 2 / Cubism 4 用的。
这个模型是 **moc3 v5**，而且有 **49 个遮罩组**（超过 SDK 默认 36 上限）。

我们之前的 `cubism-renderer.mjs` 就是为了解决这个：
- 4 张遮罩图集（ceil(49/32)）
- `setClippingMaskBufferSize(1024)`
- 否则 49 组遮罩全部溢出 → 白鼻子 + 棕色嘴块

PIXI 版本用的是同一个 `live2dcubismcore`，理论上也能配同样的遮罩参数，
但 `pixi-live2d-display` 是否暴露这个配置口，需要实测。

**这是唯一的可行性门槛，必须先验。**

## 四、验证顺序（先做这个，再决定改多大）

1. **PIXI 能不能正确加载这个模型**（含 49 遮罩组）
   - 用 `desktop/renderer/index.js` 的 `createLive2DStage` 加载 `assets/petbody/`
   - 截图看有没有白鼻子/棕色嘴块（遮罩溢出的特征）
   - 如果溢出 → 查 `pixi-live2d-display` 的 clippingMaskBufferSize 配置口；不行就退回 cubism-renderer

2. **如果 PIXI 通过** → 全部复用宿主引擎，删掉我们的 4 个模块

3. **如果 PIXI 不通过** → 折中：保留 `cubism-renderer.mjs` 作为渲染后端，
   给宿主引擎写一个 `coreModel` 垫片（shim），把 `getParameterValueByIndex` /
   `setParameterValueById` 映射到我们 renderer 的 `getParameter` / `setParameter`。
   垫片大概 50 行，比重造 200KB 划算得多。

## 五、已经确认的事实（不用再查）

- `paramDirector` 和 `emotionEngine` 在 petbody 模式下**都不存在**（实测 `window.paramDirector === false`）。
  所以「说话抽搐有两个来源」的假设**不成立** —— 抽搐只有我们这一层，已修好（单帧跳变 -72%）。
- `window.emotionMapper` 存在，是宿主旧契约的门面。
- 我们的 driver 接口：`{ engine, init, dispose, getModel, getController, setEmotion, setMouth, playMotion, diag }`，
  `setEmotion` 里第一句就是 `bridge?.playConfiguredEmotion(emotion)` —— 说明**已经有一个 bridge 在调宿主契约**。
