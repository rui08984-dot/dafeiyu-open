# 设计：派活 v2（2026-11-23）

> 只读调研产物，不改代码。依据：`dispatch/index.js`、`task-ledger.js`、`verify-contract.js`、`self-guard.js`、`petbridge/vts-server.mjs`、`dsh-dispatch.mjs`、`progress.md §122.3`、`调研-AAAAGENT派活机制-2026-11-20.md`、`D:\agent1super\fleet-bridge\src\*`。
> 一句话：保留「一次调用直接派」的零延迟，把 AAAAGENT 的 `unknown+attempted` 与 fleet 的四态验收/证据链/分任务账本合成我们自己的实现，并补上两者都没有的可靠取消。

## 1 目标 / 不做

**目标**：单次工具调用仍是唯一入口；任务从「派出去」到「结案」全程可见、可停、可追溯；完成判定只认外部证据；断线/重启不产生第二次执行；写文件的活能指定受控工作目录并逐项验收。
**不做**：不搬 T3 工作台/任务卡确认层（不增加确认往返）；不新增二次 LLM 分类/规划；不把任务结果写进人格记忆（只进工作账本）；不做任务依赖图/多 agent 编排；不做强制确认后再发送（零延迟是产品承诺）。

**可验证指标**（验收口径，不达标不算完成）：
1. 写盘任务双执行 = 0：断线注入 3 个时点 × 20 次，同一 `requestId` 的 `attempted=true` 记录恒为 1。
2. 任务可追溯率 = 100%：每次 `POST /dispatch` 都有一行账本；重启后 `GET /dispatch/tasks` 仍能查到。
3. 取消 p95 < 2s（HTTP 请求 → 进程树消失）。
4. 有 `verify` 的任务证据覆盖率 = 100%；无证据却被标 `done_verified` = 0（查询白名单除外）。
5. 重启后 in-flight 丢失 = 0（全部转 `unknown + attempted`）。
6. 3003/浏览器无令牌读任务正文 = 0 次（负向测试）。
7. 派活附加延迟 p95 < 50ms；running 状态 1s 内出现在列表。

### 3.2 数据流

```
插件 dispatch_to_dsh(task, workspace?, verify?, wait?)
  → _start: GUI 拦截 / 同意图刹车 / 并发 2 / 生成 taskId+requestId
  → POST 127.0.0.1:8103/dispatch {task, taskId, requestId, workspace, verify, rework, sessionId?, timeoutMs}
  → vts-server: 校验 workspace 别名→realpath；账本 create(state=running, attempted=false)
  → runner.start: 写 attempted=true & childPid（先落盘再 spawn）
  → DSH 子进程（.exe + ELECTRON_RUN_AS_NODE，不经过 shell）
  → 事件 session/tool/final/status → 账本增量更新
  → 退出/取消/断线 → settle → verify 四态 → 证据快照 → outcome 判定
  → 账本终态 + HTTP 响应（连接还在时）→ 插件回执（诚实措辞）
UI/`GET /dispatch/tasks` 始终读账本，不依赖插件连接
```

### 3.3 状态机

```
POST 接受 → running（attempted=false）
spawn 前   → running（attempted=true）          # 不可逆点
running → done     (outcome=done_verified|done_unproven)
running → failed   (outcome=failed；spawn 同步失败时 attempted=false，这是唯一可安全重派的 failed)
running → cancelling → cancelled (outcome=null, stateReason=cancelled)
running → unknown  (outcome=null, stateReason=disconnect|timeout|restart；attempted=true)
unknown --显式 reconcile（P2，读 DSH session）--> done/failed   # 系统永不自动重派
```

与现有三态的关系：`outcome` 仍是 `done_verified|done_unproven|failed` 三值；`cancelled|unknown` 是**状态**不是成功等级，`outcome=null`、用 `stateReason` 说明原因。`row.state` 保留 `done/failed` 以兼容回执、`_finishGoalForTask`、`dispatch-history.jsonl`，新增 `row.outcome`/`row.stateReason`；旧消费者看到的 `done/failed` 语义不变。`done_unproven` 仍进目标账本（`ok:true`），但 outcome 明确“未证实”，回执不得说成已证实。

### 3.4 数据模型（逐字段）

- 身份/幂等：`taskId`(UUID，客户端生成), `requestId`(24h 内唯一), `parentId`, `origin`(plugin|http), `attemptCount`(正常恒 1), `attempted`/`attemptedAt`。
- 执行：`state`(running|done|failed|cancelled|unknown), `outcome`(三值|null), `stateReason`(cancelled|disconnect|timeout|restart|spawn_failed), `backend`(dsh), `sessionId`, `sessionReused`, `sessionMismatch`, `childPid`, `childStartedAt`。

- 时间/成本：`createdAt`, `startedAt`, `endedAt`, `tookMs`, `settleMs`。
- 结果：`tools[]`(仅名字，≤50), `text`(≤4000), `error`(≤600), `verifyTier`(command|evidence|model|none)。

## 4 关键机制

### 4.1 verify：证据从哪来，何时标 done_unproven

- **信任顺序（同 fleet）**：command > evidence > model > none。DSH 的 `final/tools` 只算 `model`，**永不足以判 done_verified**。
- 若坚持让 DSH“自报证据”（如 final 里带文件清单 JSON），只解析成 `model` 级线索，必须与文件快照交叉核对；对不上就以快照为准，不能单独判 verified。
- 工具面新增 `verify`（一条命令）与 `workspace`（别名）。插件只透传，不执行。
- 执行顺序：DSH 退出 → `settleWorkdir`（mtime 连续 1s 不变，最多 5s）→ 快照 diff → 跑 verify。**先静默再验收**（fleet 实测：不等落盘会读到半成品）。
- 四态：`pass`→done_verified；`fail`→failed（可返工）；`broken`（命令/解释器本身坏）与 `timeout`→done_unproven（“无法判定”，不是模型的锅）。verify 用 `cmd /d /s /c` + `windowsVerbatimArguments`（避免引号嵌套）；`ENOENT` 出现在业务文件=模型没产出（fail），出现在 node/python 可执行=broken。
- 无 verify：查询动词白名单（沿用 `task-ledger.js` 的 `QUERY_VERB`/`MUTATE_VERB`）→done_verified；有文件改动→done_unproven；无改动→done_unproven（原因写“无可观测后果”，不伪造成功）。
- 返工：仅 `verdict=fail` 且 `round < reworkMax`（默认 1，上限 3）。返工走同一 session（`--session-id`，待实测）；不可用则新会话并注入“验收失败输出 + 上次改动文件 + 只修不推倒”。每轮重跑 verify；`broken/timeout` 不返工。模型升档（换 DSH model）P2，**待实测 CLI 是否支持 `--model`**。

### 4.2 断线/超时：unknown + attempted，不可重派

- `attempted=true` 必须在 spawn **之前**同步落盘；落盘失败就不 spawn（宁可拒派，不可不可追溯）。
- 三种断法分开：①HTTP 响应断（子进程可能还在跑）②子进程超时被杀 ③主进程重启。三者一律 `state=unknown, outcome=null, stateReason=disconnect|timeout|restart, attempted=true`，回执明确“结果未知，不要重复派”。
- 唯一可安全重派的是“spawn 同步失败”（`attempted=false, state=failed`）：同 `requestId` 允许重试一次；一旦 `attempted=true`，同 `requestId` 永不重派（`requestId` 与 task+workspace 绑定，内容不同返回 409）。
- 超时后**仍跑一次 verify**：通过→done_verified（超额完成，比 AAAAGENT 只给 unknown 更有信息）；不通过→unknown。
- `close`/`error` 双收口 + `settled` 防重复结案（沿用现有 `_run` 的修复）；账本是事实源，插件内存只是缓存。

### 4.3 会话续聊

- 从 DSH `type=session` 事件取 `sessionId` 落账本；`dispatch_followup({taskId, task})` 只在父任务终态且 `sessionId` 存在时允许，创建 `parentId` 子任务。
- `POST /dispatch/followup` 由服务端拼 `--session-id`；**DSH 是否稳定接受该参数 = 待实测**（探针：同一 id 连发两次，看 `session` 事件回传是否相同、是否复用历史）。
- 失配处理：回传 sessionId 与请求不一致 → `sessionMismatch=true, sessionReused=false`，回退“新会话 + 父任务摘要（≤1200 字）+ 改动文件清单”，回执说明“没接上原会话，已带上下文重开”。
- 子任务独立 `attempted/verify/outcome`；父任务结果不复制进子任务，只作引用。

### 4.4 工作目录

- `config.json` 新增 `dispatch.workspaces`：`{ "pet": "<project-root>", "dsh": "D:/agent1super" }`；`dispatch.defaultWorkspace="pet"`。插件 schema 只接受别名。
- 服务端：别名查表 → `realpathSync` → 必须是已存在目录、非盘根、深度 ≥2；失败返回 400 `unknown_workspace/workspace_missing`，`attempted=false` 不消耗。
- 仍拒 HTTP `cwd`（沿用 `sanitizeDispatchHttpBody` 的 `ignoredCwd` 日志）；`workspace` 不是路径，是白名单键。
- 快照/verify/DSH 子进程三者 cwd 同一 realpath；越界判定两侧都归一化到 root（fleet 1015 坑）；root 外改动只能靠 git status 提示，明确标注“工作区外不可见”。

### 4.5 取消

- `POST /dispatch/cancel {taskId}`：仅 `state=running` 且本进程持有 child 句柄时执行 `taskkill /PID <pid> /T /F`；轮询进程消失（≤2s）→ `cancelling→cancelled`。
- 主进程重启后账本里没有句柄 → 返回 `cannot_cancel` + `state=unknown`，提示去任务管理器/原会话核对；**不猜 pid**（Windows pid 复用会杀错进程）。
- 取消后立即拍快照，`partialWrites` 列出已写文件；回执固定话术：“已停止；已经写下的文件不会回滚”。
- UI 取消按钮只在 running 显示；双击幂等（第二次返回 cancelled）。

### 4.6 并发：保留 2，拒绝而不是排队（结论）

- 结论：**不排队**。理由：①队列会让“已接受但未开始”成为第二个不可见状态，重启后更难恢复；②单用户桌面场景 2 个足够，排队只会把延迟藏起来；③排队任务的工作目录可能已被用户改动，开跑即错。
- 超限返回 `busy` + `running:[{taskId,preview,tookMs}]` + `retryAfterMs`，插件原刹车逻辑保留；同一意图 10 分钟 2 次仍生效，且 `unknown` 也计数。
- P3 若实测 busy 率 >20% 再评估队列；届时必须有 `queued` 状态、持久化和启动恢复，不能内存队列。

### 4.7 权限

- `GET /dispatch/tasks`、`GET /dispatch/tasks/:id` **无条件**要求 `X-Pet-Token` = `.control-token`（timingSafeEqual；不是“仅带 Origin 时”）。插件用 fs 读同一令牌文件（路径推导与 vts-server 一致）；控制中心是独立进程，列表直读账本文件（只读），取消/详情用 fs 读令牌后调 8103；宠物主窗如需展示走主进程 IPC。
- 列表只回 `taskPreview≤120`、状态、耗时、outcome；正文/证据只在详情端点。3003 遥控页白名单**不新增** dispatch 路由；加负向测试。
- `POST /dispatch|cancel|followup` 沿用现有“带 Origin 必须令牌、无 Origin 内部放行”；HTTP 入口永不接受 cwd。
- 日志只打 preview，不打全文/密钥；账本文件权限尽量 0600。

## 6 风险与许可

- **AAAAGENT**：许可为“非商业使用及署名 1.0”，我们只能做**行为参照**；不抄代码/提示词原文/SQL/协议实现。本文所有 AAAAGENT 结论来自 `docs/调研-AAAAGENT派活机制-2026-11-20.md` 的 path:line，不构成复用依据。商业化版本必须完全独立实现。
- **fleet-bridge**：用户自己的代码，可借鉴四态/证据/账本/scope 思路；但**不跨项目 import、不复制文件**，在 `petbridge/` 内用 ESM 重写（预计 verify≈120 行、ledger≈100 行、runner≈200 行）。
- **DSH 漂移**：`--session-id`、`--model`、`--json` 事件名（`session/final/status/tool`）均**待实测**；runner 解析要容忍未知事件，账本记录 DSH 版本。
- **Windows**：`taskkill /T /F` 能杀进程树；但主进程重启后无句柄，取消降级为 `unknown`（不猜 pid）。`spawn` 必须 `.exe + ELECTRON_RUN_AS_NODE + shell:false`，避免多行任务被 cmd 截断（现有 `dsh-dispatch.mjs` 已修复，保留）。
- **快照成本**：跳过 `.git/node_modules/dist/build/.venv`，上限 4000 文件/8MB；超限降级 `evidence.unavailableReason`，不阻塞结案。
- **隐私**：任务正文/结果只进工作账本，不进人格记忆；列表脱敏 + 令牌；保留 200 条终态，不无界增长。
- **不新增进程/端口**：账本与 runner 都在已存在的 Electron 主进程内；控制中心复用现有独立进程与 8103；无 3003 新路由。

## 7 如果只能先做 3 件事

1. **账本 + 可见性（P0）**：`dispatch-ledger.mjs` + `GET /dispatch/tasks`（token）+ UI 区块。理由：没有账本，后面的 unknown/取消/续聊都无处落；这是唯一能同时解决“不可见、重启即丢、不可追溯”的一步，且零新进程。
2. **unknown + attempted + requestId 幂等（P0）**：在 spawn 前落 `attempted`，断线/超时/重启一律 `unknown`，同 `requestId` 复用旧记录。理由：这是唯一会造成**真实数据损坏**的缺口（写盘任务做两遍）；实现只在 vts-server + 插件 `_run` 两处，成本最低、收益最高。
3. **取消（P1 最小版）**：vts-server 持有 child 句柄，`taskkill /T /F` + `partialWrites` 提示。理由：用户第一诉求是“能停”；AAAAGENT 明确做不到，这是我们最直观的超越点；依赖第 1 步的账本和第 2 步的 running/attempted 语义，顺序不能颠倒。

之后才是 verify/workspace（让“完成”可信）、followup（让长活能接着改）。
