### 1.3 现成工具（切分 + 增量）

| 工具 | 许可证 | 能抄什么 | 落地成本 |
|---|---|---|---|
| **MediaWiki API** `action=query&generator=allpages` + `prop=revisions&rvprop=content&rvslots=main` | MediaWiki 官方 | 一次拿 50 页 wikitext（实测 pvz zh / biligame 均可用） | 极低 |
| **MediaWiki API** `list=recentchanges` + `rcstart/rcend/rcprop=ids\|timestamp\|sha1\|sizes` | MediaWiki 官方 | **增量更新的正解**：只重抓 revid/sha1 变了的页面。`$wgRCMaxAge` 在 Wikimedia 是 30 天，超出窗口需全量对账 | 低 |
| **mwparserfromhell** | **MIT** | wikitext → 去模板/去 ref/取纯文本/取内链；有 C tokenizer，纯 Python 回退 | 半天 |
| **semchunk** | **MIT** | 按 token 计数切块，支持 overlap/offset；`semchunk.chunkerify(tokenizer, chunk_size)` | 半天 |
| **chonkie** | **MIT** | `RecursiveChunker`（层级分隔符）/`SemanticChunker`（嵌入相似度断点）/`LateChunker` | 半天（与 semchunk 二选一） |
| **LlamaIndex `refresh_ref_docs`** | MIT | 增量重索引思路：同 id 文本变了才重建（官方文档明确 "updating documents with the same ID but changed text, while inserting unseen documents"）。**只抄思路，不引库** | 0（已在 recentchanges 里实现） |

**切分策略（推荐，Wiki 专用）**：
1. 先按 **MediaWiki 章节**切（`action=parse&prop=sections` 能拿到章节树），不按固定字数硬切——攻略的"阳光产出/冷却/克制关系"天然是章节。
2. 单块上限 **400 中文字 + 60 字重叠**（现有 `PROMPT_BUDGET=800` 字符，取两块刚好）。
3. 丢弃纯导航/模板/图集章节：标题命中 `导航|引用|参考|分类|画廊|Gallery|导航栏|外部链接` 直接跳过。
4. `id` 用 `游戏:语言:标题#章节`，保留 `revid` 与 `fetchedAt`——这样增量更新可以精确到章节。

### 1.5 存储格式（能直接进现有管线）

新增第 4 层 `pet-runtime/knowledge/wiki/<游戏>.jsonl`，一行一条：

```json
{"id":"pvz:zh:向日葵#阳光产出","text":"向日葵每 24 秒产 25 阳光…","kind":"wiki","source":"https://pvz.fandom.com/zh/wiki/向日葵","revid":12345,"fetchedAt":"2026-11-09","version":"1.0.0.1051","weight":0.8}
```

然后在 `knowledge-base.js` 的 `loadLayers()` 里加一个 `wiki` 分支（约 20 行）、在 `flattenToDocs()` 里映射成 `Doc{id,text,searchable,embedding:[],weight,meta:{layer:'wiki'}}`——**Rust 侧零改动**，`meta.layer` 已经是字符串字典。

若不想改代码：条目 ≤300 条时可塞进 `live/<游戏>.json` 的 `extra[]`（现有 loader 已支持），但 1,000+ 条会让单文件过大、每次全量 `JSON.parse`，不推荐。

### 1.6 推荐落地：**genshin-db + minecraft-data 先上，PvZ 再抓**

理由：两个 MIT npm 包零抓取、零许可风险、结构化，一天内能让 29 条规则涨到 6,000+ 条；PvZ 是唯一必须爬的，且只有 480 页，放第二步。

**3 步实施路径**

1. **零抓取层（半天）**：直接下 npm tarball（`npm pack genshin-db minecraft-data` 只下载解包，不写 `node_modules`、不改现有依赖）→ 写 `pet-runtime/tools/kb-import-npm.mjs`，把 `ChineseSimplified` 的角色/武器/圣遗物/食材/敌人、以及 minecraft-data 的 blocks/items/recipes 拍平成上文 JSONL，输出到 `knowledge/wiki/原神.jsonl`、`knowledge/wiki/我的世界.jsonl`。
2. **PvZ 抓取（半天）**：写 `pet-runtime/tools/wiki-fetch.mjs`：
   `allpages(aplimit=50)` → `prop=revisions&rvprop=content|ids|timestamp&rvslots=main` → `mwparserfromhell` 等价的 JS 实现（或用 `mediawiki-parser` 之类的纯 JS 包；若无合适 MIT JS 版，就把这一步做成一个 Python 小脚本，项目已有 Python 工具目录先例）→ 按章节切块 → `knowledge/wiki/植物大战僵尸.jsonl`。抓取间隔 200ms，UA 注明来源。
3. **接入 + 增量（半天）**：`knowledge-base.js` 加 `wiki` 层；另存 `knowledge/wiki/.state.json`（每页 revid + sha1），下次跑先 `list=recentchanges&rcstart=<上次时间>&rcprop=ids|sha1`，只重抓变化的页。

**验收方式**

- `grep -c '' knowledge/wiki/*.jsonl` 总数 ≥ 1,000，且 `node -e` 抽查 20 条 JSON 可解析、`text` 长度 50-500。
- 走现有 `knowledge` 工具查「向日葵 产阳光」「胡桃 元素战技」「钻石镐 合成」，`trace.corpus` 明显变大且 top-3 命中。
- 随机抽 20 条与原 wiki 页面段落逐字比对，**不得有编造**（这是硬验收，防止解析器把模板参数当正文）。

### 2.3 常驻 vs 现 spawn：实测对比

**实测条件**：本机 Windows 11 / Python 3.13.3 / 同一张合成中文测试图；每档取多次最小值（机器有其他进程，波动约 ±30%）。

| 场景 | 现 spawn（实测） | 常驻服务（预估/实测推算） | 说明 |
|---|---|---|---|
| 固定成本（import + init） | **1,431ms**（系统 Python + rapidocr_onnxruntime 1.2.3，实测） | **0**（进程启动时付一次） | 每次调用净省 1.4s |
| 全屏 2560×1600 | 固定 1,431 + 推理 **1,091ms** ≈ **2,522ms** | **≈1,091ms** | 省 57% |
| 窗口 1024×768 | 1,431 + **518ms** ≈ 1,949ms | **≈518ms** | 省 73% |
| 单行 400×60（默认参数） | 1,431 + **1,052ms** ≈ 2,483ms | ≈1,052ms | **注意：小图反而慢**，见下 |
| 单行 400×60（**rec-only**，3.x venv） | — | **68ms** | 跳过检测，只跑识别 |
| 单行 400×60（det 限长改 max=736，3.x） | — | **205ms** | 关掉"小图放大" |

**为什么小图反而更慢（本次新发现的根因）**：RapidOCR 默认配置 `Det.limit_side_len: 736, limit_type: min`（`D:/tools/rapidocr/Lib/site-packages/rapidocr/config.yaml:141-142`，实测读到）。`min` 的语义是"把**短边**拉到 736"——400×60 的短边会被放大 **12.3 倍（面积约 150 倍）** 再送进检测器，所以 400×60 比 1024×768 还慢。改成 `limit_type: max` 后同一张图 3,161ms → **205ms**（实测，约 15 倍）。

**这条改变了结论**：GUI 加速文档说"常驻只省 744ms，省完仍 2.4s，治标不治本"——**对全屏成立，对"已知区域的单行文本"不成立**。桌宠最常见的 OCR 需求恰好是后者（阳光数字、卡槽冷却、血条数字），所以真正的收益不是"常驻"本身，而是**常驻 + 区域裁剪 + 跳过检测**：

- 全屏整图：~1.1-2.5s（救不了，别做）
- 1024×768 窗口：~0.5-2.0s
- 400×60 已知文本行 rec-only：**68ms**（比现在快 30 倍以上）
- 400×60 det+rec（限长 max）：**205ms**

### 2.4 推荐落地：**自写 90 行 FastAPI server（抄 RapidOCRAPI）+ 区域/模式参数**

为什么不直接 `pip install rapidocr_api`：`rapidocr_api v0.2.x` 的依赖写死 `rapidocr>1.0.0,<3.0.0`（README 版本矩阵 + PyPI `requires_dist` 实测），而 `D:/tools/rapidocr` 里是 **3.x**——直接装会把引擎降级、模型从 PP-OCRv6 退回旧版。它的源码只用了 `RapidOCR()`、`ocr_res.boxes/txts/scores` 和 `use_det/use_cls/use_rec` 这几个 3.x 仍然存在的接口，**代码本身兼容**，所以"抄代码"比"装包"更划算（也可以 `pip install rapidocr_api --no-deps`，但没实测过，别赌）。

**3 步实施路径**

1. **起服务（半天）**：在 `D:/tools/rapidocr` venv 里 `pip install fastapi uvicorn python-multipart`（fastapi/uvicorn 本机系统 Python 已有，但该 venv 没有——实测 `fastapi MISSING`）。新建 `pet-runtime/tools/ocr_server.py`，抄 `RapidOCRAPI/rapidocr_api/main.py` 的结构，改成：
   - `POST /ocr`：`{image_b64, rect?: [x,y,w,h], mode?: "det"|"rec", use_cls?: bool}`
   - `GET /health`：返回 `{ok, engine, pid, models}`
   - 引擎模块级单例；`Det.limit_type` 默认 `max`、`limit_side_len` 默认 736。
2. **接客户端（半天）**：改 `ocr_find.py` 与 `som_annotate.py`：先 `GET /health`（超时 200ms），通了就 POST，任何失败**回落现有 spawn 路径**（保持兼容，服务挂了不影响桌宠）。
3. **按场景分档调用（半天）**：`som_snapshot` 只在 UIA 失明时用；OCR 时先按窗口矩形裁剪，再按"已知文本字段"（阳光/卡牌/血条）传 `mode=rec`，其余 `mode=det`。

**验收方式**

- `curl` 压测 100 次 400×60 `rec` 请求，**P95 < 300ms**（实测目标，按 68ms 中位留 4 倍余量）。
- 手动 kill 服务后再跑 `som_snapshot`：必须走回落路径仍然成功（日志出现 `fallback:spawn`）。
- 连续 500 次调用后 `RSS` 增长 < 50MB（防 ONNX 会话泄漏）。
- 同一张 1024×768 截图：改造前后端到端耗时对比，目标 ≥3 倍提升。

### 4.3 具体参数建议（可直接当配置）

**触发条件**（三选一，取先到者）：

- `对话历史.jsonl` **新增 ≥ 500 行**，或总行数 **≥ 1,500**（约 6 个月）；
- 文件 **≥ 1 MB**；
- 每天最多执行 **1 次**，定在 **04:00**（避开 `Docker-Weekly-Prune` 的周日 04:00，错开 30 分钟）。

**粒度（三层，只压旧不压新）**：

| 层 | 输入 | 输出 | 字数 | 保留字段 |
|---|---|---|---|---|
| L1 会话纪要 | 每 20-40 轮（按 memory-evolve 的语义切段，`segment_similarity=0.45`） | 1 条 | 200-400 | `who/what/decision/todo/emotion/confidence` |
| L2 日纪要 | 当天全部 L1 | 1 条 | ≤300 | 事实 / 偏好变化 / 未完成事项 |
| L3 主题纪要（可选） | 30 天内同主题 L2 | 1 条 | ≤500 | 仅"长期有效"的结论 |

**保留策略**：

- 原文**最近 200 行永不动**（覆盖当前上下文窗口与 memory-recall 的近期检索）。
- 更早的原文 → `data/归档/对话历史-YYYYMM.jsonl.gz`，**不删除**（可回溯，对齐 Letta "归档可恢复"与项目已有的 evolution 不删只归档纪律）。
- 摘要写入 `data/记忆摘要.jsonl`，每条带 `span:[startLine,endLine]`、`sourceSha1`、`level`、`createdAt`——**必须能回溯到原行**。

**门控与上限**：

- 复用 `memory-evolve` 的 `RULES` 权重：`≥2.0` 才进长期摘要，`<0.6` 直接丢（寒暄不进摘要）。
- 用户画像：`traits ≤ 12`、`habits ≤ 15`、候选池 `≤ 200` 条；候选淘汰规则 `count < 2 && 距今 > 30 天`。
- 检索：BM25 索引建在 **L1/L2 摘要**上而不是 859 行原文——条数从 859 降到约 60，检索更准，且不会撞 `max_docs=4000` 的墙。

**为什么是 500 行 / 200 行 / 200-400 字**：
- 500 行 ≈ 130KB ≈ 一次 LLM 调用 30-40k tokens 的输入，单次成本可控；
- 200 行原文 ≈ 2-3 天的对话，覆盖"刚才说的"；
- 400 字上限对应现有 `context-compressor` 的 `max_tokens=500`，两条链的摘要长度一致，行为可预期。

### 4.4 可直接抄的 Prompt 模板

**L1（会话 → 纪要）**

```text
你是对话归档员。把下面这段对话压成 1 条纪要。
只写事实，不写寒暄，不写情绪修饰，不编造。

输出 JSON（不要 markdown 代码块）：
{"who":[],"what":"","decision":"","todo":"","emotion":"","confidence":"high|medium|low"}

规则：
- who 只写出现的人/角色名，不写"用户""AI"
- what ≤120 字，必须包含具体对象和结果（"他说要换工作"而不是"聊了工作"）
- decision 只写明确做出的决定，没有就空串
- todo 只写用户明确说要做的，没有就空串
- 不确定或含糊的信息标 confidence=low，宁缺勿编

【之前摘要】（可能为空）：
{prev_summary}

【本次对话】：
{chunk}
```

**L2（当天 L1 → 日纪要）**

```text
把今天这些纪要合并成 1 条 ≤300 字的日记账，只保留三类：
1) 发生了什么（事实/事件）
2) 他的偏好或状态有什么变化
3) 还没做完的事

不要抒情，不要重复，不要推断没写的事。冲突时以时间更晚的为准。
【今日纪要】：
{items}
```

> 递归结构抄自 OpenAI Cookbook（"Previous summaries → Text to summarize next"）；"3 问 → 5 洞见"的反思结构抄自 Generative Agents（`thought_count=5`）；"只记已验证/有后续价值的事"抄自项目自己的 `memory-evolve` 门控 + Anthropic 的 Fable 5 结论（游戏 AI 文档 4.4 已引）。

### 4.5 推荐落地：**抄 Letta（Apache-2.0）的分层 + Generative Agents（Apache-2.0）的触发参数，写离线压缩脚本**

不引 Letta、不引 mem0（都是整框架），只抄它们的字段设计与参数；项目已有的 `evolution.py` 继续管 MemOS 库内演化，新脚本只管**落盘历史**这层——两者不重叠。

**3 步实施路径**

1. **写 `pet-runtime/tools/memory-compact.mjs`（1 天，纯 Node，零新依赖）**：读 `对话历史.jsonl` → 按 200 行切块 → 复用 memory-evolve 的 `RULES` 门控 → 调项目现有 LLM（走已有 key）用 L1 模板 → 写 `记忆摘要.jsonl` + gzip 归档原文；支持 `--dry-run`（只打印将压多少）与 `--stats`。
2. **`memory-recall` 加来源（半小时）**：`_rebuild()` 里多读一个 `记忆摘要.jsonl`（`src='摘要'`），`max_docs` 不动；摘要条数少，不会挤掉近期原文。

| **把 Umi-OCR 当 OCR 主链** | 必须 GUI 常驻（手册未提供 headless）、**不支持区域裁剪**（只收 base64/options）、官方自述"对并发支持较差"；只适合做人工对照 |
| **爬 minecraft.wiki** | API 返回 "Please wait" 反爬挑战页（实测 curl 拿不到 JSON）；且 CC BY-NC-SA 3.0 禁商用，上架/变现前必须先清 |
| **原样抄 pvz-jev 的 `offsets.py`** | 文件头自述偏移表源自 `pvztoolkit`（**GPL-3.0**，LICENSE 已核）；整包 MIT 声明与这一个文件的事实不符。只抄 `win32.py`，偏移现场标定 |
| **抄 Baritone 代码** | **LGPL-3.0**（GitHub API 实测），静态链接/分发有传染性；用 MIT 的 `mineflayer-pathfinder` |
| **灌入 PvZ 英文站全部 8,038 篇** | 中文桌宠用不上，且大量是版本/道具/琐碎页；480 篇中文页已覆盖植物/僵尸/关卡 |
| **给在线游戏做内存读取/键鼠注入** | 沿用既有红线（VALORANT 因反作弊不可行；Riot 2026-10-06 起主动阻断读内存） |
| **让 LLM 一次吞下 859 行做摘要** | 223KB ≈ 6-8 万 tokens，贵且会截断；必须分块 + 递归摘要 |
| **用 `AI日记.txt` 当压缩产物** | 它的 prompt 明确要求"总结互动感受、3-5 句、保持人格"，是**人格表演**不是事实归档；混用会污染检索 |
| **自己训 embedding / 微调小模型** | 8090 已有 Qwen3-Embedding 0.6B，1024 维，够用；训模型是几周级投入换不来对应收益 |

## 7. 一句话结论

四个方向里，**性价比排序**是：② OCR 常驻（半天到一天，单行文本 1.0s → 68ms，收益最大且零许可风险）> ① 知识灌入（一天，29 条 → 8,000+ 条，两个 MIT 包零抓取）> ④ 落盘压缩（一天，堵住 4000 条静默丢弃）> ③ PvZ 内存状态（1-2 天，收益最大但要处理 GPL 偏移表 + 版本未验证）。

**最值得先做的一项：② 的「常驻 server + rec-only 单行模式」。** 理由：它是四个方向里唯一一块**已被实测证明有 15-30 倍提升**、且不依赖任何新许可、不改游戏逻辑的改动；改完之后 `som_snapshot`、`click_text`、PvZ 三处 OCR 同时受益。
