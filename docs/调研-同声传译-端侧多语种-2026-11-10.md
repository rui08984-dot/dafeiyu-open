# 端侧多语种同声传译：调研 + 可落地方案

> 2026-11-10 · 基于本机现有 `asr/`（sherpa-onnx + SenseVoice-Small int8 + Silero VAD）的延伸设计
> 结论先行，细节在后。所有"实测/文档"与"估算"都分开标注。

---

## 0. 三个关键判断（先看这个）

**判断一：SenseVoice 做中文/英文/日文/韩文/粤语的同传，很合适；做法语、德语、西语、泰语，不行。**
SenseVoice-Small 的转写能力**只有 5 种语言**（zh / en / ja / ko / yue）。它能识别 50+ 语种（LID），但"能听出你在说什么语言"≠"能转写这种语言"。官方论文写得很明确：Small 做 5 语种低延迟 ASR，Large 才做 50+ 语种（而 Large 没开源）。
所以"拿它做多语种产品"的正确定位是：**CJK+EN 的高性价比主力通道 + 语种路由探针**，欧洲语种必须另配 Whisper / Parakeet / Omnilingual。

**判断二：SenseVoice 是"整句识别"，不是"流式识别"，这决定了它只能做"准同传"。**
它是非自回归 encoder-only，吃完整一段音频再解码。配合 Silero VAD 切句，体验是「对方说完 → 0.3~0.6s 出译文」，也就是**句级交替传译**，而不是「边说边出字」的真同传。真同传必须换流式模型（streaming Zipformer / Simul-Whisper / SimulStreaming），或者接受"每 1s 切块重解码"的折中。
这不是缺陷，是选型问题——旅游对话场景里，句级交替其实比边听边抖的流式更可用。

**判断三：手机能不能全本地跑，能；但"手机全本地"和"质量最好"是互斥的。**
务实的产品形态是**三档可切换**：手机全端侧（离线兜底）／手机采集 + 电脑算力（局域网，质量最好）／云端（任意网络）。三者共用一套协议，后端可插拔——这也是"手机和电脑怎么衔接"的答案。

### 1.1 他们用什么语言/框架写的

| 层 | 主流选择 | 说明 |
|---|---|---|
| 手机 App | **Kotlin（Android）/ Swift（iOS）**，或 **Flutter/Dart** 一套两端 | Timekettle、讯飞这类多平台 App 多为 Flutter 或原生双写 |
| 端侧推理 | **C++ / Rust + ONNX Runtime / Core ML / NNAPI / QNN** | sherpa-onnx 本身就是 C++ 核心 + 各语言绑定；手机端不可能是纯 Python |
| 服务端 | **Python（PyTorch/FastAPI）/ Go / C++** | 云端 ASR/MT 推理；Go 多用于网关 |
| 耳机固件 | **C**（杰理/恒玄/高通 SDK） | 只做蓝牙音频与拾音，不做翻译 |

**给你自己的结论：手机端用 Kotlin（Android）+ Swift（iOS），或 Flutter 一套；算法核心全部走 sherpa-onnx / ONNX Runtime；电脑端用 Python（你现有 `asr_server.py` 就是），两者用同一套 WS 协议对接。** 不要试图在手机上跑 Python。

**共性结论（很重要）：**
1. **没有一家把 ASR+MT+TTS 全塞进耳机**。耳机是"麦克风 + 扬声器 + 蓝牙链路"，算力永远在手机/云。所谓"AI 耳机"卖的是**拾音硬件 + App 生态**，不是端侧算力。
2. **离线是分水岭**。Pocketalk 纯云被骂，Timekettle 靠离线包卖 3000+，Apple 靠端侧做隐私叙事。
3. **延迟宣传值不可信**。0.2s 指的是"单句识别完成到首字音频"的某一段，不是端到端。工程上按 1~2s 做预算才不会翻车。
4. **语种数量是营销数字**。真正决定体验的是"你常去的那个国家的那几种语言"质量如何。

## 2. 技术路线：级联 vs 端到端

### 2.1 级联（ASR → MT → TTS）——推荐做主路线

```
麦克风 → VAD/端点 → ASR(流式或分块) → MT → TTS → 扬声器/耳机
```

优点：
- 每一段都能单独换模型、单独调优、单独降级（没网就换小模型）
- 术语表、说话人、语言路由都好插
- 端侧体积可控：三个小模型加起来 < 1GB
- 出问题能定位到具体一段（你现在的 `asr_server.py` 已经是这个形状）

缺点：
- 误差累积（ASR 错 → MT 更错）
- 丢韵律/情绪（TTS 是"念译文"，不是"用你的声音说"）
- 三段延迟相加

### 2.2 端到端（语音到语音）——只做桌面/服务器增强档

代表：SeamlessM4T v2 / SeamlessStreaming（2.3B，101 源语言 / 96 语言流式 ASR）、Gemini Live Translate（云端）。
优点：保留语气、韵律、甚至音色；延迟可以做到很低。
缺点：**模型太大，手机端不现实**（int8 仍 5GB 级，手机上 RTF > 1）；不可控（术语、人名、数字容易跑偏）；离线部署困难。
**结论：端到端放在"电脑/服务器"形态里做加分项，不做手机主路径。**

### 2.3 流式策略（决定"像不像同传"）

| 策略 | 延迟 | 质量 | 适用 |
|---|---|---|---|
| **VAD 切句 + 整句识别**（SenseVoice 现在的方式） | 说完后 0.3~0.8s | 最好 | 旅游对话、一句一句说 |
| **分块重解码**（1s 块 + 200ms 重叠，只重解不稳定尾巴） | 0.8~1.5s | 好 | 长句、听课 |
| **流式模型**（streaming Zipformer / Simul-Whisper AlignAtt / SimulStreaming） | 0.3~0.8s，边说边出 | 中（会回改） | 会议字幕、连续讲话 |
| **同传级**（wait-k / LocalAgreement-2 + 增量 MT + 流式 TTS） | 0.5~1.2s | 中下 | 发布会、演讲 |

工程上最关键的一条：**只把"已经稳定"的前缀送去翻译**（LocalAgreement：连续两次解码一致的词才算稳定），否则用户会听到译文反复自我修正，体验比慢更糟。

## 3. 模型选型（含许可，产品化必须看）

### 3.1 ASR

| 模型 | 语言 | 体积 | 流式 | 手机可行性 | 许可 |
|---|---|---|---|---|---|
| **SenseVoice-Small int8** | zh/en/ja/ko/yue（5） | 239MB（本机实测） | ❌ 整句 | ★★★★★ 桌面 RTF 0.04，手机估 0.15~0.3 | 代码 MIT；权重 FunASR Model License，**允许商用**（需署名/命名条款） |
| **Whisper tiny/base/small int8** | 99 | 40/80/250MB | ❌（可 chunk） | ★★★★ | MIT |
| **Whisper large-v3-turbo int8** | 99 | ~800MB | ❌（可 chunk） | ★★☆ 旗舰可跑，中端吃力 | MIT |
| **Parakeet TDT 0.6B**（NVIDIA） | v2 英语；v3 25 种欧洲语言 | ~600MB | ✅ 可流式 | ★★★ | CC-BY-4.0 |
| **streaming Zipformer**（sherpa-onnx） | 分语种：zh / en / ko / **fr** / zh-en 双语 | 20M~200MB | ✅ 原生流式 | ★★★★★ | Apache-2.0 |
| **Omnilingual ASR 300M**（Meta） | 1600+ | ~1.2GB | ❌ 批量 | ★★☆ | Apache-2.0（2025-11 开源） |
| **Silero VAD** | - | 1.8MB | - | ★★★★★ | MIT |

**组合建议：**
- 中日韩英粤 → SenseVoice（质量/速度最优）
- 法德西意 → Whisper-small（端侧）或 Parakeet v3（更快更准，欧洲语言）
- 长尾小语种 → Omnilingual 300M（只在电脑端开，手机装不下）
- 需要"边说边出" → streaming Zipformer（法语有官方模型，日语/德语没有 → 只能 Whisper 分块）

> ⚠️ 一个容易踩的坑：sherpa-onnx 的流式 Zipformer 官方**只有 zh / en / ko / fr / zh-en 双语**，没有德语西语日语。想要"流式 + 多语种"，现实解是 **Whisper 分块** 或 **SimulStreaming**。

### 3.2 MT（机器翻译）

| 模型 | 语言对 | 体积 | 手机延迟（估） | 许可 | 备注 |
|---|---|---|---|---|---|
| **Opus-MT / Marian**（Helsinki-NLP） | 1000+ 双向对 | 75~300MB/对 | **50~150ms/句** | CC-BY-4.0（逐模型确认） | 端侧首选：极小极快，质量够日常 |
| **NLLB-200-distilled-600M int8** | 200 语种 | ~600MB | 300~800ms/句 | **CC-BY-NC-4.0（禁止商用）** | 质量好但**不能进商业产品**，只能自用/研究 |
| **TranslateGemma 4B int4**（2026-01） | 55 语种 | ~2.3GB | 1~3s/句（旗舰） | Gemma Terms（可商用，有条款） | 质量接近云；放**电脑/服务器**档 |
| **SeamlessM4T v2** | 100 语种 | 2.3B | 手机不可行 | CC-BY-NC | 只做服务器端到端 |
| 小 LLM（Qwen/Gemma 1~2B）直译 | 多 | 1~2GB | 0.5~1.5s | 各自 | 灵活但不如专用 MT 稳定，且爱加解释 |

**组合建议：**
- 手机离线：**Opus-MT**（按需下载语言对，en↔fr、en↔ja、zh↔en…），一对 100MB 以内，延迟几乎无感
- 电脑/局域网：**TranslateGemma 4B** 或 NLLB（仅自用）；质量档拉满
- 云端：直接调现成翻译 API（成本最低、质量最好）

### 3.3 TTS

| 方案 | 语言 | 体积 | 手机 | 许可 |
|---|---|---|---|---|
| **Piper / VITS**（sherpa-onnx） | 30+ 语种，每语种多音色 | 20~80MB/音色 | ★★★★★ RTF 0.05~0.2 | MIT（音色单独看） |
| **Kokoro 82M**（int8 multi-lang） | 8 语种 | ~80MB | ★★★★ | Apache-2.0 |
| **Matcha / VITS 中文** | zh | 50~100MB | ★★★★★ | 多为 Apache-2.0 |
| 云 TTS | 全 | - | - | 按量付费 |

**建议：Piper 打底**（每语种一个音色，按需下载），Kokoro 做"更自然"的备选。

### 3.4 一句话选型

> **手机端：SenseVoice（CJK+EN）+ Whisper-small（欧洲语种）+ Opus-MT + Piper。**
> **电脑端：Whisper large-v3-turbo（GPU）+ TranslateGemma 4B / NLLB + Kokoro。**
> **两端同一套协议，后端可切换。**

## 4. 手机 vs 电脑：三种部署形态

### 形态 A：手机全端侧（离线兜底）
```
[手机 App] 麦克风 → VAD → ASR → MT → TTS → 耳机/扬声器
```
- 体积：ASR 250MB + MT 100MB×N + TTS 80MB×N ≈ **0.8~1.5GB**（可控）
- 延迟：**1.2~2.2s**（句级）
- 适合：出国旅游、无网、隐私敏感
- 技术栈：**Kotlin + sherpa-onnx AAR（Android）/ Swift + sherpa-onnx（iOS）**；或 Flutter（官方 `sherpa_onnx` Dart 包，一套代码两端）
- 为什么不用 Python：手机上跑 Python 是死路（体积/性能/后台限制），别在这上面浪费时间

### 形态 B：手机采集 + 电脑算力（局域网，质量最好）
```
[手机] 采集 PCM ──WiFi/WebRTC──> [电脑 GPU 服务] ASR→MT→TTS ──> 音频回传 [手机]
```
- 电脑侧：faster-whisper（large-v3-turbo，GPU RTF≈0.05）+ TranslateGemma 4B + Kokoro
- 延迟：**0.6~1.2s**，质量接近云端
- 适合：家里、办公室、车载热点、带笔记本旅行
- 你本机有 NVIDIA GPU + 32GB 内存，这套直接能跑
- 发现方式：mDNS（`_interp._tcp`）自动找电脑，二维码配对，token 鉴权

### 形态 C：云（任意网络）
- 直接调 Gemini Live Translate / 讯飞 / 自建 GPU 服务器
- 延迟取决于网络，质量最好，成本最高，隐私最差

### 「衔接」的核心：一套协议 + 可插拔后端

```python
# 后端抽象（Python 侧）
class AsrBackend(Protocol):
    def start(self, cfg) -> None: ...
    def push(self, pcm: bytes) -> list[Partial]: ...   # 20ms 一帧
    def flush(self) -> Final: ...

class MtBackend(Protocol):
    def translate(self, text, src, tgt, glossary=None) -> str: ...

class TtsBackend(Protocol):
    def synth(self, text, voice) -> Iterator[bytes]: ...
```

三套实现：`LocalOnnx`（手机/电脑 CPU）、`PcGpu`（faster-whisper + TranslateGemma）、`Cloud`。
**切换只改配置，不改协议**——这是"手机和电脑怎么衔接"的工程答案。

### 传输协议（直接复用/扩展现有 asr 契约）

上行（二进制 WS 帧）：PCM16 / 16kHz / 单声道，每 20ms 一帧（320 样本）
控制帧（JSON）：
```json
{"type":"start","src":"auto","tgt":"fr","mode":"conversation","tts":true}
{"type":"ptt","on":true}
{"type":"flush"}
```
下行：
```json
{"type":"partial","seg":12,"text":"I need to","lang":"en","stable":true}
{"type":"final","seg":12,"text":"I need to catch the 8:15 train.","lang":"en"}
{"type":"mt","seg":12,"text":"Je dois prendre le train de 8h15.","lat_ms":{"asr":280,"mt":90}}
{"type":"tts_begin","seg":12,"sr":24000,"codec":"pcm"}
{"type":"metrics","e2e_ms":1180,"rtf":{"asr":0.12,"mt":0.03,"tts":0.08}}
```
传输选型：
- **P0/P1 局域网：WebSocket + PCM**（简单，够用）
- **产品化：WebRTC**（Opus 编码、抖动缓冲、AEC、NAT 穿透，LiveKit/mediasoup 现成）

## 5. 延迟预算（按形态，估算值）

| 阶段 | 手机端侧 | 电脑 GPU（局域网） |
|---|---|---|
| VAD 端点判定 | 200~300ms | 200~300ms |
| ASR（句级） | 300~800ms | 100~250ms |
| MT | 50~150ms（Opus-MT） | 60~200ms（4B） |
| TTS 首包 | 100~250ms | 50~150ms |
| 网络 | 0 | 20~80ms（WiFi） |
| **合计（说完到出声）** | **≈1.2~2.2s** | **≈0.6~1.2s** |

对比：人做交替传译的自然停顿约 1.5~3s。所以手机端侧这个数字**在旅游对话里是可用的**，只是做不到发布会同传。

想再压：① VAD 端点从 300ms 降到 180ms（用语义端点，别用纯静音） ② ASR 用流式 ③ TTS 边译边合成（首句先出）。

## 6. 耳机与音频链路（最容易低估的部分）

### 6.1 蓝牙的硬约束
- **A2DP（高音质音乐）和麦克风不能同时用**。一旦开麦，系统切到 **HFP/SCO**：单声道、16kHz（老设备 8kHz）、延迟 100~200ms、音质明显下降。
- 也就是说：**"用蓝牙耳机边听译文边说"这条链路，音质天然受限**。这不是代码问题。
- **LE Audio / LC3** 能改善（双向低延迟、更高音质），但需要手机+耳机都支持，且 Android 生态碎片化严重。
- iOS 上 `AVAudioSession` 用 `.playAndRecord` + `.allowBluetooth` 才会走 HFP；不设置就是外放。

### 6.2 回声（比延迟更致命）
TTS 播放的译文会被自己的麦克风拾取 → 再翻译一遍 → 死循环。
三道防线：
1. **硬件 AEC**：Android `AudioRecord` 用 `VOICE_COMMUNICATION` 源；iOS 用 `.voiceChat` 模式
2. **半双工门控**：播放期间暂停 ASR（简单粗暴，最可靠）
3. **文本级过滤**：把刚合成的译文文本喂给 ASR 结果做相似度抑制

### 6.3 双人对话的三种拓扑
| 拓扑 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| 单机 + 外放 | 一台手机轮流说 | 最简单 | 吵、回声、不便 |
| 单机 + 双耳机 | 一副耳机两人各戴一只 | 无需第二台设备 | 拾音距离远、需硬件支持 |
| **双机配对**（Timekettle 的解法） | 两人各一台手机+耳机，局域网配对 session | 拾音最好、可各说各的语言 | 要装 App、要配对 |

**建议 P0 用单机外放/有线耳机，P1 做双机配对，蓝牙耳机 P1 再接（接受 HFP 音质）。**

### 6.4 拾音硬件（想认真做产品才需要）
Timekettle W4 的护城河是**骨声纹/骨传导拾音 + 3 麦阵列**——在嘈杂街头，手机麦克风就是废的。软件层面能做的是：
- 波束成形（多麦）→ 需要硬件
- 降噪（RNNoise / DeepFilterNet，端侧可跑，~10MB）
- **VAD 阈值自适应 + 只对"人声频段"做增强**

## 7. 分阶段落地

### P0（3~5 天）：跑通最小闭环，先验证"值不值得做"
1. 把 `asr/asr_server.py` 扩成 `interp/interp_server.py`：
   - 保留现有 `/v1/upload_audio` 和 `/v1/ws/vad`
   - 新增 `/v1/ws/interp`：PCM 上行 → partial/final → MT → TTS 音频下行
2. MT 先用 **Opus-MT**（CTranslate2 或 ONNX，en↔zh、en↔fr 各一对）
3. TTS 用 **Piper**（zh/en/fr 各一个音色）
4. 手机端先用**浏览器**验证（注意：`getUserMedia` 需要 HTTPS 或 localhost，局域网 IP 必须自签证书，这是 PWA 方案的必踩坑）
5. 验收：对着手机说一句中文，1.5s 内听到法语；说一句法语，1.5s 内听到中文

> P0 的产出不是产品，是**延迟数字和可用性判断**。数字出来再决定投多少。

### P1（2~3 周）：Android 原生 App
- Kotlin + `sherpa-onnx` AAR + ONNX Runtime
- 离线模型按需下载（每种语言一个包）
- 前台服务 + 通知栏常驻（Android 后台限制）
- 耳机支持（HFP + AEC + 半双工门控）
- 双机配对（局域网 UDP 广播 + WS session）

### P2（1~2 月）：产品化
- iOS（Swift + sherpa-onnx）
- 术语表/自定义词条（旅游地名菜单、专业术语）
- 字幕模式（不发声，听课/会议用）+ 语音模式
- 云端 fallback + 电脑算力自动发现
- 说话人分离 + 自动语言路由（谁说谁的语言）
- 质量/延迟滑杆

## 8. 风险与待验证

| 风险 | 说明 | 应对 |
|---|---|---|
| **SenseVoice 语种天花板** | 只有 5 种，产品必须多 ASR | 按语言路由；欧洲语种走 Whisper/Parakeet |
| **NLLB 禁止商用** | CC-BY-NC | 商业产品只能用 Opus-MT / TranslateGemma / 云 API |
| **蓝牙音质** | HFP 16kHz，无法与 A2DP 并存 | 接受；或 LE Audio；或硬件方案 |
| **回声** | TTS 被自己拾取 | AEC + 半双工 + 文本抑制 |
| **手机发热/耗电** | 连续 ASR+MT+TTS 满负荷 | 降采样、int8、按需唤醒、VAD 门控 |
| **端侧延迟估算** | 文中手机数字是估算 | P0 必须在真机上实测再定 |
| **App Store 隐私** | 麦克风后台常驻审核严 | 明示用途 + 本地处理说明（这是卖点） |
