# 记忆与技能规范（2026-11-10 三十九轮，用户要求定标准）

> 用户原话：「她现在又有知识库又有 MemOS，只要把自己都给协调好就行了；还有经验什么的学习什么
> 那些技能，是不是要定个规范？这技能怎么写，是要用 skill-creator 来写还是什么的，这个都要定好。」

## 一、四层数据源：谁存什么（**不重叠的分工**）

| 层 | 存什么 | 明确不存什么 | 位置 | 写入方式 |
|---|---|---|---|---|
| **MemOS**（她的"记忆"） | **关于用户的事实/偏好/经历**：「主人喜欢青轴键盘的声音」「11-10 和主人一起看完流量王第三集，他笑了三次」 | 世界知识、操作步骤、游戏设定 | `memos_system/data/qdrant` + graph_store | `POST /add`（LLM 提取 + 重要度过滤 + 实体） |
| **知识库**（她的"常识"） | **关于世界的知识**：原神 467 条（角色/武器/圣遗物）、我的世界 363 条（合成/生物）、游戏攻略 | 用户偏好、操作序列 | `pet-runtime/knowledge/{rules,live}` | 手工/批量导入（genshin-db、minecraft-data 直连） |
| **技能库**（她的"手艺"） | **可重放的动作序列**：「在 QQ 里给某人发消息 = 点列表 → 输入 → 回车」 | 一次性操作、参数不固定的动作、依赖编号的动作 | `knowledge/skills/skills.json` | `skill save`（自动从执行历史切片；**只有 verified 才算成功**） |
| **经验层**（她的"教训"） | **单次动作的成败证据**：「click_text 在 QQ 窗口成功」「snapshot 在微信是空壳」 | 主观感受、推断 | `knowledge/experience/<窗口名>.jsonl` | **自动**（`recordFromResult` 已接线，只记 verified 的） |

### 判定规则（一句话分流）

- 「**关于用户**的」→ **MemOS**
- 「**关于世界**的」→ **知识库**
- 「**关于怎么操作**的」→ 成序列进**技能库**，单次成败进**经验层**

### 冲突与优先级

| 情况 | 处理 |
|---|---|
| 同一事实两边都有 | **MemOS 优先**（用户是个体、时效强）；知识库退为背景 |
| MemOS 说「主人讨厌香菜」，知识库说「香菜很常见」 | 都保留，但回答用户相关问题时以 MemOS 为准 |
| 经验层说「这个按钮点不动」，技能库说「这个技能 3/3 成功」 | **经验层更新**（最近的事实覆盖历史统计）；技能库的可靠度按 Beta 后验打折，不直接信 |
| 知识库没有的冷门问题 | 用通用知识回答，**不要**往 MemOS 写（用户偏好 ≠ 世界知识） |

## 二、技能怎么写（硬性规范）

### 2.1 先澄清一个概念混淆

| | **她的技能库**（skill-library.js） | **skill-creator 技能**（SKILL.md） |
|---|---|---|
| 是什么 | **可重放的动作序列**（JSON：steps + 画面指纹） | **给 AI 读的操作说明书**（Markdown，人类可读） |
| 谁消费 | 她自己的 `skill run`（程序执行） | ZCode/Claude 等 agent（读文档后照着做） |
| 怎么写 | `skill save <名字>`（从执行历史自动切片） | 用 skill-creator 生成 SKILL.md |
| 用途 | 「这个任务第二次做，一条命令跑完」 | 「教任何 AI 怎么做这类任务」 |

**结论**：
- 她要**自己重复做**的事 → **技能库**（不要用 skill-creator）
- 要**教别的 AI / 留给人看**的流程 → **skill-creator**（本项目的 `docs/` 就是这么写的）

### 2.2 技能库的七条硬性要求（代码里已实现，此处定为标准）

1. **只有 verified 的成功才计入 successCount**——「可靠度由世界盖章」，不是自我报告
2. **必须存 `entryHash`**（进入时的画面 dHash）→ 跑之前比对 `sim ≥ 0.9` 才允许跑（界面变了不许跑）
3. **必须存 `exitHash`**（结束画面指纹）→ 跑完 `sim ≥ 0.75` 才算 verified
4. **参数必须自足**：不能依赖 `#编号`（每轮都变）、不能依赖「当前前台窗口」
5. **动作白名单**（REPLAYABLE）：`press_key` / `type_text` / `click_at` / `click_text` / `visual_click` / `semantic`
   - `click_element` / `som_click` **不允许**进技能（编号是运行时状态）
6. **命名**：`<窗口或游戏>_<目标>`，如 `qq_给好友发消息`；描述一句话说清「在什么界面、达成什么」
7. **Beta 可靠度**：`mean = (s+1)/(n+2)`；样本 <3 时打折（1/1 的运气不等于 3/3 的实力）

### 2.3 什么时候该生成技能

| 信号 | 动作 |
|---|---|
| 同一动作序列 24h 内成功 ≥2 次 | 提示 `skill save`（**待实现**：现在要手动） |
| 用户说「以后都这么干」 | 立即 `skill save` |
| 序列里有 ≥1 步是 `click_element` | **不允许**保存（编号不稳），改写或放弃 |

## 四、待补的实现（按优先级）

1. **技能自动沉淀**（24h 内同序列成功 2 次 → 提示 save）——低成本高价值
2. **四层检索仲裁**：`knowledge` action 查不到时自动回落到 MemOS（反之亦然），并在返回里标 `source`
3. **技能 run 的实测**：造一个真实技能（如「打开计算器算数」）跑一遍，验证 entryHash/exitHash 闭环
4. **知识库与 MemOS 的去重**：如果用户说过「我喜欢原神」（MemOS）而知识库有原神条目，检索时不要重复回答

## 六、本轮操控实测记录（2026-11-10 06:40-07:00，真实链路 /remote/say）

### 6.1 三个真任务的结果

| 任务 | 修前 | 修后 | 关键数据 |
|---|---|---|---|
| 计算器 37×15 | 打起 8 步才发现 snapshot 读不到（空壳 2 节点），最后靠 click_at 盲点，**没报结果** | — | 修后发现计算器里已经有「表达式为 37 × 15=、显示为 555」——**她其实点对了，只是读不到** |
| 计算器 12×34 | 2 轮 batch（6+6 步）+ 2 次 OCR，中途 noop 让她犹豫 | **1 轮 3 步 batch + 1 次 OCR → 408 正确** | 步数 14 → 4 |
| 计算器 25×8 | — | **一次成功 200** | 先试 press_key（失败：不认识 multiply）→ 立刻改 click_at 3 步全 confirmed → OCR 读到 200 |

### 6.2 这轮实测抓到的 4 个真 bug（全部已修）

| # | bug | 影响 | 修法 |
|---|---|---|---|
| 1 | `snapshot` 不认 `focus`（只看 arg） | 她传 `focus:"计算器"` → 扫了前台窗口（2 节点空壳）→ 她以为「UIA 读不到计算器」白绕一圈 | arg 空时回落 focus（和 som_snapshot 同款，上次只修了 som_snapshot 漏了最常用的 snapshot） |
| 2 | `click_element` 只有全屏 dHash 验证 | 点「清除条目」把 555→0，Invoke 明明生效却报 `suspected_noop` | 用**整个目标窗口矩形**做 region_gray 局部验证 |
| 3 | `actAndVerifySmart` 先看全屏稳不稳 | 桌面静止时 `stable=true` → 走全屏 dHash，region 根本没被用 | **给了 region 就优先局部**，不问全屏 |
| 4 | `press_key` 不认 `multiply`/`divide`/`plus` 等键名 | 她试键盘输入直接报「不认识的键」，被迫改用整屏坐标点击 | SENDKEY_MAP 补 15 个数学/符号别名（`+` 转义成 `{+}`） |

### 6.3 仍然存在的问题（诚实）

| 问题 | 影响 | 状态 |
|---|---|---|
| 同键连点（9×9 的第二个 9）偶尔仍报 noop | 1/4 概率；她能靠表达式文本判断 | 12×10 灰度采样对局部小字符变化不敏感，可再调阈值 |
| 她偏好「整屏 click_at」而不是「snapshot→click_element」 | 步数多、脆弱（窗口一动就失效） | 修好 snapshot focus 后应改善，需再观察几轮 |
| 饥饿状态压过任务（「饿到腿软了喂我一口」） | 任务进行中她会刷讨食 | **设计问题，需用户拍板**：饿时该不该拒绝干活 |
| `skill run` 未实测 | 技能库只有 save 代码路径 | 下一轮造一个真技能跑通 |

### 6.4 一句话结论

**修前她的操控是「看起来在动，实际读不到结果」；修后是「能一次做完并报对结果」。**
但离「好用」还有距离：路径不够短、同键连点有误报、饥饿会打断任务。
